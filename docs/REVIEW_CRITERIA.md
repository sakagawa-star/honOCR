# docs/REVIEW_CRITERIA.md

## レビュー基準
以下の観点でドキュメント（要求仕様書・機能設計書）およびコードをレビューする。

### 1. ドキュメントレビュー

#### 1.1 ドキュメント間の一貫性
- 要求仕様書と機能設計書の間に矛盾がないか
- 用語が統一されているか

#### 1.2 曖昧性の排除
- 「適切に」「必要に応じて」「など」等の曖昧表現がないか
- すべての条件・閾値・パラメータが具体的数値で記述されているか

#### 1.3 エラーハンドリング・境界条件
- 各機能の異常系（入力不正、外部リソース取得失敗、メモリ不足等）の振る舞いが定義されているか
- 境界値（0件入力、範囲外、空・上限値等）の扱いが明記されているか

#### 1.4 技術スタック・依存関係
- 使用ライブラリとバージョンが明記されているか
- 外部依存（API・モデル・サービスの識別子やエンドポイント）が正確か
- 対象OS・言語処理系のバージョン・実行環境が明記されているか

#### 1.5 データフロー・I/O定義
- モジュール間のデータ型・形式が明記されているか（型・スキーマ・単位・値域等）
- ファイル入出力のパス規約・命名規則が定義されているか

#### 1.6 状態遷移（該当する場合）
- UI/プロセスの状態遷移が網羅的に定義されているか
- 各状態からの遷移条件と遷移先が明示されているか

#### 1.7 非機能要件（該当する場合）
- パフォーマンス目標（処理時間、応答時間、スループット等）が定義されているか
- ログ出力・設定ファイルの方針が定義されているか

#### 1.8 詳細設計の十分性
- 実装者が判断に迷う余地がないレベルまで詳細化されているか

#### 1.9 技術スタックの整合性
- docs/TECH_STACK.md と各設計書の技術スタック記載に矛盾がないか
- 実コードのimportと TECH_STACK.md の記載が一致しているか
- バージョン未固定のライブラリがないか

#### 1.10 重要度分類（ドキュメント）
発見した問題を以下の重要度で分類する:
- **高**: 実装不能（手順・情報の欠落）、ドキュメント間の重大な矛盾、存在しないファイル・セクションへの参照
- **中**: 誤実装につながる曖昧さ、異常系・境界条件など必須条件の記述漏れ
- **低**: 運用に影響しない表記ゆれ、軽微な冗長さ

#### 1.11 ロードマップの次元と式（feat 案件の `roadmap.md` が対象に含まれる場合）

`CLAUDE.md`「パイプラインの切り方（feat 案件の必須手順）」の定義（最終出力〔変数ごとの形・次元・式〕・入力の次元・ステージ表・想定値）に照らし、**式の入力と出力を実際に追って**次の 7 項目を確認する。文面に該当する語があるかではなく、式が繋がっているかを判定する。次元は変数ごとの成分の数であり（スカラー 1、2 成分のベクトル 2、3×3 の行列 9）、変数が複数なら変数ごとに数える。

1. **次元の接続**: 各ステージの出力の次元の式が、次のステージの入力の次元の式と一致する（単位あたりの次元と単位数の両方）。最初のステージの入力は「入力の次元」の実測値に、最後のステージの出力は最終出力の各変数の次元（変数ごと）に一致する。最終出力の式の入力（ステージの出力である測定値）の個数や、報告書に並べる数の個数を、最終出力の次元と混同していない
2. **決める項の被覆**: 最終出力の各変数の式の入力（測定値）のすべてが、いずれか 1 つのステージの「決める項」に現れる。最終出力の各変数が、それらの入力と定数からの式を持つ。決める項が「無し」のステージは、手段の単体疎通か測るステージ（測る項が書かれている）のいずれかである
3. **想定値の導出**: 各ステージの想定値が `予想値 = 式（入力値）` の形で書かれ、式の**入力ごとに**「前のステージの出力（`experiment_log.md` に記録した値。実測値と計算して確定した値の両方）」「測るステージの測る項」「ロードマップで固定した定数」の**いずれかが名指しされている**。入力とはそのステージの外から入る量であり、同じステージの式で先に計算する量（途中の値）は入力に数えず、由来の記載を求めない（展開して書くことも求めない）。判定はこの閉じた 3 種への該当で行う。出所が書かれていて辿れることだけでは適合としない（3 種のいずれかの名指しと、その種に定めた出所の要件〔前のステージの出力は出所のステージ、測る項は測るステージ、定数は典拠〕の両方が要る）。3 種以外のラベル（「調査時点の実測」「事前の測定」等）が付いた入力は、値が正しく出所が辿れても不適合。ロードマップ作成時の調査で数えた値は、前提の表に定数として置かれ（いつ・何に・どの規則を当てて数えたかの典拠つき）、式から前提の番号で参照されていれば「ロードマップで固定した定数」として適合。3 種のどれにも当たらない入力が「3 種のどれにも当たらない」と明記されて報告されている行は、不適合（高）として報告する（書き手が止まって報告した状態であり、規定の改訂まで収束させない）。推測・根拠の書かれていない目視の値・出所の無い定数が式に入っている行、式そのものが無い行も不適合
4. **測るステージの対応**: 想定値の式の入力に実測が無い量があるなら、それを測るステージがその量を使うステージより前に置かれ、測る項がその量と一致する
5. **要求の逆伝播**: 最終出力に対する要求（精度・区間の幅・件数・成立条件）が目標または最終出力の変数に書かれているなら、それが最終ステージから前のステージへ式で翻訳され、該当ステージの停止条件または想定値に現れている。翻訳されていない要求があれば不適合。要求が無いなら「要求は置かない」旨が書かれている（設計上の定数〔許容誤差等〕が最終出力に効いていない場合は、それが要求でないことが明記されている）
6. **幅の計算**: 幅が確率変数に対するものなら、分布・試行数・入力の区間の取り方が書かれている。決定的な量なら幅 0 の理由（乱数・外部状態・順序依存を含まないこと）が書かれている
7. **式と次元の整合**: 各ステージの「入力の次元 → 出力の次元」の式が、入力の次元からその出力の次元を出す変換として意味が合っている（入力のどの成分がどう使われて出力の各成分になるかを式から追える）。式から出る次元と、ステージ表に書かれた出力の次元が一致する。合わない式、または式と合わない次元の記載は不適合

重要度: 項目 3・5 の不適合は**高**（想定値が式から出ていない、または要求が翻訳されていないと、外れの判定と再検討〔`CLAUDE.md`「ロードマップの改訂（再計画）」〕が成り立たない）。項目 1・2・4・6・7 の不適合は**中**。

対象に feat 案件の `experiment_log.md` が含まれる場合（ステップ7 の差し戻し、実験ログの書き換えのレビュー）は、項目 3 として次を確認する: 直前予測が `roadmap.md` の当該ステージの想定値の式に前のステージの出力（`experiment_log.md` に記録した値）を代入した値であり、式に無い項目や幅の無い点予測が加えられていないこと。不適合は**高**。

### 2. コードレビュー

#### 2.1 重要度分類
発見した問題を以下の重要度で分類する:
- **高**: クラッシュ、データ破損、セキュリティ問題、メモリリーク
- **中**: 潜在的バグ、リソースリーク、未使用コード、型の不整合
- **低**: コードスタイル、命名、軽微な非効率

#### 2.2 修正対象
- 重要度:高と中を修正対象とする
- 重要度:低は報告のみ（修正は任意）
