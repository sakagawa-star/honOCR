## 1. 発端

feat-015（chap02 の Q&A コラム見出しの分断修復）の Codex レビューで、Claude Code（当時の
モデルは Opus）は次のように進行した。

| # | フェーズ | 高 | 中 | 低 | 次に行った動作 |
|---|---|---|---|---|---|
| codex-01 | 初回レビュー | 0 | 0 | 0 | `/new` → 全文ゲート |
| codex-02 | 全文ゲート | 0 | **1** | 0 | 反映 → 同一会話で解消確認 |
| codex-03 | 解消確認（同一会話） | 0 | 0 | 0 | 人レビューへ進んだ |

このとき「レビューの進め方」ルール4〜6 は、次の**2つの読み**を許していた。

- **ループ型**: 解消確認が高・中ゼロになるたびにルール4 が再発動し、`/new` → 全文ゲートを
  ゲート自身がゼロを返すまで繰り返す。収束はゲート自身のゼロのみ
- **1回ゲート型**: `/new` による「新しい目」の全文ゲートは1回だけ。ゲートの指摘は同一会話の
  解消確認で閉じ、そこで高・中ゼロに達したら収束

Opus は codex-03 の直後に「再ゲートすべきという解釈も成り立つ」と**両方の読みを自覚した上で**、
ユーザーに確認せず一方を選んで先へ進んだ。ユーザーはこれをルール違反と指摘し、feat-015 は
On Hold となった（当時はループ型の読みに基づいて「ルール4 の無視」と認定された）。

その後、本案件（update-002）のレビュー運用の実測で「ループ型は収束が保証されない」ことが
確認され（§2 の 7）、**ユーザーは意図された規則を「1回ゲート型」と確定した**（2026-08-31）。
この確定により feat-015 の上記進行それ自体は結果的に規則に適合していたことになるが、
**発端の本質は変わらない**: 文書が2つの読みを許し、モデルが曖昧さを自覚しながら確認せず
独自解釈で前進した。本案件の目的は、(1) 収束ルールを1回ゲート型として一意に明文化し、
(2) 解釈で迷った場合の行動（止まってユーザーに確認する）を規則化して、この種の逸脱を封じる
ことである。

なお同じ文書は他リポジトリでも同一内容で運用されており、そこでは問題が表面化していない
（ユーザー確認。ゲートが指摘を返さなければ2つの読みは同じ動作になるため、曖昧さは
feat-015 で初めて顕在化した）。

   当てはまらない。**本案件に限る移行措置**として、codex-08 を収束判定の根拠となる直近の C
   とみなし、その会話の解消確認（B）で高・中ゼロに達したら収束とし、以後 C を追加しない

   解消確認 → ゼロで収束」——を提示した上で「update-002 は継続して」の指示を受けた）

## 3. 現行の記述（変更前・全文）

### 3.1 `#### レビューの進め方`（`CLAUDE.md` 263〜272 行目、2026-08-31 時点）

```markdown
#### レビューの進め方

1. **初回レビュー**: 案件種別ごとの基準と対象ファイルを指定して依頼する（依頼文は後述）
2. **修正**: 高・中の指摘は**全件まとめて反映**してから次の依頼に進む（1件ごとに再レビューを回さない）
3. **再レビュー（解消確認）**: 「前回の指摘に全件対応してドキュメントを更新した。各指摘が解消されたかを確認し、指摘ごとに解消/未解消を判定して報告して。変更点に新たな問題があれば併せて指摘して。」と依頼する。diff の添付は不要（codex が自身の記憶と再読で解消判定できることを検証済み）。高・中ゼロになるまで 2〜3 を反復する
4. **全文ゲート**: 高・中ゼロになったら `/new` を送って会話をクリアし（「新しい目」の確保。ペイン・エージェント名はそのまま）、全文・全基準のレビューを依頼する
5. **ゲートで指摘が出たら**: 全件まとめて反映し、同じ会話（`/new` はしない）で解消確認を依頼する
6. **収束**: 全文ゲートで高・中ゼロが出たら人（ユーザー）レビューに進む（収束前に人レビューはしない）
- 同一会話の回数上限は設けない（案件が適正サイズなら問題にならない。運用して必要になったら検討する）。「行き詰まり検出」（本ファイル「Claude Code 運用ルール」参照）は常時適用する
- レビュー実行時は `docs/REVIEW_CRITERIA.md` の基準に従うこと
```

### 3.2 `#### 結果の保存` の冒頭メタ行（同 288 行目）

```markdown
- 冒頭メタ: 日付・対象ファイル・ストリーム名・フェーズ（反復/ゲート。`/new` の実施を明記）・指摘数（高/中/低）・トークン実測。トークンは `~/.codex/sessions/` 配下の当該 rollout jsonl（`total_token_usage` の累積値）から取得し、jsonl のパスも記録する
```

## 4. 読み違えを許した構造要因

現行の記述は必要な情報をすべて含んでおり、素直に読めば正しい動作が導ける。それでも
モデルが「都合のよい解釈」を挟めたのは、次の4点の構造による。

### 4.1 全文ゲートが「1回だけ」か「毎回」かを特定していない

ルール4 の発動条件「高・中ゼロになったら」は、ステップ2〜3 の反復を抜けた**最初の1回**を
指す読み（1回ゲート型）と、以後も高・中ゼロに達する**たびに再発動**する読み（ループ型）の
両方を許す。ルール6 の「全文ゲートで高・中ゼロが出たら」も、「ゲート自身の結果」（ループ型）
と「ゲートの会話で達するゼロ」（1回ゲート型）の両方に読める。feat-015 の混乱はここから生じた。

### 4.2 「収束」が独立した定義になっていない

「収束」は `CLAUDE.md` の他の複数箇所（§5 の調査表を参照）から参照される用語だが、
定義がルール6 の本文に埋め込まれており、**単独で参照できる形になっていない**。
どの時点のどの「高・中ゼロ」が収束なのかを、参照元から一意に特定できない。

### 4.3 記録様式に収束判定の欄がない

「結果の保存」の冒頭メタ要件（§3.2）には、そのレビューがゲートを経ているか・収束に該当する
か否かを書く欄がない。収束の成立条件（ゲートの実施有無・どのゼロか）が記録に残らないため、
誤った収束判定を記録の時点で検出できない。判定欄が必須なら、ゲート前の解消確認のゼロを
「収束」と書こうとした時点で矛盾が露出する。

### 4.4 逸脱そのものを禁じる明文がない

手順のどこにも「解釈に迷ったら止まる」「手順を省略・読み替えしない」という規定がない。
発端の違反では、モデルは曖昧さを**自覚しながら**独自解釈で前進した。解釈の余地を潰しても、
「例外的状況だ」と称して手順の外に出る動きは残り得るため、逸脱時の行動（止まってユーザーに
確認する）自体を明文化する必要がある。

## 6. 変更の方針（詳細は design.md）

1. 「レビューの進め方」を全置換する。**既存規則の内容は変更せず、規則としては
   「逸脱の禁止」のみを新規追加する（他はすべて表現のみの変更、および §4.1 で顕在化した
   2つの読みに対するユーザー確定の明文化）**
   - 「収束」を独立した見出しの定義として切り出す。**収束ルールは 1回ゲート型**
     （`/new` の全文ゲートは案件につき1回。ゲートの会話——C 自身または C 後の解消確認——で
     高・中ゼロに達したら収束。2026-08-31 ユーザー決定。根拠は design.md §4.5）
   - 依頼を A（初回レビュー）/ B（解消確認）/ C（全文ゲート）の3種に命名し、
     「直前の依頼 × 結果 × C の実施状態 → 次にすること」の遷移表で表す（次の動作が常に一意に定まる）
   - 人レビューの前提2条件を独立させる
   - **逸脱の禁止**を明文化する（遷移表にない動きをしない。省略・不適用の理由を
     思いついたら実行せず止まってユーザーに確認する）
   - 低の指摘は遷移の判定に使わないことを明文化する。旧ルール5 の「指摘が出たら」は
     重要度を区別しない表記だが、同じ手順内の他規定（旧ルール2 の反映対象「高・中」、
     旧ルール3・4 の「高・中ゼロ」判定、旧ルール6 の「高・中ゼロで人レビュー」）が
     すべて高・中で判定していることに基づき「高・中が1件以上」と解釈を確定する
     （規則変更ではない。根拠は design.md §4.4）
2. 「結果の保存」の冒頭メタに、依頼種別（A/B/C）・直前の `/new` 送信の有無・
   **ゲート状態**（C の実施状態。収束時は根拠となる C の結果ファイル名を併記）・
   **収束判定**を必須項目として追加する。同じ B でも C の前後で意味が正反対になるため、
   ゲート状態がないと誤った収束判定を記録の時点で検出できない（§4.3）
3. 既存の情報は削らない（保持の対応表を design.md に置く）
