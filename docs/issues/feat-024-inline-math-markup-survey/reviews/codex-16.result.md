## A（初回）の指摘

### 高: 要求と完了判定の矛盾（`heading_not_found`）

FR-M2-002 は16件すべてで見出し行を特定することを受け入れ基準にしていたが、
設計は未特定でも記録して継続し、完了条件も「状態と理由の記録」のみだった。
**`heading_not_found` があっても M2 を完了し M3 へ進める**状態だった。

**対応**: `heading_not_found` を**合格条件（0件）**に改め、1件でもあれば検査3 に進まず中断。
合格ラインを設けないのは `not_covered` の件数だけであることを明示した。

### 中: `page` が未検証のまま成功に数えられる

`page` は近傍候補からの推定であり、対象候補がそのページにあることを検証していない。
抜き取り確認も `stage=block` の3件だけで、**誤った `page` を成功として 90% を通過しうる**。

**対応**: **前後の一致検証**を導入（両方向の `page_idx` が一致した場合のみ `page`）。
抜き取り確認を `block`・`page` の両方に広げ、`page` の確認に失敗したら
成功率が 90% 以上でも Go にしないことを Go 条件に加えた。

## B1 の指摘

### 高: 一方向のみの `page` が探索打ち切りでも成功扱いになる

「一方向のみ」を章の端に限定する要求に対し、設計は各方向 200 件で打ち切るため、
**章の途中で片側が見つからなくても `page_fwd_only` として成功扱い**できた。

**対応**: 方向ごとの候補数 `n_fwd` / `n_bwd` を先に確定し、一方向のみを `page` とするのは
**もう一方に候補が1件も存在しない**ときに限定。打ち切りで見つからない場合は
`none`（`search_exhausted`）とした。`reason` を6値に整理し、全分岐を擬似コードで明示した。

### 中: `stage` が3件未満のときの抜き取り確認が未定義

60件すべてが `block` なら `page` は0件になり「`page` から3件」を実施できない。

**対応**: 各 stage について **`min(3, 件数)` 件**を確認対象とし、
**件数 0 の stage は「対象なし」として Go の判定に影響させない**ことを統一して明記した。

## B2 の指摘

### 中: 抜き取り対象の選び方が再現不能

要求は「無作為に」選ぶだけでシード・アルゴリズムが未定義、一方で設計は
`page_head` / `page_tail` を優先するとしており矛盾。**選ぶ3件次第で Go/No-Go が変わる**。

**対応**: 「無作為」を廃し、**乱数もシードも使わない決定的な規則**にした
（stage ごとに `reason` の優先順 → `chapter` 昇順 → `offset` 昇順で並べ、先頭から採る）。

## B3 の指摘

### 中: 追跡情報の記録が criteria lock（`requirements.md`）にない

抜き取り確認の追跡情報を `experiment_log.md` に記録する規定が `design.md` にしかなく、
**要求だけで判定すると、選択規則を守ったか事後に監査できないログでも合格扱いにできる**。

**対応**: `requirements.md` に受け入れ基準 **2-c** を新設し、
選んだ各件の `chapter`・`offset`・`stage`・`reason` と確認結果の記録を要求。
記録が無い、または選択規則の順序と一致しない場合は 2-b を満たしたとみなさないことも明記した。
