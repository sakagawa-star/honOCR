### 1.3 発覚の経緯（誰が見つけたか）

- **逸脱そのものを見つけたのは Codex**（`reviews/codex-37` の高1）。ただし発端は**ユーザーの問い**（時系列 6・7）であり、
  それが無ければ実験ログの書き換え自体が起きず、Codex レビューにも掛からなかった
- **本体は、逸脱を自覚したうえで正当化を書いていた**（時系列 3 の「依存が無いので差し支えない」）。見落としではない
- Codex が検出できたのは、**本体がログ冒頭に「一括で記録した」と自ら書いていたため**である。
  書かなければ文書レビューでは検出できない性質の逸脱である

### 1.4 影響

| 対象 | 影響 |
|---|---|
| 段2 の**出力値** | **影響なし**。`roadmap.md` §6 の段2 の想定値と `requirements.md` の受け入れ基準はすべて満たしている（判定に使ったのは、仕様・式から一意に決まる決定的な項目だけ） |
| 段3 への引き渡し | **影響なし**（3 手段は疎通し、成果物はそのまま段3・段5 で使える） |
| M2-1 の**記録としての性格** | **プロトコル（予測→実行→照合）に適合した完了記録としては扱わない**。状態は「完了（出力値は合格／予測記録の手順逸脱あり）」と併記する |
| 予測の**不改変** | **判定不能のまま残る**。予測を記録した時点で git にコミットしていないため、追記前の内容が改変されていないことを独立の証跡で示せない。この点は完了判定の根拠に含めていない |
| 再実行 | **しない**（ユーザー判断・案A）。3 手段の出力は決定的で同じ結果になり、実測を知った後の「予測」は独立性を回復しないため |

### 1.5 原因（本体の分析）

1. **直接原因**: 自分で書いた `design.md` §8 を、「手段どうしに依存が無い」という条件を持ち出して回避した。
   規定は依存の有無を条件にしていない
2. **構造的原因**: **実装と実行をまとめてサブエージェントに委任する構成にした**ため、
   「委任前に予測を書いておく」動機が生じた。委任先が実行する限り、予測は必ず実行の手前に前倒しになる
3. **発覚を遅らせた要因**: 予測に**事前の幅を持たない点予測**（`chapter`・`location`・`stage`）が混ざっており、
   実測が違っても「確率的に正常」と説明できてしまった（事後解釈の余地を自分で作った）
