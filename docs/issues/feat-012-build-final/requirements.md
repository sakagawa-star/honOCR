# feat-012 要求仕様書: final ディレクトリ構築の自動化

## 1. プロジェクト概要

### 何を作るのか

正規化済みの中間成果物（`run-NN-normalized/`）から最終成果物 `final/{name}/`
（Markdown＋content_list.json＋images/）を組み立てて検証する CLI
`scripts/build_final.py` を新設し、`scripts/ocr_dir.py` に章単位で組み込む。
あわせて図画像のカラー再切出（`scripts/colorize_images.py`）も `ocr_dir.py` から
自動実行できるようにする。

### なぜ作るのか

`ocr_dir.py` のパイプラインは「入力PDF生成 → MinerU → 正規化 → 機械確認 → HTML表変換 →
脚注挿入 → 修正適用」までで終わり、**図画像を一切扱わない**。そのため正規化済み出力には
Markdown と content_list.json しか置かれず、`![](images/…)` の参照が解決できない。

LLM に渡せる最終成果物 `final/chapNN/` を作るには、feat-005 で定義された次の手作業が
章ごとに必要である（2026-08-28 のユーザー手動テストで、この手作業の存在が改めて確認された）。

1. `colorize_images.py` を実行して `run-NN-normalized/images/` を生成する
2. md・content_list.json・images/ を `final/chapNN/` へコピーする
3. 3種類の機械検証（バイト同一・md の画像参照の解決・content_list の `img_path` 集合の一致）を行う

PRML（8章）では一度きりの作業として許容できたが、第2の書籍『プログラミングのための確率統計』は
**10章**あり、同じ手作業を10回繰り返すことになる。本案件はこの最終段を自動化する。

### 誰が使うのか

本プロジェクトのユーザー（Claude Code を介さず `ocr_dir.py` を直接実行する）。

### どこで使うのか

`docs/TECH_STACK.md` に定義された既存環境（Ubuntu 24 系 / Python 3.12.3 / uv）。
新規のライブラリ・モデル・ネットワークアクセスは追加しない。

## 2. 用語定義

本書・機能設計書・コード内で同じ用語を使う。

| 用語 | 定義 |
|---|---|
| 正規化済みディレクトリ | `{root}/mineru-full/{name}/run-NN-normalized/`。句読点正規化・HTML表変換・脚注挿入・修正適用を経た md と content_list.json が置かれる（feat-004・008・009・010） |
| final ディレクトリ | `{root}/final/{name}/`。LLM に渡す最終成果物。md・content_list.json・`images/` の3点で構成する（feat-005 FR-004 で定義） |
| カラー再切出 | `colorize_images.py` により、content_list の bbox を使って原本 TIF から図ブロックを切り出し直す処理（feat-007）。本プロジェクトの原本は書籍により RGB / グレースケールが異なるが、処理は同一である |
| 図ブロック | content_list の要素のうち `img_path` キーを持つもの（type は image / chart / table） |
| ベース名 | MinerU 出力のファイル名の語幹。`{name}_gray300`（例: `chap07_gray300`）。final でもこの名前を維持する（feat-005 ADR-6） |
| 章単位構築 | 1つの入力ディレクトリ（1章）の処理が完了するたびに、その章の final を構築する方式。本案件で採用する（2026-08-28 ユーザー決定） |

## 3. 機能要求一覧

### FR-001: final 構築 CLI の新設（`build_final.py`）

- **機能名**: 正規化済みディレクトリから final ディレクトリを組み立てる CLI
- **概要**: 正規化済みディレクトリ内の md・content_list.json・images/ を final ディレクトリへ
  コピーする
- **入力**:
  ```
  uv run python scripts/build_final.py <正規化済みディレクトリ> -o <final出力先> [--overwrite]
  ```
- **出力**: `<final出力先>/` に次の3点を作成する
  1. `{ベース名}.md`（コピー元とバイト単位で同一）
  2. `{ベース名}_content_list.json`（コピー元とバイト単位で同一）
  3. `images/`（コピー元の `images/` の全ファイル。コピー元に `images/` が無い場合は空ディレクトリ）
- **受け入れ基準**:
  1. コピー元の md と content_list.json が、final 側とバイト単位で一致する
  2. コピー元のファイルが変更・削除されない（コピーであり移動ではない）
  3. `images/` 内の各ファイルが、final 側とバイト単位で一致する
  4. `--overwrite` を指定しない実行で、出力先に同名ファイルが既に存在する場合は
     エラーメッセージを標準エラーへ出力して終了コード 1 で終了し、出力を1バイトも書かない
  5. `--overwrite` を指定した実行では、出力先の既存ファイルを上書きする
  6. 標準出力に `{ベース名}: md=1 content_list=1 images={枚数}` の形式で結果を出力し、
     最終行に `total: 1 built` を出力する
  7. コピー・ファイル列挙・孤児削除の途中で OS 由来のエラー（`OSError`）が発生した場合、
     エラーメッセージを標準エラーへ出力して終了コード 1 で終了する
     （Python のトレースバックを標準エラーへ出さない）

### FR-002: 入力検証とエラー処理（`build_final.py`）

- **機能名**: 入力の妥当性検証
- **概要**: 構築の前に入力を検証し、不備があれば何も書かずに終了する
- **入力**: FR-001 と同じ
- **出力**: 検証エラーのメッセージを標準エラーへ出力し、終了コード 1 で終了する
- **受け入れ基準**: 次の各場合にエラーとなり、出力先に1バイトも書かれない
  1. 正規化済みディレクトリが存在しない、またはディレクトリでない
  2. 正規化済みディレクトリに `*_content_list.json` がちょうど1個存在しない（0個または2個以上）
  3. 2 で特定したベース名に対応する `{ベース名}.md` が存在しない
  4. md または content_list.json のサイズが 0 バイトである
  5. content_list.json が UTF-8 の JSON 配列として読めない
  6. **出力先が入力ディレクトリと重なる**（実体パスで比較して、出力先と正規化済みディレクトリが
     同一である、出力先が正規化済みディレクトリの配下にある、または正規化済みディレクトリが
     出力先の配下にある）。`--overwrite` の有無によらずエラーとする
     （非機能要求「コピー元を変更・削除しない」を破る入力であるため）
  7. 正規化済みディレクトリの `images` が存在するがディレクトリでない
  8. 出力先の `images` が存在するがディレクトリでない
  9. **出力先ディレクトリ自体がシンボリックリンクである**
  10. **出力先の `images` がシンボリックリンクである**
      （9・10 とも、リンク先の final 外のファイルをコピー・孤児削除が
      書き換える経路を塞ぐため。非機能要求「シンボリックリンク・ハードリンクを使わない」と整合させる）

### FR-003: 構築後の機械検証（`build_final.py`）

- **機能名**: final ディレクトリの完全性検証
- **概要**: コピー後に3種類の検証を行い、1つでも不合格なら失敗として報告する
  （feat-005 design.md §4.4 手順3 の 2・3・4 をコード化したもの）
- **入力**: FR-001 と同じ
- **出力**: 不合格の場合、内容を示すメッセージを標準エラーへ出力し、終了コード 1 で終了する
- **受け入れ基準**:
  1. **バイト同一**: md・content_list.json のコピー元と final 側がバイト単位で一致すること。
     一致しなければ不合格
  2. **md の画像参照の解決**: final 側 md から `images/` で始まる参照を抽出し、
     参照されるファイルがすべて `final/images/` 内に存在すること。存在しないものが
     1件でもあれば不合格（参照が 0 件の場合は合格）
  3. **`img_path` 集合の一致**: final 側 content_list の全図ブロックの `img_path` の
     basename のユニーク集合が、`final/images/` 直下のファイル名の集合と**完全に一致**すること。
     過不足があれば不合格（図ブロックが 0 件かつ `images/` が空の場合は合格）
  4. 検証が不合格の場合でも、既に書き出したファイルは削除しない（調査のため残す）。
     ただし終了コードは 1 とし、標準出力に成功サマリを出力しない

### FR-004: 図が 0 件の章の扱い

- **機能名**: 図を含まない章の正常処理
- **概要**: 図ブロックが 1 件も無い章（PRML chap07 の実績あり）を正常系として扱う
- **入力**: 図ブロック 0 件の content_list を含む正規化済みディレクトリ
- **出力**: `final/images/` を空ディレクトリとして作成し、終了コード 0 で終了する
- **受け入れ基準**:
  1. 空の `images/` ディレクトリが作成される
  2. FR-003 の検証3（`img_path` 集合の一致）が「空集合 = 空集合」で合格する
  3. 標準出力の枚数表示が `images=0` となる

### FR-005: `ocr_dir.py` への組み込み（章単位構築）

- **機能名**: 一括実行スクリプトへの最終段の追加
- **概要**: `ocr_dir.py` に `--final` オプションを追加し、1章の処理が完了するたびに
  「カラー再切出 → final 構築」を実行する
- **入力**: `--final`（フラグ。省略時はこれらの処理を行わない）
- **出力**: 章ごとに `{root}/final/{name}/` を構築する。PASS サマリ行に `images={枚数}` を追加する
- **受け入れ基準**:
  1. `--final` を省略した実行の動作が、本案件の変更前と同一である（既定では final を作らない）
  2. `--final` を指定した実行では、修正適用（`--fixes-dir` 指定時）の**後**に、
     `colorize_images.py`（出力先 = 正規化済みディレクトリ内の `images/`）、
     続いて `build_final.py`（出力先 = `{root}/final/{name}/`）が実行される
  3. カラー再切出または final 構築が失敗した章は FAIL となり、理由が報告される
  4. **ある章が FAIL しても、それ以前に PASS した章の final は削除されず残る**（章単位構築）
  5. 複数ディレクトリを指定した実行で、各章の final が独立して構築される
  6. `--final` 指定時の `colorize_images.py` と `build_final.py` の呼び出しには
     `--overwrite` を付ける（再実行時に既存の出力を上書きする）
  7. カラー再切出の縮小率は `colorize_images.py` の既定値（1/3）を用いる
     （`ocr_dir.py` に縮小率のオプションを追加しない）

### FR-006: 冪等性

- **機能名**: 再実行時の同一結果
- **概要**: 同じ入力に対して 2 回実行しても、結果が同じになる
- **入力**: 一度 final を構築した状態で、同じコマンドを再実行する
- **出力**: 同一内容の final ディレクトリ
- **受け入れ基準**:
  1. `build_final.py --overwrite` を同じ入力で 2 回実行したとき、
     2 回目の実行後の final の全ファイルが 1 回目の実行後とバイト単位で一致する
  2. 2 回目の実行も終了コード 0 で終了する
  3. コピー元に存在しないファイルが final 側に残っていた場合（前回の構築時にあり、
     今回は無いファイル）、`images/` 内の**孤児ファイルは削除する**
     （FR-003 の検証3「集合の完全一致」を満たすため）

### FR-007: 既存データ（PRML final）との整合

- **機能名**: 既存成果物と同一構造の出力
- **概要**: 本 CLI が構築する final が、feat-005 で手作業により構築された PRML の final と
  同じ構造・同じ内容になることを確認する
- **入力**: PRML の `{BASE}/ocr/mineru-full/chapNN/run-01-normalized/`
  （`{BASE}` = `/home/sakagawa/work/Pattern_Recognition_and_Machine_Learning`）
- **出力**: 検証結果の報告（実装時に一時ディレクトリへ出力して実施し、報告する）
- **受け入れ基準**:
  1. chap00〜07 の 8 章について `build_final.py` を一時ディレクトリへ実行し、
     終了コード 0 で完了する
  2. 生成された final の md・content_list.json が、既存 `{BASE}/ocr/final/chapNN/` の
     同名ファイルとバイト単位で一致する
  3. 生成された `images/` のファイル名集合が、既存 final の `images/` と一致する
  4. **既存の `{BASE}/ocr/final/` を変更しない**（検証は一時ディレクトリへの出力で行う）

### FR-008: 自動テスト

- **機能名**: 変更点の自動テスト
- **概要**: 新規 CLI と `ocr_dir.py` の変更について自動テストを追加し、既存テストを維持する
- **入力**: `uv run pytest -v`
- **出力**: `tests/results/feat-012_test_result.txt`（コマンド出力をそのまま保存）
- **受け入れ基準**:
  1. 既存テスト 170 件がすべて PASS する
  2. FR-001〜FR-006 の各受け入れ基準に対応するテストが追加され、すべて PASS する
  3. 実データ（PRML final・確率統計の出力）に依存するテストを含めない
     （テストはリポジトリ内で自己完結する）

## 4. 非機能要求

- **パフォーマンス**: 1章あたりの final 構築（カラー再切出を除く）は、PRML chap01
  （md 約 207KB・images 55 枚）で 10 秒以内に完了すること。
  カラー再切出は原本 TIF の読み込みが支配的であり、本案件では性能要件を設けない
- **対応環境**: Ubuntu 24 系 / Python 3.12.3 / uv。GPU は使用しない
- **信頼性**:
  - コピー元（正規化済みディレクトリ）を変更・削除しない
  - final への集約はコピーで行い、シンボリックリンク・ハードリンク・移動を使わない
    （feat-005 ADR-5 を踏襲）
  - 検証不合格時に終了コード 1 を返し、`ocr_dir.py` 側で FAIL として扱う
- **後方互換性**: `ocr_dir.py` は `--final` を省略した場合、本案件の変更前と同一に動作する

## 5. 制約条件

- 使用必須: Python 標準ライブラリ（`argparse` / `shutil` / `json` / `re` / `pathlib`）と、
  既存の `colorize_images.py`（Pillow 依存）。新規のサードパーティライブラリは追加しない
- ネットワーク: 本案件の変更部分はネットワークアクセスを行わない
- 出力互換: `ocr_dir.py` の PASS/FAIL サマリ行の既存項目（`pages=` `blocks=` `replaced=`
  `tables=` `footnotes=` `fixes=`）の書式は変更しない。`images=` を末尾に追加する
- final のファイル名: MinerU 出力のベース名（`{name}_gray300.*`）を維持する（feat-005 ADR-6）
- final の構成: md・content_list.json・images/ の3点に限定する。
  `middle.json`・`layout.pdf` 等はコピーしない（feat-005 ADR-7）
