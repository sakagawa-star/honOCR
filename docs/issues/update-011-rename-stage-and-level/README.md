## 1. 経緯・目的

### 1.1 契機

update-008〜010 で導入したロードマップ規定は、パイプラインの処理単位を「段」、再検討の水準を「手 1・手 2」と呼んでいた。ユーザーは 2026-09-08 に「名称がかっこ悪すぎる」として、実際のプログラム開発で使われる名称への改名を決めた。

Claude Code が提示した実務での対応語（ステージ／バリア／インターフェース・契約・スキーマ／リネージ／期待値／実装の変更・破壊的変更／エスカレーション／サーキットブレーカー／フリーズ／キャリブレーション）のうち、ユーザーが採ったのは「段 → ステージ」と「手 → 式の変更／次元の変更」の 2 つ。**「次元」はそのまま**（「数式の次元、そのまま。インターフェイスではない」）。

### 1.2 目的

用語を改名し、規定の内容は一切変えない。改名後に `CLAUDE.md` 内で用語が衝突しないこと（git の「ステージ対象」と、パイプラインの「ステージ」）を担保する。

### 1.3 採らなかった案と不採用の理由

| 案 | 不採用の理由 |
|---|---|
| 手 1・手 2 を「実装の変更／インターフェース変更（破壊的変更）」と呼ぶ | 次元は数式の次元（式が扱う量の成分の数）そのものであり、インターフェースやスキーマ（形・型）ではない（ユーザー 2026-09-08）。「次元の変更」と呼ぶ |
| 決める項 → リネージ、想定値 → 期待値、行き詰まり検出 → サーキットブレーカー等、他の用語も同時に改名する | ユーザーの決定は「手と段」のみ。範囲を広げない |
| 過去の案件文書（feat-024・update-008〜010）の用語も改名する | 記録の改変になる。対応表を残して読み替える |
| 置換規則（段 → ステージ等）を Sonnet に再適用させる | 保護語（手段・段階等）の判断と適用順で結果が変わりうる。全量を行単位の `old`/`new` で固定し、模擬置換とのバイト一致で検証する |
| 測る段 → 「測定ステージ」 | 新しい語を増やさない。機械適用の結果「測るステージ」をそのまま採る |
