# feat-016 要求仕様書: chap07 の中国語語彙誤認識「上的」の修正

## 1. プロジェクト概要

### 何を作るのか

『プログラミングのための確率統計』chap07 の修正定義ファイル
`{BASE2}/ocr/fixes/chap07.json`（新規・リポジトリ外）を作成し、
`apply_fixes.py`（feat-010）で既存成果物に適用したうえで、
`build_final.py`（feat-012）で `final/chap07/` を再構築する。

**リポジトリ内のコード（`scripts/`）とテストコード（`tests/test_*.py`）は一切変更しない。**
本案件で作成・更新する成果物は次の3つに限られる。

1. リポジトリ外の修正定義ファイル1件（`{BASE2}/ocr/fixes/chap07.json`）
2. それを適用したリポジトリ外の既存成果物（`{NORM}/` と `{BASE2}/ocr/final/chap07/`）
3. リポジトリ内の案件ドキュメント（`docs/issues/feat-016-chap07-chinese-vocab/`）、
   `docs/BACKLOG.md` / `docs/CHANGELOG.md` / `CLAUDE.md` の完了処理、および
   テスト結果の記録 `tests/results/feat-016_test_result.txt`（新規作成。
   CLAUDE.md「テスト」のルールで必須）

### なぜ作るのか

chap07 の本文1箇所で、原本の「[0,1) **上の**一様分布」が
「[0,1) **上的**一様分布」と OCR されている（案件 README.md §2・§3 で原本確認済み）。
「上的」は中国語表現であり、日本語の数学書の本文として誤りである。
LLM に読ませる主成果物である Markdown の品質を下げるため、修正する。

feat-013 の完了時に、確率統計の手動テストで見つかった問題を3案件に分ける方針が
決まっており（2026-08-31 引き継ぎノート）、本案件はそのうちの1件である。

### 誰が使うのか

本プロジェクトのユーザー。成果物（`{BASE2}/ocr/final/chap07/chap07_gray300.md`）を
LLM に読ませて学習に用いる。

### どこで使うのか

`docs/TECH_STACK.md` に定義された既存環境（Ubuntu 24 系 / Python 3.12.3 / uv）。
新規のライブラリ・モデル・ネットワークアクセスは追加しない。

## 2. 用語定義

feat-010 および feat-013 の要求仕様書の用語を継承する。本書で用いる主な用語は次のとおり。

| 用語 | 定義 |
|---|---|
| 修正定義ファイル | OCR 誤りを「修正前文字列（`old`）→ 修正後文字列（`new`）」のペアで記録した JSON。`{BASE2}/ocr/fixes/{name}.json` に置く。書籍本文を含むためリポジトリに置かない（feat-010） |
| 個別誤認識 | 字形の 1 対 1 対応が成立しない OCR 誤り。字形正規化テーブルでは扱わず修正定義ファイルで補正する（feat-011 ADR-3） |
| 語彙単位の誤り | 1文字の字形置換では表現できず、複数文字の並びとしてのみ判定できる誤り。本件の「上的 → 上の」がこれにあたる |
| 再適用 | 既に構築済みの成果物（`run-NN-normalized/` と `final/`）に対し、MinerU を再実行せずに修正適用・final 再構築のみを行うこと（feat-013 §2） |
| `{BASE2}` | `/home/sakagawa/work/確率統計`（git 管理外・リポジトリ外） |
| `{NORM}` | `{BASE2}/ocr/mineru-full/chap07/run-02-normalized`（chap07 の正規化済みディレクトリ） |

## 3. 機能要求一覧

### FR-001: chap07 の修正定義ファイルの新規作成

- **機能名**: `{BASE2}/ocr/fixes/chap07.json` の作成
- **概要**: 「上的 → 上の」の修正1件を、`fixes/template.json` の書式に従って定義する
- **入力**: 案件 README.md §2・§3 で確定した誤り箇所（1件）
- **出力**: `{BASE2}/ocr/fixes/chap07.json`（新規ファイル。UTF-8・JSON）
- **受け入れ基準**:
  1. `fixes/README.md`・`fixes/template.json` の書式に従い、`id` / `reason` / `old` / `new` の
     4キーをすべて文字列で持つ fix が**ちょうど1件**含まれる
  2. `apply_fixes.py` の `validate_fixes` がエラーを1件も出さない
  3. 適用**前**の `{NORM}/chap07_gray300.md` において `count(old) == 1` である
  4. 適用**後**の `{NORM}/chap07_gray300.md` において `count(new) == 1` である
     （`apply_fixes.py` の最終不変条件。CLAUDE.md の運用ルール）
  5. `reason` に、原本 TIF で確認済みであることと、`old` / `new` を一意にするために
     文脈を含めた理由を日本語で記述する
  6. ファイルはリポジトリに置かず、コミットもしない（feat-010 の運用）

### FR-002: 既存成果物への修正の適用と final の再構築

- **機能名**: chap07 の再適用
- **概要**: MinerU と `normalize_punct.py` を再実行せず、`apply_fixes.py` と
  `build_final.py` のみを実行して chap07 の成果物を更新する
- **入力**:
  - `{NORM}/chap07_gray300.md`（正規化済み・feat-013 適用後の状態）
  - `{BASE2}/ocr/fixes/chap07.json`（FR-001 の成果物）
- **出力**:
  - `{NORM}/chap07_gray300.md`（インプレース更新）
  - `{BASE2}/ocr/final/chap07/`（再構築）
- **受け入れ基準**:
  1. `apply_fixes.py` の終了コードが 0 で、`applied = 1` である
  2. `build_final.py` の終了コードが 0 である（3種類の機械検証がすべて合格）
  3. 適用後の `{NORM}/chap07_gray300.md` に「上的」が **0 件**である
     （件数はすべて Python の `str.count()` による**出現回数**で数える。
     `apply_fixes.py` の不変条件と同じ数え方であり、行数ではない）
  4. 適用後の `{NORM}/chap07_gray300.md` に「上の一様分布」が **17 回**出現する
     （適用前16回 ＋ 本修正1回。2026-08-31 実測に基づく）
  5. 適用前後で `{NORM}/chap07_gray300.md` の文字数が変わらない
     （「的」→「の」の 1 文字 → 1 文字の置換であるため）
  6. 適用前後で、本修正箇所以外の差分が**ない**（差分は1行のみ）
  7. `final/chap07/` の md・content_list.json が `{NORM}/` とバイト同一である
  8. `final/chap07/images/` のファイル数が 16 のまま変わらない
  9. `{NORM}/chap07_gray300_content_list.json` は**変更されない**
     （`apply_fixes.py` は md のみを対象とする既存ポリシー。feat-010／feat-013 §6.1）

### FR-003: 影響範囲の限定

- **機能名**: 本案件で変更しない対象の明示
- **概要**: 修正の影響を chap07 の md 1箇所に限定する
- **受け入れ基準**:
  1. `scripts/` 配下のコードを1行も変更しない
  2. `tests/test_*.py`（テストコード）を1行も変更しない。
     `tests/results/feat-016_test_result.txt` の新規作成は**この制限の対象外**であり、
     CLAUDE.md「テスト」のルールに従って必ず作成する
  3. 確率統計の chap07 以外の9章の成果物・修正定義ファイルを変更しない
  4. PRML（`{BASE}`）の成果物を変更しない
  5. 既存の自動テストを全件実行し、feat-013 完了時点と同じくすべて成功する

## 4. 非機能要求

| 項目 | 要求 |
|---|---|
| 性能 | 再適用は chap07 1章のみ・MinerU 再実行なしのため、全工程が 10 秒以内に完了する |
| 再現性 | `apply_fixes.py` は冪等である（2回目以降の実行では `old` 不在・`new` 1件のため `skipped` として扱われ、終了コード 0・内容不変） |
| 可搬性 | 修正定義ファイルは書籍本文を含むためリポジトリ外に置く。リポジトリ側には書式テンプレート（`fixes/template.json`）のみを保持する（feat-010 の既存方針） |
| 保守性 | 修正の根拠（原本確認の事実と一意性確保の理由）を `reason` に残し、再 OCR 時に文面が変われば `apply_fixes.py` がエラーで検出できる状態を保つ |

## 5. 制約条件

- **MinerU を再実行しない**。OCR 結果は同一入力に対して変わらず、35 分の実行コストに見合わない（feat-013 ADR-3 と同じ判断）
- **`normalize_punct.py` を再実行しない**。feat-013 で適用済みであり、本案件は字形正規化テーブルを変更しないため結果は変わらない
- **`final/` を直接編集しない**。final は `run-NN-normalized/` からのコピーであり、コピー元を更新しないと次回の final 再構築で変更が失われる（feat-013 の既存方針）
- **`content_list.json` を修正しない**。MinerU のスキーマを維持する既存ポリシー（feat-010）。結果として md と json の当該箇所の表記が一致しなくなるが、これは feat-013 §6.1 で許容済みの既知事項である
- 修正定義ファイルの実体は**コミット禁止**（書籍本文を含むため）
- 本案件は**コード変更を含まない**。作業中にコード変更が必要と判明した場合は中断して報告する

## 7. スコープ外

次の項目は本案件では扱わない。

- 語彙単位の誤りを自動検出する仕組みの追加（本件は手動テストで発見した1件のみを対象とする）
- `normalize_punct.py` の置換表への「上的 → 上の」の追加（機能設計書 ADR-1 で不採用とする理由を記す）
- feat-014（Q&A コラム見出しの「？」アイコン分離）および feat-015（chap02 の見出し分断）の修正
- PRML 成果物への字形正規化の再適用（引き継ぎノートの別項目）
