## 1. 経緯・目的

### 1.1 契機

Codex は、文書に式が書いてあれば式の整合を追える（update-009 codex-06「次元を固定しても出力値が変われば後段の予測値は変わる」、feat-025 codex-01〜05 の統計設計の是正 10 件）。一方で、**式の連鎖が最終出力の要求まで届いているか**は見ていない。

| 事例 | Codex の結果 | 見落とし |
|---|---|---|
| feat-024 `roadmap.md` 第4版（2026-09-08） | 全文ゲート codex-62 が高・中・低ゼロ | 段4 の項目 (b)（`k_i` の二項分布の予測区間）は、推測 `p̂_pred` を停止条件に置いた旧項目 4 と同種の誤り。想定値が式から導出されているかを検査していない（feat-024 `rule_feedback_notes.md` F16） |
| feat-025 `roadmap.md` 第1版（2026-09-09） | A〜C の 5 回で収束（高・中ゼロ） | (1) 許容誤差 `e = 0.10` が `n` の算出にだけ使われ、最終出力の区間（有限母集団修正なし・`u` の分だけ広がる）への要求として翻訳されていない。(2) `k = round(n × q) × p₀` が S3 と S4 で同じ判定関数を前提にしているのに、前提として書かれていない（2026-09-09 の Claude Code〔Fable〕による人レビュー前の確認） |

原因は Codex の理解ではなく、**依頼文と基準書に「導出されているか」を検査する指示が無い**こと。現行の依頼文は「docs/REVIEW_CRITERIA.md の基準に従い、以下のドキュメントをレビューせよ: {roadmap.md}」だけで、`docs/REVIEW_CRITERIA.md` には次元・式の観点が無い（1.1〜1.9 は文書間の一貫性・曖昧性・I/O 定義・技術スタック等）。update-009 で予想欄の書式を固定し「式の無い行は不適合」としたが、これは形式の検査であり、式の形をした推測や、要求が翻訳されていない連鎖の切れ目は形式検査をすり抜ける（update-009 README §5 判断 B の「足りる」は、feat-025 の実例で足りないことが分かった）。

### 1.2 目的

Codex のロードマップレビューに、式の入力と出力を実際に追う検査項目を与える。担保するもの:

1. 想定値の式の入力がすべて「前のステージの実測」「測るステージの測る項」「固定した定数」に由来すること（式の形をした推測を排除する）
2. 最終出力への要求が、最終ステージから前のステージへ式で翻訳され、停止条件または想定値に現れていること（連鎖の切れ目を検出する）
3. 次元の接続・決める項の被覆・測るステージの対応・幅の計算の根拠

判定条件は update-008〜010 と同じ: Codex に「これは要るか」の判断を求めず、式の入力の由来と接続を機械的に辿らせる。

### 1.3 採らなかった案と不採用の理由

| 案 | 不採用の理由 |
|---|---|
| 検査項目を `AGENTS.md` に書く | `AGENTS.md` は定型指示（マーカー・重要度分類・規定適合確認）の置き場で、案件種別固有の観点は依頼文と基準書に置く規定（CLAUDE.md「依頼文の基準部分」）。`docs/` 直下の基準書は AGENTS.md の指示で Codex が読む |
| 次元と式の定義を基準書に再掲する | 定義は CLAUDE.md「パイプラインの切り方」にあり、Codex はフロー節を読む。再掲は二重管理になる（粒度の原則） |
| 次元の接続を機械検査するスクリプトを作る | コード変更になり update 案件の範囲外。まず Codex の検査で効くかを feat-025 で見る |
| 検査項目を依頼文だけに書く（基準書に置かない） | 依頼文が長くなり、ステップ3・5・実験ログの書き換えの 3 か所に同じ内容を書くことになる。基準書に 1 か所置いて依頼文から参照する |
