### 1.2 壁打ち（2026-09-08。ユーザーと Claude Code〔Fable 5.1〕）で確定した枠

ユーザーの説明を、確定した順に記す（引用はユーザーの発言）。

1. **次元と式は全ての入出力に使う考え方**。「全部の入力と出力でチェックすると大変だから、パイプラインの入力と出力でチェックする」。段の境界は検査点であって、式の適用範囲ではない
2. **予想値は次元と式を考慮したものになる**。「出力に幅がある場合は、その幅を明記すべきだが、その幅の根拠は明記すべき」。根拠の「種別」（実測／導出／推測）というラベルではなく、幅を出した計算そのものを書く
3. **予想と異なる結果が出たら計画の再検討を行う**。対象は「パイプラインを構成する次元・式、もしくはロードマップ全体」。**再計画のトリガーに人の許可は要らない**（「事前のロードマップ、計画で人のレビューが通っているので必要ない〔はず、運用してみて変えるかも〕」）。**再計画したものは人レビュー必須**（「全自動が望ましいが、現状のAIの品質を考えると」）
4. **外れの「意味」は式で出す**。層G の 48/48 について「現状、式や次元の根拠が無いので層Gの結果が何を意味するのかが分からないし、理解しようとも思っていない。まず次元・式の考え方でそれが何を意味するかをまず出させないと判断できない」。意味には**「その項が最終出力の各成分にどう効くか」を含む**（「最終目標を達成することが目的だから。パイプラインやマイルストーンを置いて途中経過でチェックしているのは、大きい実装を避けたいから。小さく作りたいから。小さく作ってそれを組み合わせて最終結果を出すには、信用できる根拠が必要、それが入出力の次元と式になる」）
5. **根拠が無くて幅が書けない出力は、事前に測定できるプロセスを挟む**（「未知のものを作る場合はある程度事前想定が出来るものを積み上げていかないと解が収束しない。なので、根拠がないなら事前に測定できるようなプロセスを挟むべき。それがマイルストーンという考え方でもいいし、パイプラインという考え方でもいい」）
6. **行き詰まり検出の「外れ 2 回」は必要**。理由は「**AIは事前の予想（推論）に執着があるので、それを断ち切るトリガーが欲しいから**」。この理由を規定に書く。回数と再検討の水準は対応づけない（Claude Code が提案した「1 回目＝段の式、2 回目＝ロードマップ全体」は退けられた）
7. **外れた後の思考手順は 2 段**（「足りる」との回答の中で提示）: (1) 入出力の次元を固定して式を変える。(2) 式を変えてもダメなら次元も変える。「その場合は次元を変えたのが入力なら前段にも影響が出る、出力なら後段にも影響が出る、なので再度想定や実装をやり直す（計画の見直し）」。これが梯子の手 1〜4 の置き換えになる。再計画の範囲がエージェントの判断ではなく、次元のどちら側を変えたかで決まる
8. **criteria lock が固定するのは式と幅の計算方法**であって値ではない。「前段の出力が入力になるので、もし確定してから決めればよいです」
9. **式の精度は未検証**（「今のところ曖昧なのは式の精度なのだが、これは実際に運用してみないと分からんのが正直なところ」）。規定には未検証と書き、運用で発火の頻度と幅の広さを記録して見直す

### 1.3 目的

feat 案件のロードマップにおいて、次を担保する。

1. **予想は式から出る。** 各段の予想値は、その段の出力の式に前段の実測と定数を代入して出す。幅があれば幅と、幅を出した計算を書く。式で出せない量は、それを測る段を前に置く。式の無い予想行は人レビュー・Codex レビューで不適合とする（書式を固定して検出可能にする）
2. **外れの意味は式で示し、判断は人がする。** 外れたらエージェントは解釈・判定・分類・自作の選択肢を書かず、予想を生んだ式・実測が式のどの項を決めたか・その項が最終出力の各成分にどう伝播するかを式の連鎖で示し、改訂したロードマップを人レビューに出す
3. **再検討の手順を 2 段に固定し、範囲を次元で決める。** 次元を固定して式を変える → それでも外れたら次元を変え、入力側なら前段・出力側なら後段に波及させて予想と実装をやり直す。梯子の手 1〜4 と「手を飛ばす・戻すにはユーザー指示」は廃止する
4. **推論への執着を外部から断つ。** 行き詰まり検出の「外れ 2 回」を残し、理由を規定に書く

判定条件は update-008 と同じく「記入欄と手順だけで構成され、エージェントに『これは要るか』『同じ原因か』『問題ないか』の判断を要求しないこと」。本案件で加わる観点は、**発火後にエージェントが書けることを列挙で制限すること**（Opus 自身の整理「手順があることで、結局は私の判断でしかないものが検証済みの体裁をまとって出てくる。手順が無いより悪い」〔F11〜F14 の共通点〕）。

### 1.4 採らなかった案と不採用の理由

いずれも 2026-09-08 の壁打ちで Claude Code（Fable）が提案し、ユーザーが退けたか、ユーザーの枠に無いと判明して Claude Code が取り下げたもの。

| 案 | 不採用の理由 |
|---|---|
| 予想を「停止条件（式から導出できる要求。外れたら再検討）」と「結果の予想（参考。外れても記録のみ）」に二分する（F5 の型1／型2、F16 の「停止条件に限る」） | ユーザーの枠では予想は全部が次元・式から出るもので、外れたら全部が再検討の対象。「参考欄」は外れを再検討から逃がす出口になる。Opus の型1／型2 と同じく、エージェントが発火を減らすために作った区分 |
| 想定値の「根拠の種別」（実測／式から導出／推測）を残し、「推測」の項目だけ停止条件から外す | 求められているのは種別のラベルではなく幅の根拠そのもの。予備目視 30 件から出すなら 30 件からの計算を書く。「推測」というカテゴリ自体が根拠の無い幅を許す穴 |
| 外れの回数を再検討の水準に対応づける（1 回目＝段の式、2 回目＝ロードマップ全体） | 「外れ 2 回」の役割は水準の選択ではなく、エージェントの推論への執着を断つトリガー。水準はエージェントが式の連鎖を辿った結果で決める |
| 行き詰まり検出の「外れ 2 回」を廃止する（1 回で再計画に入るので不要） | ユーザー「必要」。上記の理由 |
| 層G の 48/48 の意味を Claude Code が説明する（「30 件が層G を代表する前提が壊れた」） | 式の無いところに付けた解釈。ユーザーが拒否したもの（§1.2 項目 4） |
| 独立項目（F1・F3・F6〜F9・F15・F18）を本案件に含める | ユーザー決定で改訂を 2 段に分ける。本案件は壁打ちの枠のみ。独立項目は本案件の完了後に見直して要否を判断する |
| feat-024 を現行規定のまま最後まで走らせる | ユーザー当初の希望だったが、ルール改訂を優先して一時中断（On Hold）。第 2 段の後に feat-025 で目的だけをコピーして新規定で実施する |

### 1.5 人（ユーザー）レビューで方針が変わった記録

壁打ちの過程で、Claude Code（Fable）は 3 回同じ癖（式の無いところに構造・解釈を足す）を出し、いずれもユーザーの説明で取り下げた。

- 予想の二分法（停止条件／結果の予想）→ 「予想は全部が式から出る。外れは全部が再検討」
- 回数と水準の対応づけ → 「2 回ルールは推論への執着を断つトリガー」
- 層G の外れへの解釈 → 「式が無い限り意味は分からない。まず式で意味を出させる」

これらは本案件が防ごうとしている振る舞い（F11〜F14）そのものであり、規定の改訂だけでなく Claude Code 側のメモリにも残した（リポジトリ外）。
