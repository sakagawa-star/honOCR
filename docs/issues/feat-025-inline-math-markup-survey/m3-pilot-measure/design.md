## 1.4 各機能の詳細設計

### 1.4.1 予備標本 30 件の無作為抽出（FR-301）

#### データフロー

- 入力: `{BASE2}/ocr/feat-025/m2_all_candidates.jsonl`（414 行）
- 出力: 抽出した 30 個の物理行番号（昇順）と、`{BASE2}/ocr/feat-025/m3_sample_candidates.jsonl`（30 行）

#### 定数

| 記号 | 値 | 位置づけ |
|---|---|---|
| `SAMPLE_SIZE` | **30** | 予備標本の件数（`roadmap.md` §7 のステージ表の単位数） |
| `SEED` | **20260917** | 乱数の種。**本設計で固定する**（ADR-20）。本マイルストーンの着手日（2026-09-17）を数値にしたもので、実行結果を見てから選ぶ余地が無い |
| `POPULATION` | **414** | 候補の件数（`roadmap.md` §3 の P14。S2 の実測と一致する） |

#### 処理ロジック

次を **1 回だけ**実行し、標準出力に出た行番号を使う。

```
uv run python -c "import random; print(sorted(random.Random(20260917).sample(range(1, 415), 30)))"
```

- `random.Random(SEED).sample(range(1, POPULATION + 1), SAMPLE_SIZE)` は**復元なしの単純無作為抽出**であり、同じ種から常に同じ 30 個を返す（重複しない）
- 得た 30 個を**昇順**に並べたものを、以降「標本の行番号」と呼ぶ
- 実行の前に、`wc -l` で入力が 414 行であることを確認する。414 行でない場合は**中断して報告する**（`POPULATION` と食い違うため）

#### 予備標本ファイルの作成

標本の行番号を `sed` の行指定に変換して抽出する（`{n1}` 〜 `{n30}` は昇順の行番号）。

```
sed -n '{n1}p;{n2}p;…;{n30}p' {BASE2}/ocr/feat-025/m2_all_candidates.jsonl \
  > {BASE2}/ocr/feat-025/m3_sample_candidates.jsonl
```

`sed -n` は**元ファイルの並び順**で出力するため、予備標本ファイルの 1 行目が標本の行番号のうち最小のもの、30 行目が最大のものになる。作成後に `wc -l` で 30 行であることを確認する。

#### 行番号の対応

予備標本ファイル内の行番号（1〜30）と、元ファイルの物理行番号との対応表を `experiment_log.md` に記録する（FR-301 の受け入れ基準）。以降の `--select` は**予備標本ファイル内の行番号**（1〜30）を指す。

#### 境界条件

| 事象 | 振る舞い |
|---|---|
| 入力が 414 行でない | 中断して報告する（上記） |
| 標本に M2-1 で判定した候補（元ファイルの 1 行目）が含まれる | **そのまま標本に残し、M2-1 の判定を流用せず §1.4.4 の規則で判定し直す**（`requirements.md` FR-301・§1.7） |

### 1.4.2 予備標本の逆引き（FR-302）

#### データフロー

- 入力: `m3_sample_candidates.jsonl`（30 行）と、各章の content_list
- 出力: `m3_located.jsonl`（30 行。`judgment` は `null`）と、標準出力への内訳 30 行

#### 処理ロジック

`scripts/locate_candidates.py` の**全件処理の経路**（`--select` を付けない）を 1 回実行する。`../m2-1-locate-smoke/design.md` §1.4.5 の全件処理の 6 手順により、入力順が保たれ、章ごとに content_list が 1 回だけ読まれ、逆引きに失敗した候補も `page_idx` = `null` のレコードとして出力に含まれる。

標準出力の内訳（`{行番号} {chapter} offset={offset} block={block_idx} page={page_idx} k={k}`）を全 30 行とも控える。ブロック番号は §1.4.3 の切り出しに使う。

#### 境界条件

| 事象 | 振る舞い |
|---|---|
| 逆引きに失敗した候補がある | エラーにしない（終了コード 0）。その候補は §1.4.4 の判定手順で `undecidable` になる |
| 30 件すべてが逆引きに失敗した | 切り出しを 1 件も行わず、全件が `undecidable` になる。`q` = 0 となり §1.4.6 の停止条件に入る |

### 1.4.3 原本 TIF からの切り出し（FR-303）

#### データフロー

- 入力: §1.4.2 のブロック番号と、章ごとの content_list・原本 TIF ディレクトリ
- 出力: `{BASE2}/ocr/feat-025/m3-crops/` 配下の PNG

#### 処理ロジック

**章ごとに 1 回**実行する（`crop_blocks.py` は content_list と TIF ディレクトリを 1 組しか受け取らないため）。逆引きに成功した候補を `chapter` でまとめ、その章のブロック番号を `--index` に並べる。

```
uv run python scripts/crop_blocks.py \
  {BASE2}/ocr/final/{chapter}/{content_list のファイル名} \
  {BASE2}/dewarping/{chapter}/out \
  -o {BASE2}/ocr/feat-025/m3-crops \
  --index {block1} --index {block2} …
```

- content_list のファイル名は `{BASE2}/ocr/final/{chapter}/*_content_list.json` の glob で解決する（`../m2-1-locate-smoke/design.md` §1.4.1 と同じ規約。ちょうど 1 個であることを確認する）
- **逆引きに失敗した候補（`block` が `None`）は `--index` に含めない**
- **同じ章の同じブロックが 2 件以上の候補で重なる場合、`--index` にはその番号を 1 回だけ書く**（`crop_blocks.py` は `--index` の重複をエラーにする）。PNG は 1 枚を 2 件の候補で共用する
- `--margin` は既定値（8.0）を使う。読めない場合の扱いは §1.4.4 の判定手順 2 に定める
- 出力ファイル名は `crop_blocks.py` の規約により `{content_list の stem}_b{ブロック番号}_p{page_idx}.png`。**同一章・同一ブロックの候補が複数あるとき、この名前は候補を一意に識別しない**ため、「候補の元ファイル行番号 → PNG のパス」の対応表を `experiment_log.md` に記録する（`requirements.md` FR-303）

#### 境界条件

| 事象 | 振る舞い |
|---|---|
| 逆引きに成功した候補が 0 件 | 切り出しを 1 回も実行しない |
| ある章の候補が 0 件 | その章については実行しない |

### 1.4.4 判定規則（FR-304。`roadmap.md` P9-1 の「判定規則の本体」）

**本節が判定規則の本体である。M4（S4）はこの規則をそのまま適用し、変更しない**（`requirements.md` C-308）。判定者は Claude Code 本体である。

#### 判定の対象

候補レコードの `char`（1 文字）が、**原本の該当箇所でどう組まれているか**。文脈（`before` / `after`）は、PNG のどこが該当箇所かを特定するために使う。

#### 判定に使う基準量（すべて PNG 上の見た目で比べる）

判定の条件は、次の 3 つの基準量との比だけで書く。**画素単位の計測は求めず、PNG を見て比べる**。

まず、比較の基準にする和文 1 文字（**基準文字**）を次の規則で**一意に**選ぶ。

1. 候補の字形と**同じ行**にある**漢字**のうち、候補に最も近いもの（左右の距離が同じなら**左**）
2. 同じ行に漢字が無ければ、同じ行の**カタカナ**のうち、候補に最も近いもの（同じく同距離なら左）
3. カタカナも無ければ、同じ行の**ひらがな**のうち、候補に最も近いもの（同じく同距離なら左）
4. 同じ行に漢字・カタカナ・ひらがなのいずれも無ければ、基準文字は**定まらない**（下の「同じ行に和文が無い場合」に従う）

漢字を最優先にするのは、字面が上下いっぱいに組まれて高さが安定しているためである（ひらがなの `っ`・`ー` のように字面が小さい文字を基準にすると、比が実態と合わない）。

| 記号 | 定義 |
|---|---|
| `H` | **基準文字の外接矩形の高さ** |
| `BL` | **基準文字の外接矩形の下端**を通る水平線（ベースライン） |
| `h` | **候補の字形の高さ**。候補の `char` に対応する字形の外接矩形の高さ |

比の閾値は **0.8 / 1.2 / 1.5 / 0.2** の 4 つだけを使う（下の手順で用いる）。

**閾値の検証の状態（未検証）**: 上の 4 つの閾値は、本書籍の組版を測らずに置いた**設計値**であり、**検証されていない**。閾値を実測で定める実験（`experiments/thresholds/`。ADR-22）は、`experiments/thresholds/criteria.md` §4.3 の測定不足（群 G3 で測定に成功した標本が 18 件で、19 件に達しなかった）で停止した後、2026-10-07 のユーザー判断で中止した。その結果、閾値は置き直しておらず、3-1(a)(b) の上付き・下付きに位置（浮き上がり・沈み込み）の下限を設ける変更も行っていない。経過と測った値は `experiments/thresholds/experiment_log.md` にある。S3・S4 は本節の規則をこの状態のまま適用する

**どちらとも判断できない場合の扱い**: ある条件について、閾値のどちら側かを PNG 上で判断できない場合、**その条件は満たされないものとして扱う**（項に当てはまらないものとして次の項に進む）。

#### 判定手順（この順に適用し、最初に当てはまった項で決める）

1. **PNG が無い**（逆引きに失敗して切り出していない）→ **`undecidable`**
2. **PNG はあるが、候補の該当箇所を特定できない、または字形を判読できない** → `--margin` を 8.0 から **32.0** に上げて、その候補のブロックについて切り出しを `--overwrite` 付きで 1 回だけやり直す。それでも特定・判読できなければ → **`undecidable`**
   - 「特定できない」とは、PNG に写った文字列の中に、候補レコードの `before` の末尾または `after` の先頭と対応する箇所が見つからないことをいう
3. **該当箇所が特定でき、その位置に候補の `char` に対応する字形がある**とき、次の 4 項を上から順に見て、いずれかに当てはまれば → **`missing`**
   1. **数式の構造の一部**である。構造は次に**列挙したものに限る**——(a) **上付き**（候補の字形または隣接する要素の**下端が `BL` より上**にあり、かつその高さが `0.8 × H` 以下） (b) **下付き**（同じく**下端が `BL` より下**にあり、かつ高さが `0.8 × H` 以下） (c) **分数**（水平の線の上と下の両方に文字が積まれている） (d) **根号**（`√` の横線が右に伸びて 1 文字以上を覆っている） (e) **大型演算子の範囲指定**（3-2 の 6 文字のいずれかの**真上・真下・右上・右下**に、高さが `0.8 × H` 以下の文字が置かれている） (f) **行列・場合分け**（2 行以上の文字の並びが 1 組の括弧で囲まれ、その括弧の高さが `1.5 × H` 以上）
   2. **大型演算子**である。対象は **`∑`・`∏`・`∫`・`∮`・`⋃`・`⋂` の 6 文字に限る**（この 6 文字以外は本項に当てはまらない）。かつ **`h` ≥ `1.5 × H`** である
   3. **右に傾いている**（イタリック体である）。対象はラテン文字とギリシャ文字に限る（`roadmap.md` §6 の数学記号は本項に当てはまらない）。傾きの条件は**字形の外接矩形の上端に接する画の位置が、下端に接する画の位置より右にある**ことをいう（縦画が垂直なら本項に当てはまらない）
   4. **数式の要素と隣接している**。すなわち、候補の字形の**前後の範囲**に、本手順の 3-1〜3-3 のいずれかに当てはまる字形が**1 つでも**あり、かつ**その字形の下端と候補の字形の下端のずれが `0.2 × H` 以内**である
      - **前後の範囲**: 候補の字形と**同じ行**で、候補から**左へ**、和文（ひらがな・カタカナ・漢字）の字形または**行頭**に当たるまでの間にあるすべての字形と、候補から**右へ**、和文の字形または**行末**に当たるまでの間にあるすべての字形。範囲の端に当たった和文の字形は範囲に含めない。候補の隣の 1 字形に限らない（隣の字形が `(`・`,` などで 3-1〜3-3 に当てはまらなくても、その先の字形が範囲内にあれば対象になる）
      - 範囲内に 3-1〜3-3 に当てはまり、下端のずれの条件を満たす字形が 1 つでもあれば、本項に当てはまる（`missing`）。1 つも無ければ本項には当てはまらない
4. 3 のどれにも当てはまらず、次の 3 つを**すべて**満たす → **`not_missing`**
   1. **`0.8 × H` ≤ `h` ≤ `1.2 × H`**（和文と同じ大きさ）
   2. 候補の字形の**下端と `BL` のずれが `0.2 × H` 以内**（和文とベースラインが揃っている）
   3. 3-3 の傾きの条件に**当てはまらない**（和文と同じ立体である）
5. 1〜4 のいずれでも決められない → **`undecidable`**

**条件を確認できない場合の扱い**: 3 の各項と 4 の条件は、上の基準量（`H`・`BL`・`h`）との比だけで書かれている。かすれ・解像度・切り出しの端で基準文字を選べない、または `H`・`BL`・`h` を PNG 上で読み取れない場合、または閾値のどちら側かを判断できない場合、**その条件は満たされないものとして次の項に進む**。その結果 4 の 3 条件をすべては満たせなければ、手順 5 により **`undecidable`** になる（「定義できない見え方」は `missing` にも `not_missing` にも入れない）。

**同じ行に和文が無い場合**（別行立ての数式の中など。上の規則 4）は**基準文字が定まらず** `H`・`BL` も定まらない。このとき 3-1 の (c)・(d)・(f) と 3-3 は `H`・`BL` を使わないため判定でき、それらに当てはまらなければ手順 5 により **`undecidable`** になる。

#### 記録

候補ごとに次の 3 つを `experiment_log.md` に記録する（FR-304 の受け入れ基準）。

1. **判定の 3 値**
2. **当てはまった項の番号**（`1`・`2`・`3-1`・`3-2`・`3-3`・`3-4`・`4`・`5` のいずれか。`3-1` はさらに `(a)`〜`(f)` のどれかを添える）
3. **PNG で読めた該当箇所の文字列**。ただし読めた文字列が存在しない場合（手順 1・2 で `undecidable` になった場合、および手順 5 で該当箇所を読めないまま `undecidable` になった場合）は **`null`** とし、**理由**を次の 3 語のいずれかで記録する

   | 理由 | 意味 |
   |---|---|
   | `PNG なし` | 逆引きに失敗して切り出していない（手順 1） |
   | `特定不能` | PNG はあるが、`before` の末尾・`after` の先頭と対応する箇所が見つからない（手順 2） |
   | `判読不能` | 該当箇所は特定できたが字形を判読できない（手順 2 の `--margin` 32.0 の再試行後も同じ） |

   手順 5 で `undecidable` になった場合（該当箇所を読めてはいるが、3 のどの項にも当てはまらず 4 の 3 条件も満たせない場合）は、読めた文字列をそのまま記録し、理由の欄は空にする

#### 判定規則についての注記

- 本規則は**原本の組み方だけ**を見る。md 側が数式マークアップを持つかどうかは判定に使わない（候補は定義上すべて md の数式マークアップの外にある。`roadmap.md` §6）
- 本規則は**修正の要否を判定しない**（`roadmap.md` P2。本案件は調査のみ）
- 手順 2 の `--margin` のやり直しは**同一実行の中で自分が直前に作った PNG を置き換える**ものであり、手順 -1 の退避の対象である前回の実行の成果物には掛からない

- **却下 A**: 標本抽出・判定入力・集計を行う M3 専用のスクリプトを作る
- **却下 B**: `locate_candidates.py` に `--sample` / `--seed` / 複数の `--select` を足す
- **理由**: `roadmap.md` §7 のステージ表は本ステージの手段を「S2-1 で疎通した逆引き処理＋`scripts/crop_blocks.py`＋目視」と固定している。却下 A は新しい手段に当たり、`CLAUDE.md`「ステージの切り方の規則」により単体疎通のステージを前に置く必要が生じる（ロードマップの改訂とステップ3 のやり直しを伴う）。却下 B も、疎通済みの手段に未疎通の処理を足すことになり、同じ問題を持つ。M2 の ADR-7（検証スクリプトを作らない）と同じ判断である
- **代償**: 判定の記録が 30 回の実行になる（§1.4.5）。1 回の実行で 1 件にしか判定を書けない CLI の仕様によるもので、手順は決定的であり判断を要しない

### ADR-20: 乱数の種を 20260917 に固定する

- **採用**: `SEED` = 20260917（本マイルストーンの着手日）。抽出コマンドを 1 回だけ実行する
- **却下 A**: 種を固定せず、実行のたびに変わる値（時刻など）を使う
- **却下 B**: 種を複数試して、標本の内訳（章の散らばりなど）が良いものを選ぶ
- **理由**: 却下 A は再現性（NFR-303・NFR-305）を失い、`experiment_log.md` の記録から標本を復元できなくなる。却下 B は**実行結果を見てから標本を選ぶ**ことであり、`CLAUDE.md`「実験・検証の進め方」手順4 の事後解釈の禁止に当たる。着手日を種にするのは、実行前に一意に決まり、恣意の余地が無いためである

### ADR-21: 判定規則を「原本の組み方だけ」を見る順序つきの手順にする

- **採用**: §1.4.4 の 5 項の手順。上から順に適用し、最初に当てはまった項で決める
- **却下 A**: 「数式として組まれているか」を総合的に判断する（手順に分けない）
- **却下 B**: md 側の文脈（周囲に `$…$` があるか）も判定に使う
- **却下 C**: 「明らかに大きい」「和文書体ではない」のような、見え方の程度を言葉で書いた条件にする
- **理由**: `roadmap.md` P9-1 は S3 と S4 で**同一の判定規則**を使うことを求めている。却下 A は判定のたびに基準が揺れ、S4 で同じ規則を適用したと言えなくなる。却下 B は、候補が定義上すべて md の数式マークアップの外にあること（`roadmap.md` §6）と、測る対象が「原本で数式として組まれている記号のうち md でマークアップを失っているもの」であること（§1）から、判定の入力に md 側の状態を混ぜると同語反復になる。手順を上から順に適用する形にすることで、判定できない場合（1・2・5）が `undecidable` に集まり、`q` の定義（`roadmap.md` §7）と対応する。却下 C は、同じ PNG に対して判定が分かれうるため S3 と S4 で同一の規則を適用したと言えなくなる（codex-52 の指摘）。そこで、構造を (a)〜(f) の 6 種に、大型演算子を 6 文字と高さ 1.5 倍以上に、傾きを対象文字の種類に、隣接をベースラインと介在する文字種に、それぞれ閉じた条件として書き下し、**条件を PNG 上で確認できない見え方は `undecidable` に落ちる**ようにした

### ADR-22: 判定規則の閾値を定める実験の実験コードを `experiments/thresholds/` に置く

- **採用**: §1.4.4 の閾値（0.8 / 1.2 / 1.5 / 0.2 と、新設する上付き・下付きの位置の下限）を実測で定める実験を、`experiments/thresholds/criteria.md` に従って行う。そのための実験コード `extract_samples.py`（標本の抽出）と `measure_glyphs.py`（2 値化・連結成分・高さとずれの計算）を **`m3-pilot-measure/experiments/thresholds/`** に置く
- **却下 A**: `scripts/` にプロダクトコードとして置き、`tests/` にテストを置く
- **却下 B**: 実験コードを書かず、目視で高さとずれを比べる
- **却下 C**: S3 の手段に組み込む（S3 の実行の中で閾値を測る）
- **理由**: `CLAUDE.md`「ドキュメント作成ルール」の判定基準は「**その案件が終わった後も使うか**」である。本実験コードは本案件の閾値を一度定めるためだけのもので、案件の完了後に他の入力・他の案件で使う見込みが無い。したがって実験コードであり、マイルストーンフォルダ配下（実験フォルダ）に置く（却下 A）。却下 B は、閾値を目視の印象で置いた現状（根拠の無い値）と同じ問題を残す。却下 C は、`roadmap.md` §7 のステージ表が S3 の手段を「S2-1 で疎通した逆引き処理＋`scripts/crop_blocks.py`＋目視」と固定していることに反し、新しい手段として単体疎通のステージが要る。**本実験コードは S3 の実行（§1.9.2）では一切使わず、その出力は §1.4.4 に書く閾値の数値だけ**であるため、S3 の手段には加わらない（ADR-19 の「新しいスクリプトを作らない」は S3 の実行に使うコードについての判断であり、本 ADR と矛盾しない）
- **依存**: Python 標準ライブラリと Pillow 12.3.0 だけ（§1.3）。numpy は使わない
- **動作確認**: `tests/` にテストを置かない代わりに、両スクリプトに `--selftest` を持たせ、`experiments/thresholds/criteria.md` §3.5 の固定ケース（期待値つき）を実行する。測定の前に実行し、終了コードが 0 でなければ測定に進まず中断して報告する
- **作成と実行の分担**: 実験コードの作成は `CLAUDE.md`「実装の実行方法（Sonnetサブエージェント）」に従い Sonnet サブエージェントに委任する（委任の範囲は criteria.md §2.2・§3.2・§3.5 の仕様のとおりのコードの作成と、§3.5 の `--selftest` が終了コード 0 で終わることの確認まで）。測定（実データの投入と成分の選択）は Claude Code 本体が行う。実験コードは `tests/` にテストを置かない（`CLAUDE.md`「テスト」の対象はプロダクトコードであるため）
- **経緯**: 2026-09-17 の人レビューで、§1.4.4 の閾値に実測の根拠が無いことが判明した。ユーザー指示（2026-10-06）により「閾値・パラメータの妥当性検証」として実験を行うこととし、criteria.md の全文ゲート（codex-60）と解消確認（codex-61）で、実験コードの配置と判断を実装前に `design.md` の ADR に記録するよう指摘された
- **結果**: 実験は criteria.md §4.3 の測定不足で停止し、2026-10-07 のユーザー判断で中止した。§1.4.4 の閾値は置き直していない（§1.4.4「閾値の検証の状態」）。実験フォルダの文書・実験コードと、リポジトリ外の成果物は削除しない
