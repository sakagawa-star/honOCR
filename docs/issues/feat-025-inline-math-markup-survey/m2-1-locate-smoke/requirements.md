# feat-025 M2-1 要求仕様書: 逆引き処理の単体疎通

- **マイルストーン**: M2-1（ステージ S2-1）
- **作成日**: 2026-09-10
- **関連**: `../roadmap.md`（§3 の P6・P7・P9-1 / §5 入力の次元と `c'_i` / §7 ステージ表 / §8 の S2-1 / §9 の M2-1）、`../m2-population/design.md`（入力となる候補レコードの出所）、`../m1-extract-smoke/design.md` §1.4.3（候補レコードの形式）

**要求 ID の付番**: 本案件内で一意にするため、M1 は 000 番台、M2 は 100 番台、**M2-1 は 200 番台**（FR-201〜206）を使う。

## 1.1 プロジェクト概要

- **何を作るのか**: 候補レコード 1 件から、その候補が原本のどのページにあるかを content_list 経由で特定する**逆引き処理**（CLI）を作る。そのうえで、既存の `scripts/crop_blocks.py` で原本 TIF の該当領域を PNG に切り出し、目視できることを確認して、**判定結果レコード 1 件**を出力する
- **なぜ作るのか**: `roadmap.md` §7 のステージ表で S2-1 の手段は「無し（新規の逆引き処理）」であり、この手段は S3（予備標本 30 件）と S4（本標本 `n` 件）で使う。`CLAUDE.md`「ステージの切り方の規則」により、使うステージより前に 1 単位の入力で通す単体疎通を置く必要がある。本マイルストーンがその単体疎通である
- **誰が使うのか**: Claude Code（M3・M4 が同じ逆引き処理を標本の全件に適用する）
- **どこで使うのか**: honOCR リポジトリのローカル環境（Python 3.12、`uv run`）。GPU 不要、ネットワーク不要

## 1.2 用語定義

`roadmap.md` と M1・M2 の文書で定義済みの語を同じ意味で使う（定義の本体は下表の参照先にあり、本書では再定義しない）。本マイルストーンで新たに定める語には「新規」と記す。

| 用語 | 意味と定義の所在 |
|---|---|
| **候補レコード** | 候補 1 件を表すデータ。5 キー（`chapter`・`offset`・`char`・`before`・`after`）。成分数は `c_i`（`roadmap.md` §5、`../m1-extract-smoke/design.md` §1.4.3） |
| **判定結果レコード** | 候補レコードに**原本ページ番号 1 成分と判定 1 成分を足した**データ。成分数は `c'_i` = `c_i` + 2（`roadmap.md` §5） |
| **逆引き** | 候補レコードから content_list のブロックを特定し、そのブロックの `page_idx`（原本ページ番号）と `bbox` を得ること（`roadmap.md` P7） |
| **照合キー**（新規） | 逆引きで content_list のブロックを探すときに使う、候補の前後の文脈を含む文字列。作り方は `design.md` §1.4.2 |
| **`K` の階梯**（新規） | 照合キーの長さを段階的に短くする手順。値の並びは `design.md` §1.4.2 で固定する |
| **逆引き失敗**（新規） | 照合キーがどの長さでもブロックを一意に定められないこと。このとき原本ページ番号は `null` になる。**失敗したときの扱いはマイルストーンで異なる**（§1.7 の「逆引きが失敗する候補への対処」） |
| **判定** | 候補が原本で数式として組まれていたか否かの結論。値の集合は `design.md` §1.4.4。**判定規則の本体は M3 の `design.md` で定める**（`roadmap.md` P9-1） |

## 1.3 機能要求一覧

### FR-201 候補レコードから content_list のブロックを特定する

- **概要**: 候補レコードの前後の文脈を照合キーとして、その章の content_list からブロックを一意に特定する
- **入力**: 候補レコード 1 件と、その章の content_list
- **出力**: ブロック番号（content_list の配列の添字）と `page_idx`
- **受け入れ基準**:
  - [ ] 候補の `chapter` から、その章の content_list を一意に決められる（`design.md` §1.4.1 の規約）
  - [ ] 照合キーを作る前に、候補の前後の文脈を**改行で切り詰める**（`design.md` §1.4.2・ADR-17）
  - [ ] 切り詰めは照合キーの生成にだけ効き、**候補レコードの `before` / `after` は原文のまま残る**（`roadmap.md` §5 の `c_i` が変わらない）
  - [ ] 照合キーの作り方と `K` の階梯が `design.md` §1.4.2 のとおりであり、同じ入力に常に同じ結果を返す
  - [ ] ブロックが一意に定まったとき、その `page_idx` を原本ページ番号とする
  - [ ] ブロックを一意に定められないとき（すべての `K` で 0 件、またはある `K` で 2 件以上）、**逆引き失敗**として原本ページ番号を `null` にする（エラーで終了しない）
  - [ ] 特定したブロック番号・`page_idx`・採用した `K` を標準出力に出す（後続の切り出しに使うため）

### FR-202 判定結果レコードを出力する

- **概要**: 候補レコードに原本ページ番号と判定を足した判定結果レコードを、JSONL としてファイルに書き出す
- **入力**: FR-201 の結果と、判定の値
- **出力**: JSONL ファイル
- **受け入れ基準**:
  - [ ] レコードのキーが **7 個**（候補レコードの 5 キー ＋ `page_idx` ＋ `judgment`）であり、`roadmap.md` §5 の `c'_i` = `c_i` + 2 と一致する
  - [ ] 1 行が 1 件で、JSON として読み戻せる
  - [ ] 判定を与えないとき `judgment` が `null` になる
  - [ ] 逆引き失敗のとき `page_idx` が `null` になる
  - [ ] 出力先が既に存在するとき、上書きを指定しない限り書き込まずに終わる

### FR-203 CLI としての実行

- **概要**: コマンドラインから、候補レコードのファイル・成果物ディレクトリ・出力先・処理対象の候補・判定を指定して実行できる
- **入力**: コマンドライン引数
- **出力**: 終了コード（**正常終了は 0 / 運用エラーは 1 / 引数の形式・必須引数の誤りは 2**）と、標準出力への逆引きの内訳
- **受け入れ基準**:
  - [ ] 候補レコードのうち **1 件だけを選んで処理できる**（本マイルストーンは 1 単位のみを扱うため）
  - [ ] 候補レコードの**全件を処理できる**（M3・M4 で使うため）
  - [ ] 入出力のパス・パラメータをハードコードせず、すべて引数で受け取る（`CLAUDE.md`「コーディング規約」）
  - [ ] 入力ファイル・成果物ディレクトリが存在しないとき、そのパスを標準エラー出力に示して終了コード 1 で終わる
  - [ ] 引数の形式が誤っているとき、使い方を表示して終了コード 2 で終わる（`argparse` の標準の挙動）

### FR-204 原本 TIF からの切り出しと目視

- **概要**: FR-201 で特定したブロックを、既存の `scripts/crop_blocks.py` で原本 TIF から PNG に切り出し、目視する
- **入力**: FR-201 のブロック番号、その章の content_list と原本 TIF ディレクトリ
- **出力**: グレースケール PNG
- **受け入れ基準**:
  - [ ] `scripts/crop_blocks.py` を**変更せずに**使う（C-203）
  - [ ] PNG が出力され、Read ツールで開いて**原本の該当箇所を目視できる**
  - [ ] 目視した内容を `experiment_log.md` に記録する

### FR-205 判定の記録

- **概要**: 目視の結果を判定として判定結果レコードに記録する
- **入力**: FR-204 の目視の結果
- **出力**: `judgment` を持つ判定結果レコード 1 件
- **受け入れ基準**:
  - [ ] **本ステージの出力**（`design.md` §1.6 の判定結果レコードのファイル）のレコードの `judgment` が、`design.md` §1.4.4 の値の集合のいずれかであり、`null` でない
  - [ ] **逆引きに成功した場合に限り**、本ステージの出力を作る。逆引きに失敗した場合（および PNG を判読できなかった場合）は判定を記録せず、判定結果レコードを作らない（`design.md` §1.9.2 の手順 3 の分岐、ADR-16）
  - [ ] 中間出力（逆引きのみを行った出力）と全件処理の出力では `judgment` が `null` でよい。これらは**本ステージの最終出力ではない**（レコードの形と判定結果レコードとしての定義は同じである。`design.md` §1.4.4）
  - [ ] CLI の機能として `undecidable` を記録できる（M3・M4 が判定不能を数えるため。`design.md` §1.4.4）
  - [ ] **本マイルストーンの判定 1 件を S3・S4 の測定に用いない**（§1.7。判定規則の本体は M3 で定めるため）

### FR-206 予測と実測の照合を記録する

- **概要**: 実行前の予測と実行後の実測の照合を `experiment_log.md` に記録する
- **入力**: `roadmap.md` §8 の S2-1 の想定値の式と、FR-202 の出力
- **出力**: `experiment_log.md` の記録
- **受け入れ基準**:
  - [ ] 実行の**前**に直前予測（式・入力値とその出所・予測値・幅）が記録され、その 1 ファイルだけがコミットされている
  - [ ] 実行の後に実測（判定結果レコードの件数、逆引きの内訳、目視の結果）が記録されている
  - [ ] 再実行のときは、退避した前回の成果物のパスと一覧が記録されている（C-209）
  - [ ] 予測値・実測値・差の照合が記録されている
  - [ ] 実測が `roadmap.md` §8 の S2-1 の想定値の幅を外れた場合、`experiment_log.md` に書く内容を `CLAUDE.md`「ロードマップの改訂（再計画）」の「書いてよいもの」に限る（外れの条件は `roadmap.md` を参照する。本書には再掲も追加もしない）

## 1.7 範囲外（本マイルストーンで扱わないこと）

- **判定規則の本体**: 何をもって「原本で数式として組まれていた」とするかの規則は **M3 の `design.md`** で定める（`roadmap.md` P9-1）。本マイルストーンは判定の値を書き込む器と経路だけを通す
- **本マイルストーンの判定 1 件の測定への流用**: `q`・`p₀`（S3）と `k`・`u`（S4）の測定に用いない。判定規則が確定する前の 1 件であるため
- **標本の抽出**: M3（予備標本 30 件）・M4（本標本 `n` 件）で行う。本マイルストーンは `design.md` §1.4.5 で固定した 1 件だけを扱う
- **逆引きの成功率の測定**: 判定可能率 `q` は S3（M3）で測る（`roadmap.md` P8）。本マイルストーンは 1 件の疎通のみで、成功率を推定しない
- **逆引きが失敗する候補への対処**: 失敗を減らす工夫（照合の手段の追加）は本マイルストーンで行わない。失敗したときの扱いは、**M2-1 では判定を記録せず本ステージの最終出力を作らない**（件数 0 として `roadmap.md` §8 の S2-1 の幅を外れ、再計画に入る。`design.md` §1.9.2 の手順 3、ADR-16）。**M3・M4 では全件処理の経路で `undecidable`（判定不能）として扱い、`roadmap.md` の `u` に数える**（`design.md` §1.4.4・§1.4.5）
- **`crop_blocks.py` の機能追加・修正**: C-203 のとおり行わない
