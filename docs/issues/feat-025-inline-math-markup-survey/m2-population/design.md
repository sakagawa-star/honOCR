## 1.4 各機能の詳細設計

### 1.4.1 全10章の入力指定（FR-101）

/home/sakagawa/work/確率統計/ocr/final/chap06/chap06_gray300.md
/home/sakagawa/work/確率統計/ocr/final/chap07/chap07_gray300.md

```

章名は CLI が親ディレクトリ名から取る（`../m1-extract-smoke/design.md` の ADR-5）。したがって出力の `chapter` は `chap00`〜`chap09` になる。

#### 処理ロジック

CLI 側の処理は M1 で完成しており、本マイルストーンで変えない。入力の順に処理され、各ファイルの中では `offset` の昇順に並ぶ（`../m1-extract-smoke/design.md` §1.4.5 の手順 4 と §1.4.2）。

#### エラーハンドリング

| 想定される事象 | 検出方法 | 処理 |
|---|---|---|
| 入力ファイルのいずれかが存在しない | CLI が全件を先に確認する（`../m1-extract-smoke/design.md` §1.4.5 の手順 2） | CLI が終了コード 1 で終わり、出力ファイルを作らない。実行を中断し、パスを確認する |
| 入力が UTF-8 として読めない | CLI の `UnicodeDecodeError` | CLI が終了コード 1 で終わる。想定外事象として実行を中断し、報告する |

#### 境界条件

| 事象 | 振る舞い |
|---|---|
| 章に候補が 1 件も無い | その章のレコードが 0 件になり、標準エラー出力に `0 件` と出る。エラーにしない（`../m1-extract-smoke/design.md` §1.4.4） |

### 1.4.2 単一 JSONL への出力（FR-102）

#### データフロー

- 入力: §1.4.1 の 10 ファイル
- 出力: `{BASE2}/ocr/feat-025/m2_all_candidates.jsonl`（1 行 1 レコードの JSONL）

#### ファイル形式

M1 と同一（`../m1-extract-smoke/design.md` §1.4.4）。レコードのキーは `chapter`・`offset`・`char`・`before`・`after` の 5 個で、文字コードは UTF-8、改行コードは `\n`。形式・順序が保たれることは M1 のテストで検証済みであり、本マイルストーンで再検証しない（`requirements.md` §1.7）。

#### 出力先の保護

`--overwrite` を**付けない**（ADR-9）。出力先が既に存在すれば CLI が終了コード 1 で終わる（`../m1-extract-smoke/design.md` §1.4.4 の「出力先の判定」）。これにより、誤って 2 回実行しても既存の出力を壊さない。

出力先のファイル名は M1 の出力と異なる（§1.6）ため、M1 の出力を上書きする経路が無い（C-102）。

**再実行が必要になった場合**（実行が途中で失敗して出力が残った場合など）は、既存の出力ファイルの内容を確認したうえで実行を中断して報告する。本設計は `--overwrite` の使用を手順に含めない。

#### 境界条件

| 事象 | 振る舞い |
|---|---|
| 出力先の親ディレクトリ `{BASE2}/ocr/feat-025/` が既に存在する（M1 が作成済み） | そのまま書き込む（CLI が `exist_ok=True` で扱う） |
| 出力先 `m2_all_candidates.jsonl` が既に存在する | CLI が終了コード 1 で終わる。上記「再実行が必要になった場合」に従う |

### 1.4.3 測定値 `N` の確定（FR-103）

#### データフロー

- 入力: §1.4.2 の出力 JSONL と、CLI の標準エラー出力
- 出力: `N`（整数。次元 1）

#### 処理ロジック

`N` を**出力 JSONL の行数**とする。次の 2 つの経路で数え、一致することを確認する。

1. CLI が標準エラー出力に出す「合計」の件数（`../m1-extract-smoke/design.md` §1.8）
2. `wc -l` による出力 JSONL の行数

**2 つが一致しない場合は `N` を確定せず、想定外事象として実行を中断して報告する**（`CLAUDE.md` 機能追加フローのステップ6 の想定外事象の扱い）。

**`wc -l` が正しく数える根拠**: CLI は各レコードの末尾に改行を付けて書く（`../m1-extract-smoke/design.md` §1.4.4）。したがって最終行にも改行があり、`wc -l` の値はレコード件数と等しい。

#### 照合

`N` を `roadmap.md` §8 の S2 の想定値と幅に照合する。照合は**合計 `N` に対してのみ**行い、章別件数には行わない（`roadmap.md` §8 の S2）。幅を外れた場合の扱いは `CLAUDE.md`「ロードマップの改訂（再計画）」に従う。

### 1.4.4 リソースと性能

CLI は全10章を文字列としてメモリに載せて処理する（`../m1-extract-smoke/design.md` §1.4.6）。ストリーム処理・並列化・キャッシュを行わない。

**処理時間（NFR-103）の検証**: 実行時に経過時間を測り、60 秒以内であることを確認する。測定の方法は §1.9.2 の手順 3（GNU time による計測）、記録先は同 手順 5（`experiment_log.md`）、**60 秒を超えた場合の扱いは同 手順 3 の分岐**（マイルストーンを完了扱いにせず中断して報告する）に定める。

### 1.9.2 S2 の実行手順（FR-101〜FR-104）

**本マイルストーンで作成・変更するコードが無いため、ステップ6 の実装をサブエージェントに委任しない**（委任の対象となる実装が存在しない。`CLAUDE.md`「実装の実行方法（Sonnetサブエージェント）」）。**ステージの実行も委任しない**（同 機能追加フローのステップ6、`requirements.md` C-106）。Claude Code 本体が次の順に行う。**実行単位は「全10章を 1 回」の 1 単位であり、予測の記録もこの 1 実行についてのみ行う。**

0. **全件テストの実行**: §1.9.1 のとおり `uv run pytest -v` を実行し、結果を `tests/results/feat-025_test_result.txt` に上書き保存する。失敗があれば中断して報告する
1. **直前予測の記録**: `experiment_log.md` に、`roadmap.md` §8 の S2 の想定値の式に入力値を代入した予測値と幅を書く。式の入力は `C_all`（`roadmap.md` §3 の P14 の定数）1 つであり、入力ごとに出所（**ロードマップで固定した定数**）を名指しする。式に無い項目の予測と、幅の無い点予測を足さない（`CLAUDE.md`「実験・検証の進め方」項目2）
2. **予測のコミット**: `experiment_log.md` の **1 ファイルだけ**をコミットする。メッセージは定型 `feat-025: M2 全10章 の予測を記録`（末尾トレーラーは本体が稼働しているモデルの `Co-Authored-By`）。**push はしない**（`CLAUDE.md`「git 操作の実行方法」の予測記録の例外。本体が直接行う）。コミット対象に他のファイルが含まれる場合や失敗した場合は、対処せず報告する
3. **実行と処理時間の計測**: 次のコマンドを **1 回だけ**実行する（`--overwrite` を付けない）。**GNU time（`/usr/bin/time`）で囲んで経過時間を測る**（`/usr/bin/time` はラップしたコマンドの終了コードをそのまま返すため、手順 4 の終了コードの取得に影響しない）

     /home/sakagawa/work/確率統計/ocr/final/chap04/chap04_gray300.md \
     /home/sakagawa/work/確率統計/ocr/final/chap05/chap05_gray300.md \
     /home/sakagawa/work/確率統計/ocr/final/chap06/chap06_gray300.md \
     /home/sakagawa/work/確率統計/ocr/final/chap07/chap07_gray300.md \
     /home/sakagawa/work/確率統計/ocr/final/chap08/chap08_gray300.md \
     /home/sakagawa/work/確率統計/ocr/final/chap09/chap09_gray300.md \
     -o /home/sakagawa/work/確率統計/ocr/feat-025/m2_all_candidates.jsonl
   ```

   **経過時間が 60 秒を超えた場合**（NFR-103 の違反）は、`N` の照合を行わず、マイルストーンを完了扱いにしない。経過時間と実測を `experiment_log.md` に記録したうえで**中断して報告する**（想定外事象の扱い。`CLAUDE.md` 機能追加フローのステップ6）

4. **実測の取得**: 次を行い、値を控える
   1. CLI の終了コードと標準エラー出力（ファイルごとの件数と合計）
   2. `/usr/bin/time` が標準エラー出力に出した `経過時間: {秒} 秒`
   3. `wc -l /home/sakagawa/work/確率統計/ocr/feat-025/m2_all_candidates.jsonl` による行数
   4. §1.4.3 のとおり 2 つの件数（CLI の合計・`wc -l`）が一致することを確認し、一致した値を `N` とする
   5. 手順 4-2 の経過時間が 60 秒以内であることを確認する（NFR-103）。超えていれば手順 3 の分岐に従う
5. **照合の記録**: `experiment_log.md` に、実測（`N` と CLI の標準エラー出力）と、予測値・実測値・差の照合を書く。章別件数と経過時間は**記録のみ**とし、照合の対象にしない（章別件数は `requirements.md` §1.7、経過時間は `roadmap.md` §8 の S2 の想定値の式に無い項目であり、`requirements.md` NFR-103 の受け入れの確認に用いる値である）。想定の幅を外れた場合は `CLAUDE.md`「ロードマップの改訂（再計画）」に従い、`experiment_log.md` に書く内容を同節の「書いてよいもの」に限る

**シェルの扱い（実行時の注意）**: 確認のために一時的なコマンドを書く場合、**ダブルクォート内に正規表現やバックスラッシュを含む文字列を書かない**。シェルがエスケープを解釈して意図と異なる式になるため、クォートしたヒアドキュメント（`<<'PY'`）を使う。

## 2. 記述ルールへの適合

### 2.1 曖昧表現の排除

本設計書に「適切に」「必要に応じて」「等」を使っていない。入力パス 10 個、出力パス、実行コマンド、計数の経路、中断の条件をすべて具体値で示した。

### 2.2 実装判断ゼロの確認

本マイルストーンで書くコードは無いため、実装判断の余地は実行手順に限られる。次の点を明示したことで、2 通り以上の実行が考えられる箇所を無くした。

- 入力を **1 回の実行**で 10 個渡すこと（章ごとに 10 回実行しない）
- 入力パスを **glob でなく明示列挙**すること（ADR-8）と、その順序（`chap00` → `chap09`）
- `--overwrite` を**付けない**こと（ADR-9）
- 出力ファイル名を `m2_all_candidates.jsonl` とすること（M1 の出力と別名）
- `N` を 2 つの経路（CLI の合計・`wc -l`）で数えて一致を確認すること
- 処理時間を `/usr/bin/time -f "経過時間: %e 秒"` で測り、60 秒を超えたら完了扱いにせず中断すること（NFR-103）
- 新規のコード・テストを追加せず、既存テストを全件実行して結果を上書きすること

### 2.3 コード例の位置づけ

本書にコードは無い。§1.9.2 のコマンドは実行手順であり、そのまま実行するものである。

## 2.2 設計判断の記録（ADR）

### ADR-6: M1 の CLI を変更せず、そのまま使う

- **採用**: `scripts/extract_math_candidates.py` を無変更で 10 ファイルに適用する
- **却下 A**: 全10章専用のラッパースクリプト（章の列挙を内蔵したもの）を作る
- **却下 B**: CLI に「ディレクトリを渡すと配下の md を全部処理する」機能を足す
- **理由**: M1 の FR-005 で「入力ファイルを 2 個以上指定できる」ことが要求・実装・テスト（T-16）済みであり、S2 に必要な機能は既にある。却下 A・B はいずれも `roadmap.md` §7 のステージ表で本ステージの手段を「S1 の CLI」と定めたことに反し、新しい手段を足すことになる（新しい手段には単体疎通のステージが要る。`CLAUDE.md`「ステージの切り方の規則」）。また却下 B は章の集合が入力ディレクトリの内容に依存し、実行のたびに対象が変わりうるため、決定性（NFR-104）を弱める

### ADR-7: 出力を検証するスクリプトを作らない

- **採用**: 新しいスクリプトを作らない。`N` は CLI の標準エラー出力と `wc -l` の 2 経路で数える（§1.4.3）。出力の形式・順序・成分数 `c_i` は M1 のテストで検証済みのものとして再検証しない（`requirements.md` §1.7）
- **却下 A**: 出力 JSONL を読んで章別内訳・順序・`c_i` の分布を数える検証スクリプトを作り、S2 の確認に使う
- **却下 B**: 却下 A のスクリプトを作り、その単体疎通のマイルストーンを S2 の前に足す（ロードマップを改訂する）
- **理由**: `roadmap.md` §7 のステージ表は本ステージの手段を「S1 の CLI」と固定している。検証スクリプトは新しい手段であり、`CLAUDE.md`「ステージの切り方の規則」により、それを使うステージより前に単体疎通のステージを置く必要が生じる（却下 A は規則違反、却下 B はロードマップの改訂とステップ3 のやり直しを伴う）。本ステージの決める項は `N` だけであり（`roadmap.md` §7）、`N` を得るのに検証スクリプトは要らない。出力の形式・順序・成分数は M1 の要求（FR-003・FR-004・FR-005）としてテスト済みで、本マイルストーンでコードを変えないため崩れる経路が無い。**このレビュー指摘は codex-28 による**（`../reviews/codex-28.result.md`）
- **`c_i` の扱い**: `roadmap.md` §5 は本案件の全候補が `c_i` = 88 であることを実測として記載しており、S2 の出力の次元 `Σ c_i` = `N` × 88 はその実測に依る。本マイルストーンはこの実測を再測定せず、`roadmap.md` の記載をそのまま用いる

### ADR-8: 入力パスを glob でなく 10 個明示列挙する

- **採用**: §1.4.1 のとおり 10 個のフルパスを書き並べる
- **却下**: `{BASE2}/ocr/final/chap0*/chap0*_gray300.md` のようにシェルの glob で渡す
- **理由**: glob の展開結果は、ディレクトリの内容・シェルの設定（`nullglob`・ロケールによる並び順）に依存する。`roadmap.md` §8 の S2 の幅が 0 であることは「同じ入力に同じ規則を適用すれば出力が一意である」ことに依るため、**入力の集合と順序が実行時の環境で変わる余地を残さない**。10 個という数は固定であり（`roadmap.md` P1）、列挙の手間は問題にならない

### ADR-9: 出力先の保護を `--overwrite` なしで働かせる

- **採用**: 実行コマンドに `--overwrite` を付けない
- **却下**: 常に `--overwrite` を付けて、何度でも実行できるようにする
- **理由**: 本ステージの実行は 1 回であり（`roadmap.md` §7 の処理単位が全10章 1 単位）、予測の記録とコミットの後に 1 実行だけを行う（`CLAUDE.md`「実験・検証の進め方」項目2）。`--overwrite` を常用すると、実行が 2 回以上行われても記録から見分けられなくなる。付けなければ 2 回目の実行が終了コード 1 で止まり、記録と実体の食い違いが起きない
