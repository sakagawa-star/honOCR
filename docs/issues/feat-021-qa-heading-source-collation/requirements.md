## 1.1 プロジェクト概要

### 何を作るのか

書籍『プログラミングのための確率統計』の OCR 成果物（`{BASE2}/ocr/final/`）に含まれる
**Q&A コラム見出し全74件**を、**スキャン原本 TIF の該当箇所と1件ずつ突き合わせ**、
一致/不一致を全件記録する。あわせて、原本の任意領域を content_list の座標から
切り出して目視できるようにする CLI（`scripts/crop_blocks.py`）を新設する。

**本案件は調査であり、見つかった不一致の修正は行わない**（§1.5 制約条件 C-04）。

### なぜ作るのか（解決したい課題）

これまでユーザーが手動テストで発見した OCR の問題は、**すべて Q&A コラム見出しで発生している**。

| 発見された問題 | 扱い |
|---|---|
| Q&A 見出しの2ブロック分断（`? 2.2`） | feat-015（Closed） |
| Q&A 見出し先頭の「？」アイコン分離 8件 | feat-014（Closed） |
| Q&A 見出しが見出しとして認識されない 19件 | feat-020（Open・未着手） |
| `? 2.7` の欠落 | feat-020 の γ型として起票済み |
| `? 2.10` の誤読「こぜんぶ → これぜんぶ」 | 未起票 |

現状は「ユーザーが読んでいて偶然気づく」ことに依存しており、**発見が網羅的でない**。
Q&A 見出しは MinerU の layout 解析が繰り返し失敗している箇所であり、かつ全74件と数が
限られるため、**全件を原本と突き合わせて洗い出すことが現実的かつ有効**である。

### 誰が使うのか

- 本案件の実施者: Claude Code 本体（原本画像の目視判断を伴うため）
- `scripts/crop_blocks.py` の利用者: 本プロジェクトで OCR 誤りを調査する者
  （ユーザーが Claude Code なしで単独実行することも想定する）

### どこで使うのか（実行環境の概要）

- OS: Linux（Ubuntu 24 系）
- Python 3.12 / uv によるパッケージ管理
- 原本・OCR 成果物はリポジトリ外（`{BASE2}` = `/home/sakagawa/work/確率統計`）
- GPU 不要（MinerU の再実行は行わない）

## 1.3 機能要求一覧

### FR-001: Q&A コラム見出し74件の所在の確定

- **機能名**: 74件の所在特定と S 型分類
- **概要**: final 全10章の content_list から Q&A コラム見出し74件を特定し、各件について
  「章・番号・content_list のブロック番号・`type`・`text_level`・`page_idx`・原本 TIF ファイル名・bbox」を確定する。
  あわせて次の6分類（**S 型**）を与える。

  | S 型 | content_list 上の状態 | 件数 |
  |---|---|---|
  | S1 | `type=text`・`text_level=2`・先頭に `?` あり（正常な見出し） | 52 |
  | S2 | `type=text`・`text_level=2`・先頭に `?` なし | 6 |
  | S3 | `type=text`・`text_level` なし・先頭に `?` あり（本文段落） | 12 |
  | S4 | `type=text`・`text_level` なし・先頭に `?` なし（本文段落） | 1 |
  | S5 | `type=equation`（数式ブロックに埋没） | 1 |
  | S6 | `type=code`（コードブロックに埋没） | 2 |
  | | **計** | **74** |

- **入力**: `{BASE2}/ocr/final/chap00〜09/chapNN_gray300_content_list.json`（10ファイル）、
  `{BASE2}/ocr/pdf/chapNN_gray300.pdf.manifest.json`（10ファイル。page_idx → TIF 名の解決に使う）
- **出力**: 74行の所在一覧（`design.md` に確定値として掲載済み。実施時に再生成して一致を確認する）
- **受け入れ基準**:
  1. 抽出件数がちょうど **74件**であること
  2. S 型ごとの件数が上表（52/6/12/1/1/2）と一致すること
  3. 各件の `page_idx` が当該章の TIF 枚数の範囲内（`0 <= page_idx < 枚数`）であること
  4. 74件の (章, 番号) がすべて相異なること

### FR-002: 母集団74件の妥当性検証

- **機能名**: 網羅性の裏づけ
- **概要**: 「Q&A コラム見出しは74件で全部である」ことを、次の3つの独立した検査で裏づける。
- **入力**: final 全10章の md と content_list
- **出力**: 3検査の結果（合格/不合格と、不合格時は該当箇所の一覧）
- **受け入れ基準**（3件すべてが合格であること）:
  1. **連番検査**: 各章の Q&A 番号が 1 から始まる連番で、欠番が無いこと
     （chap09 は A.1〜A.3・B.1・C.1〜C.2 の3系列それぞれについて判定する）
  2. **重複検査**: 74件の番号に、章をまたぐ重複が無いこと
  3. **相互参照検査**: md 全文から `？N.M` / `?N.M` 形式の相互参照を収集し、
     そこに現れる番号がすべて74件の集合に含まれること（74件に無い番号への参照が 0 件であること）
- **既知の残存リスク（本案件では解消しない）**: 「章の最大番号より後ろの Q&A が、番号ごと
  完全に失われている」場合、上記3検査のいずれにも現れない。この可能性を排除するには全383ページの
  走査が必要であり、**2026-09-02 のユーザー決定により本案件では行わない**（母集団は74件で確定する）。
  本リスクは突合結果の記録に明記する。

### FR-003: 原本との突合の実施

- **機能名**: 74件の原本突合
- **概要**: 74件それぞれについて、原本 TIF の該当領域を目視し、印刷されている文字列と
  md の文字列を比較して、一致/不一致を判定する。
- **入力**: FR-001 の所在一覧、原本 TIF、`{BASE2}/ocr/final/chapNN/chapNN_gray300.md`
- **出力**: 74件それぞれの判定結果（§FR-004 の記録に格納する）
- **判定の構造**: 各件に「**主判定**」を1つだけ与え、主判定が `P1`（不一致）の場合に限り
  「**不一致の内訳フラグ**」を1つ以上立てる。主判定は排他であり、74件の主判定別件数の合計は必ず 74 になる。
  内訳フラグは複数立てられるため、フラグ別件数の合計は P1 の件数と一致しない（一致させない）。

- **主判定**（排他。各件にちょうど1つ）:

  | 区分 | 定義 |
  |---|---|
  | **P0** | 一致（§比較規則により、原本の質問文と md の質問文が一致する） |
  | **P1** | 不一致（§比較規則により、一致しない箇所が1つ以上ある） |
  | **P9** | 判定不能（原本が判読できない、または該当領域が特定できない） |

- **不一致の内訳フラグ**（`P1` のときのみ。1件に複数立ててよい）:

  | フラグ | 定義 |
  |---|---|
  | **D1** | **質問文部**の地の文の文字の不一致（誤読・脱落・余分な挿入。例: 「こぜんぶ」←「これぜんぶ」） |
  | **D2** | 見出し体裁の不一致（**プレフィックス部**に `##` が無い・`?` が無い・番号が無い。空白の差は含めない） |
  | **D3** | ブロック構造の不一致（数式・コード・画像など別種のブロックに取り込まれている） |
  | **D4** | **質問文部**の数式の不一致（§比較規則の数式部分の規則により、対応が取れない要素がある） |

- **比較規則**（実施者によらず同じ結論になるよう、次のとおり定める）:

  1. **見出しの切り分け**: 各件を**プレフィックス部**と**質問文部**に分ける（用語定義を参照）。
     - **プレフィックス部は体裁の比較（規則7・`D2`）でのみ判定し、文字単位の比較（`D1`）の対象にしない。**
       md 側の `##` は Markdown の記法であって原本の紙面には存在しないため、
       プレフィックス部を文字単位比較に含めると全件が不一致になり、判定が成立しない
     - **プレフィックス部に含まれる空白の有無・量は判定しない。**
       原本の「？」は**装飾アイコン**であり、アイコンと番号の間の隙間は空白文字ではないため、
       原本側から空白の有無を確定できない（md 側には `?0.1` と `? 0.1` の両方の表記が存在するが、
       この差は判定に用いない）
     - **切り分けの手順（要素の有無によらず一意に決まる）**: 対象の文字列の先頭から、
       次の要素が**存在する場合にのみ**この順に取り除く。取り除き終えた残りが質問文部である。
       1. md 側のみ: 行頭の `#` の連なり（`##` 等）と、その直後の空白
       2. `?` / `？`（md 側）または ？アイコン（原本側）と、その直後の空白
       3. 番号（`N.M` 形式。`N` は数字または `A`〜`C`）と、その直後の空白
       **存在しない要素は読み飛ばし、その分だけプレフィックス部が短くなる。**
       たとえば md が `2.7 さっきの例題…`（`##` と `?` の両方が欠落）なら、
       プレフィックス部は `2.7 `、質問文部は `さっきの例題…` である。
       md が `## むずかしすぎて…`（番号が欠落）なら、プレフィックス部は `## `、
       質問文部は `むずかしすぎて…` である
     - **番号が欠落していても `D1`/`D4` の評価は行う**（比較範囲は上の手順で一意に決まるため）。
       番号の欠落自体は `D2` として記録する
     - 以降の規則2〜6は**質問文部にのみ**適用する
  2. **前処理（正規化）**: 原本の書き起こしと md の**質問文部**の双方に、次の正規化のみを施す。
     - N1: 連続する空白文字（半角空白・全角空白・タブ）を半角空白1つに畳む
     - N2: 文字列の前後の空白を除去する
     - N3: **これ以外の正規化は行わない**（約物・記号・かなの字体・全角半角の別はそのまま比較する）
  3. **数式範囲の表記規約（書き起こし時に適用する）**: 原本の書き起こしでは、
     **原本の紙面上で数式組版になっている範囲**（変数がイタリック体で組まれている、
     上付き・下付きがある、数学記号・演算子・分数・積分記号を含む）を `$…$` で囲んで記録する。
     この `$` は書き起こしの記法であり、**`$` 自体は比較の対象にしない**。
     これにより、原本側と md 側の双方で数式部分と地の文が同じ規約で切り分けられる
  4. **地の文の比較**: 質問文部のうち数式部分（`$…$` および `$$…$$` に囲まれた範囲）を除いた部分に
     ついて、正規化後の文字列を**文字単位で比較**する。1文字でも異なれば `D1` を立てる
  5. **数式部分の対応づけ**: 原本側の数式範囲（規則3 で `$…$` を付けた範囲）と md 側の数式範囲を、
     質問文部中の**出現順**で1対1に対応づける。**個数が異なる場合は、その時点で `D4` を立てる**
     （対応づけができないため、以降の要素比較は行わず、対応づかなかった範囲を備考に記す）
  6. **数式部分の比較**: 原本の数式は印刷された組版であり md は LaTeX であるため、文字単位で
     比較できない。代わりに、対応づいた範囲ごとに、**原本の数式に現れる記号・添字・上付き・演算子・
     括弧のそれぞれが、md の LaTeX の対応する要素と1対1に対応するか**を判定する。
     対応が取れない要素が1つでもあれば `D4` を立てる。
     **LaTeX の記法の違い（空白コマンド・`{}` の有無・`\cdot` と `·` の別など）だけで、
     対応が1対1に取れる場合は不一致としない**
  7. **体裁の比較（プレフィックス部）**: md 側のプレフィックス部に `##`・`?`・番号の
     **いずれかが欠けていれば** `D2` を立てる。**`?` と番号の間の空白の有無・量は `D2` の判定に用いない**
     （規則1）。原本側は74件すべてで ？アイコンと番号を持つことを目視で確認し、
     欠けている場合はその事実を備考に記す
  8. **ブロック構造の比較**: md 側で当該行が数式ブロック・コードブロック・HTML `div` などに
     取り込まれていれば `D3` を立てる
  9. **主判定の決定**: `D1`〜`D4` のいずれも立たなければ `P0`、1つ以上立てば `P1`、
     原本が判読できない、または該当領域が特定できない場合は `P9` とする（`P9` では内訳フラグを立てない）

- **受け入れ基準**:
  1. 74件すべてについて主判定が記録されていること（未判定 0 件）
  2. 主判定別件数（P0 / P1 / P9）の合計が **74** であること
  3. `P1` の各件に内訳フラグが1つ以上立っていること。`P0` と `P9` の各件に内訳フラグが立っていないこと
  4. `P9` が発生した場合、その理由が件ごとに記録されていること
  5. 判定に用いた原本 TIF ファイル名とページ内の位置（bbox）が件ごとに記録されていること
  6. `? 2.10`（chap02）について、原本が「**これ**ぜんぶ」であり md が「こぜんぶ」であることが
     **`P1`（内訳フラグ `D1`）**として記録されていること
     （既知の不一致。突合手順が実際に不一致を検出できることの確認を兼ねる）

### FR-005: 原本切り出し CLI（`scripts/crop_blocks.py`）の新設

- **機能名**: content_list の座標による原本 TIF の領域切り出し
- **概要**: content_list のブロック番号を指定して、そのブロックの `bbox`・`page_idx` から
  原本 TIF の該当領域を切り出し、PNG として保存する CLI を新設する。
- **入力（CLI 引数）**:
  - 位置引数1: content_list の JSON パス
  - 位置引数2: 原本 TIF のディレクトリ
  - `-o/--outdir`: 出力ディレクトリ（必須）
  - `--index`: 切り出すブロック番号（0 始まりの整数。複数指定可。**同じ番号を2回以上指定した場合はエラー**）
  - `--margin`: bbox の四方に加える余白。**0–1000 正規化単位**。既定 8。
    **`bool` を除く有限の数値（`math.isfinite` が真）で 0 以上**であること。`NaN` / `inf` はエラー
  - `--max-width`: 出力画像の最大幅（ピクセル）。超える場合は縦横比を保って縮小する。既定 1500。1 以上の整数
  - `--overwrite`: 既存ファイルを上書きする（指定しない場合、既存ファイルがあればエラーで終了）
- **出力**: `{outdir}/{content_list のファイル名の語幹}_b{index}_p{page_idx}.png`（グレースケール PNG）
- **受け入れ基準**:
  1. `--index` で指定したブロック番号の**個数と同数**の PNG が生成されること
     （重複指定はエラーとするため、指定個数＝ユニークな番号の個数＝生成枚数となる）
  2. 出力画像に、当該ブロックの文字が判読可能な状態で含まれること
     （検証は本案件の突合作業で実地に行う。合成データによる自動テストでは座標変換の正しさを検査する）
  3. 次のいずれかに該当する場合、**1件も出力せずに**エラーメッセージを標準エラーへ出力し、
     終了コード 1 で終了すること
     - 存在しないブロック番号を指定した
     - `--index` に同じ番号を2回以上指定した
     - 対象ブロックの `page_idx` が範囲外、または int でない
     - 対象ブロックの `bbox` が不正（欠落・長さが4でない・`bool` を含む・有限数値でない・0–1000 の範囲外・`x0 > x1` または `y0 > y1`）
     - `--margin` が `bool` である、有限数値でない、または負である
     - `--max-width` が 1 未満である
  4. `--overwrite` なしで出力先に同名ファイルが存在する場合、**1件も出力せずに**エラーで終了すること
  5. 原本 TIF・content_list・final のいずれも変更しないこと（読み取り専用）
  6. `uv run pytest -v` の全件が成功すること

### FR-006: 後続案件への引き渡し

- **機能名**: 不一致の型別集計と引き渡し
- **概要**: 突合で判明した不一致を判定区分・S 型で束ね、後続の修正案件に渡せる形にする。
- **入力**: FR-004 の記録
- **出力**: 要約（`collation_summary.md`）内の「後続案件への引き渡し」節。
  区分ごとに「件数・該当する章と番号・feat-020 のスコープに含まれるか否か」を記す。
- **受け入れ基準**:
  1. 不一致の全件について、feat-020 のスコープ（19件）に含まれるか否かが判定されていること
  2. feat-020 のスコープ外の不一致が1件以上ある場合、それらを束ねた後続案件の起票案
     （案件名・対象件数・対象の章と番号）が記されていること
  3. 本案件では後続案件の起票を行わない（起票の可否はユーザーが判断する）

## 1.4 非機能要求

### NFR-001: データ不変性（最重要）

本案件は**読み取りのみ**を行う。以下を一切変更しない。

- `{BASE2}/dewarping/` 配下の原本 TIF（全383枚）
- `{BASE2}/ocr/final/` 配下の md・content_list.json・images/（全10章）
- `{BASE2}/ocr/fixes/` 配下の修正定義ファイル
- `{BASE2}/ocr/mineru-full/` 配下の中間成果物

**検証方法**: 突合作業の前後で、上記4ディレクトリ配下の全ファイルの SHA-256 一覧を取得し、
完全一致することを確認する（差分 0 件）。

### NFR-002: 処理時間

- `scripts/crop_blocks.py` の1回の実行（1章分・最大12ブロック）は **60 秒以内**に完了すること
  （原本 TIF は1枚あたり最大約13MB・約4500×5500 ピクセル。同一ページの複数ブロックを切り出す場合、
  TIF の読み込みはページ単位でキャッシュして再読み込みしないこと）
- 突合作業全体（74件）の所要時間には要求を設けない

### NFR-003: 対応環境

- Python 3.12（`.python-version` で固定済み）
- GPU 不要。MinerU の再実行を行わない
- ネットワーク不要（プロキシ設定に依存しない）

### NFR-004: 信頼性

- `scripts/crop_blocks.py` は、入力の検証をすべて済ませてから出力を開始する
  （検証で1件でもエラーがあれば、1件も出力しない。`colorize_images.py` と同じ方針）
- 突合作業が中断した場合、詳細記録（FR-004）に記録済みの件はやり直さずに再開できること
  （記録は1件ずつ追記可能な形式とする）
