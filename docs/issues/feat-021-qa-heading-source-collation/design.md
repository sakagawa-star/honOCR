## 5. `scripts/crop_blocks.py` の詳細設計（FR-005）

### 5.1 目的と位置づけ

content_list のブロック番号から、原本 TIF の該当領域を PNG として切り出す。
原本 TIF は Read ツールで直接開けない（TIF 非対応）ため、**原本を目視するための唯一の手段**である。

`colorize_images.py` は `img_path` を持つ図ブロックしか扱えず、本案件が対象とする
テキスト・数式・コードのブロックを切り出せない。そのため新規に設ける（§9 ADR-4）。

### 5.2 データフロー

| 段階 | データ | 型・形式・値域 |
|---|---|---|
| 入力1 | content_list JSON | ファイル。トップレベルは配列。各要素は dict で `bbox`（長さ4の数値配列・0–1000）と `page_idx`（int・0 始まり）を持つ |
| 入力2 | 原本 TIF ディレクトリ | ディレクトリ。`page-*_1L.tif` と `page-*_2R.tif` を含む |
| 入力3 | `--index` | int の並び（0 始まり・順不同）。1個以上必須。**重複はエラー** |
| 入力4 | `--margin` | float。0–1000 正規化単位。既定 `8`。**`bool` を除く有限数値で 0 以上**（負値・`NaN`・`inf` はエラー） |
| 入力5 | `--max-width` | int。1 以上。既定 `1500`（0 以下はエラー） |
| 中間 | TIF 画像 | `PIL.Image`。ページ単位でキャッシュする（NFR-002） |
| 中間 | ピクセル座標 | `(px0, py0, px1, py1)`。int。0 ≤ 値 ≤ 画像の幅/高さ |
| 出力 | PNG ファイル | グレースケール（mode `L`）。`{outdir}/{stem}_b{index}_p{page_idx}.png` |

`{stem}` は content_list のファイル名から拡張子を除いたもの
（例: `chap02_gray300_content_list.json` → `chap02_gray300_content_list`）。

### 5.3 処理ロジック

```
1. CLI 引数を解析する
2. content_list を読み込む
   - トップレベルが配列でなければエラー
3. TIF を列挙する: list_tifs(dir)
   - glob("page-*_1L.tif") と glob("page-*_2R.tif") を連結し、ファイル名の辞書順でソートする
   - colorize_images.py の list_tifs と同一（ADR-2）
   - 0 枚ならエラー
4. 【検証フェーズ】すべての --index について次を検査し、エラーを全件集めてから判定する
   4-0. --index に同じ番号が2回以上現れていないか（重複はエラー）
   4-1. 0 <= index < len(content_list) か
   4-2. ブロックが bbox を持ち、長さ4の配列で、各値が【bool でない有限数値】（math.isfinite が真）
        かつ 0 <= 値 <= 1000 か
   4-3. x0 <= x1 かつ y0 <= y1 か
   4-4. ブロックが page_idx を持ち、【bool でない】int で 0 <= page_idx < len(tifs) か
   4-5. --margin が【bool でない有限数値】かつ 0 以上か、--max-width が【bool でない】int で 1 以上か
   4-6. 出力先パスが既存で、--overwrite が指定されていないか
   → エラーが1件でもあれば、全件を標準エラーへ出力し、【1件も出力せずに】終了コード 1 で終了する
5. 出力ディレクトリを作成する（mkdir -p 相当）
6. 各 --index について（指定順）:
   6-1. page_idx の TIF をキャッシュから取得（無ければ Image.open してキャッシュに入れる）
   6-2. margin を bbox に加える: [x0-m, y0-m, x1+m, y1+m]（m = --margin）
   6-3. bbox_to_pixels() でピクセル座標へ変換（round → 0..幅/高さ にクランプ）
   6-4. crop する。幅または高さが 0 になった場合は 1 ピクセルに切り上げる
   6-5. 幅 > --max-width なら、縦横比を保って LANCZOS で縮小する
        新しい高さ = max(1, round(高さ * max_width / 幅))
   6-6. convert("L") でグレースケール化し、PNG で保存する
7. 生成枚数を標準出力へ出力し、終了コード 0 で終了する
```

**ループの終了条件**: `--index` で指定された件数を処理し終えたとき。

**条件分岐の網羅**:
- 検証エラーあり → 出力なし・終了コード 1
- 検証エラーなし・幅 ≤ max-width → 縮小せず保存
- 検証エラーなし・幅 > max-width → 縮小して保存
- 同一 index が重複指定された場合 → **検証フェーズ 4-0 でエラー**（出力なし・終了コード 1）。
  重複を許すと出力パスが衝突し、指定個数と生成枚数が一致しなくなるため（ADR-8）

### 5.4 座標変換（`colorize_images.py` と同一）

```python
BBOX_SCALE = 1000

def bbox_to_pixels(bbox, size):
    w, h = size
    x0, y0, x1, y1 = bbox
    px0 = max(0, min(round(x0 / BBOX_SCALE * w), w))
    py0 = max(0, min(round(y0 / BBOX_SCALE * h), h))
    px1 = max(0, min(round(x1 / BBOX_SCALE * w), w))
    py1 = max(0, min(round(y1 / BBOX_SCALE * h), h))
    return px0, py0, px1, py1
```

上のコードは意図の伝達が目的であり、そのままコピーして使うものではない
（`colorize_images.py` の同名関数と同じ式である、という指定である）。

**TIF のページキャッシュ**（NFR-002）: `dict[int, Image.Image]` に `page_idx` をキーとして保持し、
同一ページの複数ブロックを切り出す際に `Image.open` を繰り返さない。

### 5.5 エラーハンドリング

| 想定エラー | 検出方法 | 処理 |
|---|---|---|
| content_list が存在しない／JSON として壊れている | `json.load` の例外 | メッセージを標準エラーへ出し、終了コード 1 |
| content_list のトップレベルが配列でない | `isinstance(data, list)` | 同上 |
| TIF ディレクトリが存在しない／TIF が 0 枚 | `list_tifs` の結果が空 | 同上 |
| `--index` に重複がある | §5.3 の 4-0 | 検証フェーズで全件収集し、出力なしで終了コード 1 |
| `--index` が範囲外 | §5.3 の 4-1 | 同上 |
| `bbox` が不正（欠落・長さ違い・非数値・`bool`・`NaN`・`inf`・範囲外・順序逆転） | §5.3 の 4-2, 4-3 | 同上 |
| `page_idx` が不正（欠落・非 int・`bool`・範囲外） | §5.3 の 4-4 | 同上 |
| `--margin` が `bool`／`NaN`／`inf`／負、`--max-width` が `bool`／0 以下 | §5.3 の 4-5 | 同上 |
| 出力先に同名ファイルがあり `--overwrite` なし | §5.3 の 4-6 | 同上 |
| TIF の読み込み・保存に失敗 | `Image.open` / `save` の例外 | メッセージを標準エラーへ出し、終了コード 1（途中まで生成されたファイルは削除しない） |

**ログ出力**: 本スクリプトは `logging` を使わない（`colorize_images.py` と同じ方針）。
- 正常時: 標準出力に `wrote {n} file(s) to {outdir}` の1行
- 異常時: 標準エラーに1行1エラーで列挙し、終了コード 1

### 5.6 境界条件

| 条件 | 振る舞い |
|---|---|
| `--index` が 1 個 | 1 枚出力する |
| content_list が空配列 | すべての `--index` が範囲外となりエラー（終了コード 1） |
| bbox が `[0,0,0,0]` | 幅・高さが 0 になるため 6-4 で 1 ピクセルに切り上げて出力する（エラーにしない） |
| bbox が `[0,0,1000,1000]` | ページ全体を切り出す。`--max-width` で縮小される |
| margin を加えるとページ外へ出る | `bbox_to_pixels` のクランプで page 内に収まる |
| 出力先ディレクトリが存在しない | 作成する（親も含めて） |
| 出力先が既存のファイル（ディレクトリでない） | `mkdir` が失敗し、例外メッセージを出して終了コード 1 |
| 切り出し後の幅が `--max-width` ちょうど | 縮小しない（`>` で判定する） |
| `--margin` が `0` | bbox をそのまま使う（エラーにしない） |
| `--margin` が `NaN` / `inf`、bbox に `NaN` / `inf` が含まれる | 検証フェーズでエラー（出力なし・終了コード 1）。`math.isfinite` で判定する |
| `--index` に同じ番号が2回以上 | 検証フェーズでエラー（出力なし・終了コード 1） |

## 6. 突合の実施手順（FR-003）

### 6.1 実施者

**Claude Code 本体が行う**（Sonnet サブエージェントに委任しない。§9 ADR-5）。
原本画像の目視と文字列の照合という視覚判断を伴うためである。

**`scripts/crop_blocks.py` と `tests/test_crop_blocks.py` の実装だけは、
`CLAUDE.md`「実装の実行方法（Sonnetサブエージェント）」に従い Sonnet サブエージェントに委任する。**

### 6.2 章ごとの手順（chap00 → chap09 の順に、1章ずつ完了させる）

1. **切り出し**: 当該章の Q&A 見出しブロック（§4.1 の表の `block` 列）を `--index` に列挙して
   `crop_blocks.py` を実行し、スクラッチパッド配下（`{S}/crops/{章}/`）に PNG を出力する
2. **目視**: 出力された PNG を Read ツールで開き、**原本に印刷されている質問文を書き起こす**
   （番号・`？` アイコンの有無・記号・空白も含めて、見えたままを記録する）。
   このとき、**原本の紙面上で数式組版になっている範囲**（変数がイタリック体で組まれている、
   上付き・下付きがある、数学記号・演算子・分数・積分記号を含む）を **`$…$` で囲んで**記録する
   （`requirements.md` FR-003 比較規則の規則3）。この `$` は書き起こしの記法であり、
   **`$` 自体は比較の対象にしない**。数式が無い質問文には `$` を書かない
3. **md の該当行の取得**: 当該章の md から、その番号の行を取得する
   （`grep -n` で番号を検索する。§4.1 の md 上の型に応じて、行頭・ブロック内のいずれかにある）
4. **照合**: 書き起こしと md の文字列を `requirements.md` FR-003 の比較規則で照合する。
   **プレフィックス部（`##`・`?`・番号とその周辺の空白）は体裁（`D2`）でのみ判定し、
   文字単位の比較は質問文部にのみ行う**（§6.3 手順1）。照合の結果、
   **主判定**（P0 一致 / P1 不一致 / P9 判定不能）を1つ与える。P1 の場合は
   **内訳フラグ**（D1 地の文の文字 / D2 体裁 / D3 ブロック構造 / D4 数式）を1つ以上立てる。手順は §6.3
5. **記録**: §7.1 の詳細記録に1件ずつ追記する
6. 当該章の全件が済んだら、次の章へ進む

### 6.3 判定の手順

`requirements.md` FR-003 の**比較規則**をそのまま適用する。手順は次のとおりで、実施者の裁量を残さない。

1. **見出しの切り分け**: 原本側・md 側とも、**プレフィックス部**（md: 行頭の `##`・`?`・番号と
   その間および番号直後の空白 / 原本: ？アイコン・番号と同様の空白）と、**質問文部**
   （番号より後ろの全体）に分ける。
   **プレフィックス部は手順6（`D2`）でのみ判定し、文字単位の比較（`D1`）の対象にしない。**
   **プレフィックス部の空白の有無・量は判定しない**（原本の「？」は装飾アイコンであり、
   アイコンと番号の間の隙間は空白文字ではないため、原本側から空白の有無を確定できない）。
   **切り分けは、対象文字列の先頭から次の要素を「存在する場合にのみ」この順に取り除いて行う**
   （残りが質問文部）: (a) md 側のみ `#` の連なりとその直後の空白、(b) `?` / `？` または
   ？アイコンとその直後の空白、(c) 番号（`N.M`）とその直後の空白。
   **存在しない要素は読み飛ばす**ため、`##` や `?` や番号が欠落していても境界は一意に決まる
   （例: md が `2.7 さっきの例題…` ならプレフィックス部は `2.7 `、質問文部は `さっきの例題…`。
   md が `## むずかしすぎて…` ならプレフィックス部は `## `、質問文部は `むずかしすぎて…`）。
   **番号が欠落していても `D1`/`D4` の評価は行い**、番号の欠落自体は `D2` として記録する。
   以降の手順2〜5は**質問文部にのみ**適用する
2. **正規化**: 原本の書き起こしと md の**質問文部**の双方に、N1（連続空白を半角空白1つに畳む）と
   N2（前後の空白を除去）のみを施す。**N3: それ以外の正規化は行わない**
3. **数式部分の切り分け**: 質問文部のうち、原本側・md 側とも `$…$` および `$$…$$` に囲まれた範囲を
   数式部分、それ以外を地の文とする。**原本側の `$` は §6.2 手順2 の書き起こし規約で付けたもの**であり、
   区切り記号 `$` 自体は比較しない
4. **地の文の比較**: 正規化後の文字列を**文字単位で比較**する。1文字でも異なれば **`D1`** を立てる
5. **数式部分の対応づけと比較**: 原本側と md 側の数式範囲を**出現順で1対1に対応づける**。
   **個数が異なれば、その時点で `D4`** を立て（要素比較は行わない）、対応づかなかった範囲を備考に記す。
   対応づいた範囲ごとに、原本の数式に現れる記号・添字・上付き・演算子・括弧のそれぞれが、
   md の LaTeX の対応する要素と**1対1に対応するか**を判定する。対応が取れない要素が
   1つでもあれば **`D4`** を立てる。LaTeX の記法の違いだけで対応が1対1に取れる場合は
   不一致としない（例: `\cdot` と `·`、`{}` の有無、`\,` などの空白コマンド）
6. **体裁の比較（プレフィックス部）**: md 側のプレフィックス部に `##`・`?`・番号の
   **いずれかが欠けていれば** **`D2`** を立てる。**`?` と番号の間の空白の有無・量は判定に用いない**。
   原本側に ？アイコンまたは番号が欠けている場合は、その事実を備考に記す
7. **ブロック構造の比較**: md 側で当該行が数式ブロック・コードブロック・HTML `div` などに
   取り込まれていれば **`D3`** を立てる
8. **主判定の決定**:
   - `D1`〜`D4` がいずれも立たない → **`P0`**
   - `D1`〜`D4` が1つ以上立つ → **`P1`**（立てたフラグをすべて記録する）
   - 原本が判読できない、または該当領域が特定できない → **`P9`**（内訳フラグは立てない。理由を備考に記す）

**主判定は排他であり、1件にちょうど1つだけ与える**（P0 / P1 / P9 の件数の合計は必ず 74）。
**内訳フラグは1件に複数立ちうる**（例: `?` が欠落し、かつ誤読もある場合は `D1` と `D2` の両方）。
そのためフラグ別件数の合計は P1 の件数と一致しない。要約では両者を別々に集計する（§7.2）。

`P9` は突合が完了していないことを意味するため、要約で件数と理由を明示する。

### 6.4 中断と再開

詳細記録（§7.1）は1件1行の表であり、処理済みの行がそのまま進捗を表す。
中断した場合は、記録済みの最後の番号の次から再開する。

md は「こぜんぶ覚えないといけませんか？」である**（「れ」が1文字脱落。設計時に原本

## 9. 設計判断の記録（ADR）

### ADR-1: 74件の特定は md ではなく content_list を基準にする

- **採用**: content_list の全ブロックを走査し、`type`・`text_level`・`bbox`・`page_idx` で特定する
- **却下: md の行頭正規表現で走査する** — feat-014 は `^(## )?N\.M[ 　]` で走査して19件を
  取りこぼし、feat-020 は行頭走査のため chap04 4.6 をコードブロック内と気づかず β型に分類した。
  md の行頭は、ブロックの種類（数式・コード・HTML div）に取り込まれた見出しを表現できない
- **利点**: content_list は全ブロックを保持し、`bbox` と `page_idx` を持つため、

- **留意点**: `apply_fixes.py` は md のみを対象とするため、feat-014 で修正した3件は

### ADR-2: TIF の列挙は `colorize_images.py` と同じファイル名の辞書順にする

- **採用**: `page-*_1L.tif` と `page-*_2R.tif` を連結してファイル名の辞書順でソートし、

### ADR-3: 詳細記録はリポジトリ外、要約はリポジトリ内に置く

### ADR-4: `colorize_images.py` を拡張せず、新規スクリプトを設ける

### ADR-5: 突合の実施は Claude Code 本体が行う

- **採用**: `crop_blocks.py` の実装のみ Sonnet サブエージェントに委任し、

### ADR-6: 出力は PNG グレースケールにする

- **却下: JPEG** — 非可逆圧縮のノイズが文字の判読を妨げうる。`colorize_images.py` が

- **却下: RGB** — 原本の大半がグレースケール（`L`）であり、質問文の突合に色情報は不要。

### ADR-7: 「実験・検証の進め方（予測→実行→照合）」は適用しない

- **判断**: 本案件は `CLAUDE.md`「実験・検証の進め方」の対象外とし、
  criteria 文書の作成と criteria lock を行わない
- **理由**: 同節が対象とするのは「数値判定を伴う実験・検証」であり、閾値や合格ラインを

  実験の合否を分ける閾値ではない
- **却下: 念のため criteria 文書を作る** — 測るべき未知の量が無いため、
  criteria 文書は本書の受け入れ基準の写しになる。二重管理になり、更新漏れの原因になる
- **この判断はレビューで検証されるべき論点である**（Codex レビューで否定された場合は、
  criteria 文書を作成して criteria lock を行ってから実施する）

### ADR-8: 主判定を排他の3区分にし、不一致の内訳を別のフラグに分ける

- **採用**: 主判定 `P0`（一致）/ `P1`（不一致）/ `P9`（判定不能）を排他の1区分とし（合計 74）、
  不一致の内訳 `D1`〜`D4` を複数立てられるフラグとして別に持つ
- **却下: 単一の区分に「複数該当する場合はすべて記録する」を許す** —
  区分が排他でなくなるため「区分別件数の合計が 74」という受け入れ基準が成立しない。
  1件が「文字の不一致」かつ「体裁の不一致」であることは実際に起こりうる（feat-020 のα型は
  体裁の欠落であり、そこに誤読が重なる可能性がある）ため、複数記録の要求自体は落とせない
- **却下: 区分を優先順位で1つに丸める（例: 体裁 > 文字）** — 丸めた側の情報が失われ、
  後続案件が修正定義を作るときに詳細記録を読み直すことになる

### ADR-9: 数式部分は文字単位で比較せず、要素の1対1対応で判定する

- **採用**: 質問文を数式部分（`$…$` / `$$…$$`）と地の文に分け、地の文は正規化後の文字単位比較、
  数式部分は「記号・添字・上付き・演算子・括弧の1対1対応」で判定する（`D4`）
- **理由**: 原本の数式は**印刷された組版**であり md は **LaTeX** であるため、
  文字単位の比較は原理的に成立しない。同じ式が `\cdot` と `·`、`{}` の有無、空白コマンドの有無で
  複数の書き方を持つため、文字列一致を要求すると正しい OCR 結果まで不一致になる
- **却下: 数式部分を突合の対象から外す** — 数式内の添字の誤りは実際に起きうる誤りであり
  （`docs/PROJECT_KNOWLEDGE.md`: MinerU の内部処理は 200dpi 相当で頭打ちのため添字の認識が弱い）、
  対象外にすると突合の価値が下がる。ユーザー決定「突合の粒度は質問文の全文」にも反する
- **却下: 「意味が同じなら一致」とする** — 主観的で、実施者によって結論が変わる
  （`docs/REQUIREMENTS_STANDARD.md` 2.3 が禁じる主観的表現に当たる）
- **数式範囲の切り分け**: 原本は紙面であり `$` の区切りを持たないため、
  **書き起こしの時点で数式組版の範囲を `$…$` で囲む規約**を置く（§6.2 手順2）。
  これにより原本側と md 側が同じ規約で切り分けられ、「どこを数式として扱うか」が
  実施者の判断に委ねられなくなる。原本側と md 側で数式範囲の**個数が異なる場合は
  それ自体を `D4`** とする（対応づけができないことは不一致の一種である）

### ADR-10: 見出しをプレフィックス部と質問文部に分け、文字単位比較は質問文部だけに行う

- **採用**: 見出しを**プレフィックス部**（`##`・`?`・番号とその周辺の空白）と**質問文部**
  （番号より後ろ）に分け、`D1`（文字の不一致）と `D4`（数式の不一致）の判定は質問文部にのみ行う。
  プレフィックス部は `D2`（体裁）でのみ判定し、**その中の空白の有無・量は判定しない**
- **経緯**: 実装フェーズ（2026-09-03）の chap00 の突合で、当初の比較規則が**実行不能**であることが
  判明した。(1) md 側の `## ` は Markdown の記法であって原本の紙面に存在しないため、
  見出し全体を文字単位で比較すると**74件すべてで `D1` が立ち判定が成立しない**。
  (2) md には `?0.1`（空白なし・8件）と `? 0.3`（空白あり・47件）が混在するが、原本の「？」は
  装飾アイコンであり、アイコンと番号の間の隙間は空白文字ではないため、**原本側から空白の有無を
  確定できない**。この2点は当初の規則に規定が無く、実行時に規則を作らざるを得ない状態だった
  （`docs/DESIGN_STANDARD.md` 2.2「実装判断ゼロの原則」に反する）
- **却下: 見出し全体を文字単位で比較し、`## ` だけを除外する** — `?` と番号の間の空白の問題が残る。
  原本側から確定できない差で `D1` を立てると、実施者の裁量が入る
- **却下: `?N.M` と `? N.M` の表記ゆれも `D2` として不一致に数える** — 原本側で空白の有無を
  確定できない以上、不一致の根拠が示せない。なお feat-014 はこの表記ゆれをスコープ外としており、
  本案件で扱わないことは既存の判断とも整合する
- **番号欠落時の境界**: プレフィックス部の3要素（`#` の連なり・`?`・番号）は
  **存在するものだけを先頭から順に取り除く**規則としたため、いずれが欠落していても
  質問文部の境界は一意に決まる。したがって体裁の欠落（`D2`）と質問文の誤読（`D1`）が
  併発しても判定は実施者に依存しない
- **維持されるもの**: ユーザー決定「突合の粒度は質問文の全文」は、質問文部の全文を
  文字単位で比較することで満たされる（`? 2.10` の「こぜんぶ」←「これぜんぶ」は質問文部にあるため
  `D1` として検出される）
