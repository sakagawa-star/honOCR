## 指摘

### 高-1: `apply_fixes.py` の失敗／適用件数不一致時に復元手順がない

**指摘内容**（原文の要旨）:

> `design.md` の手順2（`apply_fixes.py` の実行）および §9 のエラーハンドリング表は「中断のみ」を
> 指示しているが、その時点で修正定義 JSON は追記済みである。次回の事前 SHA-256 照合が必ず失敗し、
> 要求された「章失敗時は当該章を退避から復元」とも矛盾する。

**修正案**（原文の要旨）:

> `apply_fixes.py` の非0終了、または `applied` / `skipped` 不一致の場合にも、
> `{NORM_NN}` の md・`{FINAL_NN}`・修正定義ファイルの3点を退避から復元し、
> 事前確認が再度 OK になることを確認して中断する手順を追加すること。

**判定: 妥当。** 手順1 で修正定義ファイルへの追記を済ませてから手順2 を実行する設計であるため、
手順2 の失敗時に追記を戻さないと、次回の手順1 の SHA-256 照合（§4.1）で必ず中断し再開できない。
また `applied` / `skipped` の不一致は終了コード 0（md は書き換わっている）で起きるため、
md も併せて復元する必要がある。

## 反映内容（本レビュー後に実施）

`design.md` を次のとおり修正した。

1. **手順3 固有だった「失敗時の復元」を、手順1〜手順3 に共通する独立節へ格上げ**
   （`#### 失敗時の復元（{FINAL_NN} の部分更新への対処）` → `### 失敗時の復元（手順1〜手順3 に共通）`）。
   発動条件の表（手順1 / 手順2 / 手順3 のそれぞれで何が起きたら発動するか）と、
   「その章について既に書き換えた対象だけを戻せばよい」旨を追加
2. **手順2 に復元への明示的な指示を追加**（終了コード 0 以外、または `applied` / `skipped` 不一致の
   場合に3点を復元してから中断・報告する。修正定義ファイルが追記済みであるため復元が必須である
   理由も明記）
3. **§9 エラーハンドリング表の8行を更新**（`old` が2件以上 / `old` も `new` も0件 /
   適用後に `new` が2件以上 / 既存 fix が最終不変条件に違反 / `applied`・`skipped` 不一致 /
   JSON 不正 / `APPEND_OK` 失敗 / `build_final.py` 失敗）。いずれも「§6「失敗時の復元」に従い
   復元してから中断・報告する」に統一
4. **§10（サブエージェントへの委任指示）の記載を「手順1〜手順3 のいずれかが期待どおりに
   終わらなかった場合」に一般化**
