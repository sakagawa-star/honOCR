# feat-022 要求仕様書: Q&A コラム見出しの語彙誤読4件の修正

## 1. プロジェクト概要

### 何を作るのか

『プログラミングのための確率統計』の既存の修正定義ファイル4件
（`{BASE2}/ocr/fixes/chap01.json`・`chap02.json`・`chap03.json`・`chap08.json`。いずれも作成済み・
リポジトリ外）に修正を**各1件ずつ計4件追記**し、`apply_fixes.py`（feat-010）で既存成果物に
適用したうえで、`build_final.py`（feat-012）で `final/chap01/`・`final/chap02/`・`final/chap03/`・
`final/chap08/` を再構築する。

**リポジトリ内のコード（`scripts/`）とテストコード（`tests/test_*.py`）は一切変更しない。**
本案件で作成・更新する成果物は次の3つに限られる。

1. リポジトリ外の修正定義ファイル4件（`{BASE2}/ocr/fixes/chap01.json`・`chap02.json`・
   `chap03.json`・`chap08.json` への各1件の追記）
2. それを適用したリポジトリ外の既存成果物（4章の `{NORM_NN}/` と `{FINAL_NN}/`）
3. リポジトリ内の案件ドキュメント（`docs/issues/feat-022-qa-heading-vocab-misread/`）、
   `docs/BACKLOG.md` / `docs/CHANGELOG.md` / `docs/PROJECT_KNOWLEDGE.md` の完了処理、および
   テスト結果の記録 `tests/results/feat-022_test_result.txt`（新規作成。
   CLAUDE.md「テスト」のルールで必須）

**`CLAUDE.md` は更新しない**（update-003 で確定した非対称ルール: CLAUDE.md 本体の変更は
update 案件でのみ行う）。`docs/PROJECT_KNOWLEDGE.md` の更新要否は機能設計書 §11 で定める。

### なぜ作るのか

feat-021（Q&A コラム見出し全74件の原本突合）により、見出しの質問文に**語彙単位の誤読が4件**
あることが確定した（案件 README.md §3）。

| 章 | 番号 | 原本 | md（誤） |
|---|---|---|---|
| chap01 | 1.8 | 描いたら**いい**んでしたっけ | 描いたら**い**んでしたっけ |
| chap02 | 2.10 | **これ**ぜんぶ | **こ**ぜんぶ |
| chap03 | 3.5 | 賭け**ろ**ということ | 賭け**る**ということ |
| chap08 | 8.6 | そういうことだ**ろ**？ | そういうことだ**る**？ |

誤読を残すことは本プロジェクトのゴール「入力への忠実な OCR」に反するため、修正する。
4件はいずれも読み手の理解を妨げる（1.8・2.10 は語が崩れて非文になり、3.5・8.6 は
命令形・終助詞が別語に変わって文意が通らなくなる）。

### 誰が使うのか

本プロジェクトのユーザー。成果物（`{BASE2}/ocr/final/chapNN/chapNN_gray300.md`）を
LLM に読ませて学習に用いる。

### どこで使うのか

`docs/TECH_STACK.md` に定義された既存環境（Ubuntu 24 系 / Python 3.12.3 / uv）。
新規のライブラリ・モデル・ネットワークアクセスは追加しない。

## 2. 用語定義

feat-010・feat-013・feat-016・feat-017・feat-019 の要求仕様書の用語を継承する。
本書で用いる主な用語は次のとおり。

| 用語 | 定義 |
|---|---|
| 修正定義ファイル | OCR 誤りを「修正前文字列（`old`）→ 修正後文字列（`new`）」のペアで記録した JSON。`{BASE2}/ocr/fixes/{name}.json` に置く。書籍本文を含むためリポジトリに置かない（feat-010） |
| 語彙単位の誤り | 1文字の字形置換では表現できず、複数文字の並びとしてのみ判定できる誤り。本件の4件がこれにあたる |
| 最終不変条件 | `apply_fixes.py` が適用後に検査する条件。**全 fix について `count(old) == 0` かつ `count(new) == 1`**。1つでも破れると出力を書かずにエラー終了する（feat-010 FR-003 規則6） |
| 再適用 | 既に構築済みの成果物（`run-NN-normalized/` と `final/`）に対し、MinerU を再実行せずに修正適用・final 再構築のみを行うこと（feat-013 §2） |
| Q&A コラム見出し | 『プログラミングのための確率統計』の各章にある質問形式のコラムの見出し。全10章で74件ある（feat-021） |
| `D1` / `D2` | feat-021 の突合で用いた内訳フラグ。`D1` = 質問文部の地の文の文字の不一致、`D2` = 見出し体裁の不一致（`##`・`?`・番号の欠落） |
| `{BASE}` | `/home/sakagawa/work/Pattern_Recognition_and_Machine_Learning`（PRML。git 管理外・リポジトリ外） |
| `{BASE2}` | `/home/sakagawa/work/確率統計`（git 管理外・リポジトリ外） |
| `{NORM_NN}` | `{BASE2}/ocr/mineru-full/chapNN/run-01-normalized`（chapNN の正規化済みディレクトリ。NN ∈ {01, 02, 03, 08}） |
| `{FINAL_NN}` | `{BASE2}/ocr/final/chapNN`（chapNN の最終成果物ディレクトリ。NN ∈ {01, 02, 03, 08}） |
| 対象4章 | chap01・chap02・chap03・chap08。本案件で変更する章 |
| 非対象6章 | chap00・chap04・chap05・chap06・chap07・chap09。確率統計のうち本案件で変更しない章 |

## 3. 機能要求一覧

### FR-001: 修正定義ファイル4件への修正追記

- **機能名**: `{BASE2}/ocr/fixes/chap01.json`・`chap02.json`・`chap03.json`・`chap08.json` への
  修正各1件（計4件）の追記
- **概要**: 4件の誤読を `fixes/template.json` の書式に従って定義し、
  各ファイルの既存 fix の後ろに1件ずつ追記する
- **入力**: 案件 README.md §3・§6 で確定した誤り箇所（4箇所）
- **出力**: 上記4ファイル（既存ファイルの更新。UTF-8・JSON）
- **受け入れ基準**:
  1. `fixes/README.md`・`fixes/template.json` の書式に従い、`id` / `reason` / `old` / `new` の
     4キーをすべて文字列で持つ fix が**各ファイルに1件ずつ追加**され、追記後の `fixes` 配列の
     要素数が chap01 = **3**（既存2＋新規1）、chap02 = **5**（既存4＋新規1）、
     chap03 = **7**（既存6＋新規1）、chap08 = **2**（既存1＋新規1）になる
  2. 新規 fix の `id` は `chap01-003` / `chap02-005` / `chap03-007` / `chap08-002` とする
     （各ファイルの既存 ID の最大値 + 1）
  3. 既存の fix（chap01-001・002、chap02-001〜004、chap03-001〜006、chap08-001 の計13件）の
     `id` / `reason` / `old` / `new` を1文字も変更しない
  4. `apply_fixes.py` の `validate_fixes` が4ファイルとも エラーを1件も出さない
  5. 適用**前**の各 `{NORM_NN}/chapNN_gray300.md` において、新規 fix の `count(old) == 1` である
  6. 適用**後**の各 `{NORM_NN}/chapNN_gray300.md` において、当該章の**全 fix** について
     `count(old) == 0` かつ `count(new) == 1` である（最終不変条件）
  7. 各 `reason` に、原本 TIF で確認済みであることと、`old` / `new` を一意にするために
     文脈を含めた理由を日本語で記述する
  8. ファイルはリポジトリに置かず、コミットもしない（feat-010 の運用）

### FR-002: 語彙誤読4件の訂正

- **機能名**: 4章の md における語彙誤読の訂正
- **概要**: 案件 README.md §3 の4箇所を訂正する
- **入力**: 各 `{NORM_NN}/chapNN_gray300.md`（適用前）
- **出力**: 同（適用後）
- **受け入れ基準**:
  1. 適用後の各 md における次の**誤読文字列の出現回数が 0** である（適用前はいずれも 1）:
     `描いたらいんでしたっけ`（chap01）/ `こぜんぶ覚えない`（chap02）/
     `賭けるということですよね`（chap03）/ `そういうことだる`（chap08）
  2. 適用後の各 md における次の**訂正後文字列の出現回数が 1** である（適用前はいずれも 0）:
     `描いたらいいんでしたっけ`（chap01）/ `これぜんぶ覚えない`（chap02）/
     `賭けろということですよね`（chap03）/ `そういうことだろ`（chap08）
  3. 件数はすべて Python の `str.count()` による**出現回数**で数える。
     `apply_fixes.py` の不変条件と同じ数え方であり、行数ではない。**`grep -c` を使わない**
  4. 適用後の各 md の該当行が、次の文字列を含む（行番号は適用前後で変わらない）:

     | 章 | 行 | 含むべき文字列 |
     |---|---|---|
     | chap01 | 298 | `どんなやり方で描いたらいいんでしたっけ` |
     | chap02 | 1395 | `2.10 これぜんぶ覚えないといけませんか` |
     | chap03 | 585 | `期待値の高いほうに賭けろということですよね` |
     | chap08 | 520 | `高い。そういうことだろ` |

  5. 確率統計の final 全10章の md に対し、案件 README.md §5 と同じ4本の正規表現
     （`.{6}でしたっけ` / `.{4}ぜんぶ` / `賭け.{0,4}` / `.{4}だ[るろ]`）で抽出した出現形の集計が、
     適用前の集計から**本案件の4件の変化のみ**を示す（他の出現形の件数が変わらない）

- **受け入れ基準**:
  1. `apply_fixes.py` の終了コードが4章とも 0 で、`applied` / `skipped` が次のとおりである

  5. 適用前後の `diff` の差分ハンクが各章とも **1つ**のみであり、FR-002 基準4 の行の
     1箇所の変更だけである。他の行に差分があってはならない
  6. 各 `{FINAL_NN}/` の md・content_list.json が対応する `{NORM_NN}/` とバイト同一である
  7. 各 `{FINAL_NN}/images/` のファイル数が変わらない

  8. 各 `{NORM_NN}/chapNN_gray300_content_list.json` は**変更されない**

## 4. 非機能要求

| 項目 | 要求 |
|---|---|
| 性能 | 再適用は対象4章のみ・MinerU 再実行なしのため、全工程（4章分の apply_fixes + build_final）が 120 秒以内に完了する |
| 再現性 | `apply_fixes.py` は冪等である（2回目以降の実行では `old` 不在・`new` 1件のため `skipped` として扱われ、終了コード 0・内容不変） |
| 可搬性 | 修正定義ファイルは書籍本文を含むためリポジトリ外に置く。リポジトリ側には書式テンプレート（`fixes/template.json`）のみを保持する（feat-010 の既存方針） |

| 原子性 | 章単位で適用する。ある章で失敗した場合、**その章のみ**を退避から復元し、残りの章には進まない（機能設計書 §6 手順3） |

## 5. 制約条件

- **MinerU を再実行しない**。OCR 結果は同一入力に対して変わらず、10章で約35分の実行コストに
  見合わない（feat-013 ADR-3・feat-015 ADR-4・feat-016 ADR-2・feat-017 ADR-4・feat-019 ADR-3 と同じ判断）
- **`normalize_punct.py` を再実行しない**。feat-013 で適用済みであり、本案件は字形正規化
  テーブルを変更しないため結果は変わらない
- **`final/` を直接編集しない**。final は `run-NN-normalized/` からのコピーであり、コピー元を
  更新しないと次回の final 再構築で変更が失われる（feat-013 の既存方針）
- **`content_list.json` を修正しない**。MinerU のスキーマを維持する既存ポリシー（feat-010）。
  結果として md と json の当該箇所の表記が一致しなくなるが、これは feat-013 §6.1・
  feat-016 §8・feat-017 design.md §8・feat-019 design.md §8 で許容済みの既知事項である
- **置換表（`normalize_punct.py`）に本件の4件を追加しない**（機能設計書 ADR-1 で理由を記す）
- **`old` / `new` に疑問符（`?` / `？`）を含めない**（機能設計書 ADR-2）。約物の全角/半角ゆれは
  後続案件案 C の対象であり、そこで文字が変わると本案件の `old` が一致しなくなるため
- **`CLAUDE.md` を変更しない**（update-003 の非対称ルール）
- 修正定義ファイルの実体は**コミット禁止**（書籍本文を含むため）
- 本案件は**コード変更を含まない**。作業中にコード変更が必要と判明した場合は中断して報告する
