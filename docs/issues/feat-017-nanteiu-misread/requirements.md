# feat-017 要求仕様書: 確率統計 4章の誤読「なんという → なんていう」9件の修正

## 1. プロジェクト概要

### 何を作るのか

『プログラミングのための確率統計』の chap01・chap03・chap06・chap08 について、
修正定義ファイル（`{BASE2}/ocr/fixes/chapNN.json`・リポジトリ外）に「なんという →
なんていう」の修正を計9件定義し、`apply_fixes.py`（feat-010）で既存成果物に適用したうえで、
`build_final.py`（feat-012）で各章の `final/chapNN/` を再構築する。

修正定義ファイルは、**chap01・chap03・chap08 は新規作成**、**chap06 は既存ファイルへの追記**である。

**リポジトリ内のコード（`scripts/`）とテストコード（`tests/test_*.py`）は一切変更しない。**
本案件で作成・更新する成果物は次の3つに限られる。

1. リポジトリ外の修正定義ファイル4件（chap01・chap03・chap08 は新規作成、chap06 は追記）
2. それらを適用したリポジトリ外の既存成果物（4章分の `{NORM}` と `{FINAL}`）
3. リポジトリ内の案件ドキュメント（`docs/issues/feat-017-nanteiu-misread/`）、
   `docs/BACKLOG.md` / `docs/CHANGELOG.md` の完了処理、および
   テスト結果の記録 `tests/results/feat-017_test_result.txt`（新規作成。
   CLAUDE.md「テスト」のルールで必須）

### なぜ作るのか

原本の「なん**て**いう」が OCR で「なん**と**いう」と誤読されている箇所が、
確率統計 final 全10章に計10件あることが feat-015 の調査で判明した。
そのうち chap02 の1件は feat-015 で修正済みであり、**残り9件が未修正のまま残っている**
（案件 README.md §1・§2）。

9件すべてについて原本 TIF を目視確認し、すべて原本が「なんていう」であることを確認済みである
（案件 README.md §3）。誤読を残すことは本プロジェクトのゴール「入力への忠実な OCR」に反するため、
修正する。

特に図 3.15・3.16 のキャプション2件は、誤読を残すと**意味が反転する**。原本の
「合計が 3.5n に近づいていく、なんていうことはない」（＝そのようなことは起きない）が
「なんということはない」（＝たいしたことではない）になると、
「合計は 3.5n に収束しない」という図の主旨が「合計が 3.5n に収束するのは些細なことだ」と
読める文になってしまう（案件 README.md §3.1）。

### 誰が使うのか

本プロジェクトのユーザー。成果物（`{BASE2}/ocr/final/chapNN/chapNN_gray300.md`）を
LLM に読ませて学習に用いる。

### どこで使うのか

`docs/TECH_STACK.md` に定義された既存環境（Ubuntu 24 系 / Python 3.12.3 / uv）。
新規のライブラリ・モデル・ネットワークアクセスは追加しない。

## 2. 用語定義

feat-010・feat-013・feat-015・feat-016 の要求仕様書の用語を継承する。本書で用いる主な用語は次のとおり。

| 用語 | 定義 |
|---|---|
| 修正定義ファイル | OCR 誤りを「修正前文字列（`old`）→ 修正後文字列（`new`）」のペアで記録した JSON。`{BASE2}/ocr/fixes/{name}.json` に置く。書籍本文を含むためリポジトリに置かない（feat-010） |
| 語彙単位の誤り | 1文字の字形置換では表現できず、複数文字の並びとしてのみ判定できる誤り。本件の「なんという → なんていう」がこれにあたる（feat-016 の「上的 → 上の」と同種） |
| 最終不変条件 | `apply_fixes.py` が適用後に検査する条件。**全 fix について `count(old) == 0` かつ `count(new) == 1`**。1つでも破れると出力を書かずにエラー終了する（feat-010 FR-003 規則6） |
| 再適用 | 既に構築済みの成果物（`run-NN-normalized/` と `final/`）に対し、MinerU を再実行せずに修正適用・final 再構築のみを行うこと（feat-013 §2） |
| `{BASE2}` | `/home/sakagawa/work/確率統計`（git 管理外・リポジトリ外） |
| `{NORM}(NN)` | `{BASE2}/ocr/mineru-full/chapNN/run-01-normalized`（各章の正規化済みディレクトリ） |
| `{FINAL}(NN)` | `{BASE2}/ocr/final/chapNN`（各章の最終成果物ディレクトリ） |

## 3. 機能要求一覧

### FR-001: 修正定義ファイルへの修正の定義（4章・計9件）

- **機能名**: `{BASE2}/ocr/fixes/chap01.json`・`chap03.json`・`chap08.json` の新規作成と
  `chap06.json` への追記
- **概要**: 9件の誤読を、`fixes/template.json` の書式に従って章ごとの fix として定義する
- **入力**: 案件 README.md §2・§3 で確定した誤り箇所（9箇所）
- **出力**: 修正定義ファイル4件（UTF-8・JSON）
- **受け入れ基準**:
  1. `fixes/README.md`・`fixes/template.json` の書式に従い、各 fix が `id` / `reason` / `old` / `new` の
     4キーをすべて文字列で持つ
  2. 各ファイルの `fixes` 配列の要素数が次のとおりになる。新規に定義する fix の合計は **9件**である

     | ファイル | 既存 | 新規 | 追記後の要素数 |
     |---|---|---|---|
     | `chap01.json`（新規作成） | 0 | 1 | 1 |
     | `chap03.json`（新規作成） | 0 | 3 | 3 |
     | `chap06.json`（既存に追記） | 1（`chap06-001`） | 4 | 5 |
     | `chap08.json`（新規作成） | 0 | 1 | 1 |
  3. 既存の `chap06-001` の `id` / `reason` / `old` / `new` を1文字も変更しない
  4. `apply_fixes.py` の `validate_fixes` がエラーを1件も出さない
  5. 適用**前**の各章の md において、新規 fix のそれぞれについて `count(old) == 1` である
  6. 適用**後**の各章の md において、**その章のすべての fix**（新規・既存とも）について
     `count(old) == 0` かつ `count(new) == 1` である（最終不変条件）
  7. 各 `reason` に、原本 TIF で確認済みであることと、`old` / `new` を一意にするために
     文脈を含めた理由を日本語で記述する
  8. ファイルはリポジトリに置かず、コミットもしない（feat-010 の運用）

### FR-002: 「なんという」の誤読の訂正（9件）

- **機能名**: 4章の md における「なんという」→「なんていう」の訂正
- **概要**: 案件 README.md §2 の表に挙げた9箇所を訂正する
- **入力**: 各章の `{NORM}(NN)/chapNN_gray300.md`（適用前）
- **出力**: 同（適用後）
- **受け入れ基準**:
  1. 適用後の各章の md における「なんという」の出現回数が **0** である
     （適用前は chap01 = 1、chap03 = 3、chap06 = 4、chap08 = 1）
  2. 適用後の各章の md における「なんていう」の出現回数が、
     chap01 = 1、chap03 = 3、chap06 = 4、chap08 = 1 である（適用前はいずれも 0）
  3. 件数はすべて Python の `str.count()` による**出現回数**で数える。
     `apply_fixes.py` の不変条件と同じ数え方であり、行数ではない。**`grep -c` を使わない**
  4. 確率統計 final 全10章の md における「なんという」の残存が **0 件**になる
     （chap02 は feat-015 で修正済み、chap00・02・04・05・07・09 はもともと 0 件）

### FR-003: 既存成果物への修正の適用と final の再構築（4章）

- **機能名**: chap01・chap03・chap06・chap08 の再適用
- **概要**: MinerU と `normalize_punct.py` を再実行せず、`apply_fixes.py` と
  `build_final.py` のみを4章それぞれに対して実行する
- **入力**: 各章の `{NORM}(NN)/chapNN_gray300.md` と `{BASE2}/ocr/fixes/chapNN.json`
- **出力**: 各章の `{NORM}(NN)/chapNN_gray300.md`（インプレース更新）と `{FINAL}(NN)/`（再構築）
- **受け入れ基準**:
  1. `apply_fixes.py` の終了コードが 4章とも 0 であり、`applied` / `skipped` の内訳が
     chap01 = 1/0、chap03 = 3/0、chap06 = 4/1（既存 `chap06-001` は適用済みのため skipped）、
     chap08 = 1/0 である
  2. `build_final.py` の終了コードが 4章とも 0 である（3種類の機械検証がすべて合格）
  3. 適用後の各章の md の**文字数と行数が適用前と同一**である
     （「と」→「て」は 1 文字 → 1 文字であり、改行の増減もないため）。
     2026-08-31 実測の基準値: chap01 = 24856 文字 / 586 行、chap03 = 54009 文字 / 1462 行、
     chap06 = 36479 文字 / 835 行、chap08 = 67199 文字 / 1566 行
  4. 適用前後の `diff` の差分ハンクが、chap01 = 1、chap03 = 3、chap06 = 4、chap08 = 1 であり、
     いずれも「なんという」→「なんていう」の1文字のみの変更である
  5. `{FINAL}(NN)/` の md・content_list.json が `{NORM}(NN)/` とバイト同一である
  6. `{FINAL}(NN)/images/` のファイル数が変わらない
     （2026-08-31 実測: chap01 = 27、chap03 = 66、chap06 = 19、chap08 = 43）
  7. 各章の `content_list.json` は**変更されない**（`apply_fixes.py` は md のみを対象とする
     既存ポリシー。feat-010／feat-013 §6.1）。SHA-256 で検証する

### FR-004: 影響範囲の限定

- **機能名**: 本案件で変更しない対象の明示
- **概要**: 修正の影響を 4章の md 計9箇所に限定する
- **受け入れ基準**:
  1. `scripts/` 配下のコードを1行も変更しない
  2. `tests/test_*.py`（テストコード）を1行も変更しない。
     `tests/results/feat-017_test_result.txt` の新規作成は**この制限の対象外**であり、
     CLAUDE.md「テスト」のルールに従って必ず作成する
  3. 確率統計の対象外6章（chap00・02・04・05・07・09）の成果物を変更しない
  4. 既存の修正定義ファイル `chap02.json`・`chap04.json`・`chap05.json`・`chap07.json`・
     `chap09.json` を変更しない
  5. PRML（`{BASE}`）の成果物を変更しない
  6. 既存の自動テストを全件実行し、feat-015 完了時点（216 passed）と同じくすべて成功する

## 4. 非機能要求

| 項目 | 要求 |
|---|---|
| 性能 | 再適用は 4章のみ・MinerU 再実行なしのため、全工程が 60 秒以内に完了する |
| 再現性 | `apply_fixes.py` は冪等である（2回目以降の実行では `old` 不在・`new` 1件のため `skipped` として扱われ、終了コード 0・内容不変） |
| 可搬性 | 修正定義ファイルは書籍本文を含むためリポジトリ外に置く。リポジトリ側には書式テンプレート（`fixes/template.json`）のみを保持する（feat-010 の既存方針） |
| 保守性 | 修正の根拠（原本確認の事実と一意性確保の理由）を `reason` に残し、再 OCR 時に文面が変われば `apply_fixes.py` がエラーで検出できる状態を保つ |
| 独立性 | 章ごとに `apply_fixes.py` → `build_final.py` を完結させる。ある章が失敗しても、完了済みの章の final は正しい状態で残る（feat-012 の章単位構築の方針と同じ） |

## 5. 制約条件

- **MinerU を再実行しない**。OCR 結果は同一入力に対して変わらず、10章で約35分の実行コストに
  見合わない（feat-013 ADR-3・feat-015 ADR-4・feat-016 ADR-2 と同じ判断）
- **`normalize_punct.py` を再実行しない**。feat-013 で適用済みであり、本案件は字形正規化
  テーブルを変更しないため結果は変わらない
- **`final/` を直接編集しない**。final は `run-NN-normalized/` からのコピーであり、コピー元を
  更新しないと次回の final 再構築で変更が失われる（feat-013 の既存方針）
- **`content_list.json` を修正しない**。MinerU のスキーマを維持する既存ポリシー（feat-010）。
  結果として md と json の当該箇所の表記が一致しなくなるが、これは feat-013 §6.1・
  feat-015 design.md §8・feat-016 §8 で許容済みの既知事項である
- **置換表（`normalize_punct.py`）に「なんという → なんていう」を追加しない**
  （機能設計書 ADR-1 で理由を記す）
- 修正定義ファイルの実体は**コミット禁止**（書籍本文を含むため）
- 本案件は**コード変更を含まない**。作業中にコード変更が必要と判明した場合は中断して報告する
