# feat-010: 手動修正の永続化 — 修正定義ファイルの機械適用（apply_fixes.py）

- **ステータス**: Closed（2026-08-25 完了。ユーザーが実データで式番号修正5件を確認）
- **種別**: feat（機能追加）

## 概要

MinerU の OCR には後処理で機械的に解消できない個別の認識誤りが残る（直近の例: 式番号と式の誤結合。ユーザー報告 2026-08-25、chap01 式 (1.25)/(1.26)）。これらは手動修正するしかないが、最終成果物 `{BASE}/ocr/final/` の md を直接修正すると、再OCR後に final を再構築した時点で修正が失われる。

対処として、修正1件を「修正前の文字列（old）→ 修正後の文字列（new）」のペアとして章ごとの**修正定義ファイル**に記録し、パイプラインの最終段で機械適用する CLI `scripts/apply_fixes.py` を追加する。再OCR後も定義ファイルを再適用すれば修正が復元され、OCR 出力の変化で old が見つからなくなった場合は**エラーで停止**して気づける（黙って壊れない）。

### 公開リポジトリとの分離（ユーザー要件）

修正定義ファイルの実体は書籍本文の文字列を含むため、将来リポジトリを GitHub 公開しても表に出ないよう、**最初からリポジトリ外の `{BASE}/ocr/fixes/` に置く**（スキャン・final と同じ扱い）。リポジトリには仕組みだけを置く: 適用スクリプト、書式テンプレート（架空の文字列のみ）、使い方の README。`.gitignore` でリポジトリ内に置く案は、誤コミット1回で履歴に残り公開時に履歴書き換えが必要になるため不採用（ユーザー合意済み）。

## 調査記録（2026-08-25）

### 方式の検討（ユーザーと合意済み）

1. **修正定義ファイル方式（採用）**: old→new ペアの定義ファイル＋機械適用。適用失敗（old が見つからない・複数一致）を検出でき、再OCR後の復元が1コマンドで済む
2. パッチファイル方式（不採用): 行番号・前後文脈依存で OCR 出力の変化に弱く、失敗時の調査もしにくい
3. final の git 管理＋diff 救出（不採用。任意の保険として運用は可): 再適用が手作業になる

### 設計上の前提（実測）

- 適用対象は正規化・HTML表変換・脚注挿入がすべて済んだ md（final と run-NN-normalized は同一状態）。修正の old/new はこの状態の文字列として書く
- content_list.json は無改変とする（feat-008/009 と同方針。迷子番号のブロックは content_list にも残るが、content_list は座標・画像用データであり閲覧用ではない）
- ocr_dir.py の `name`（chap01 等）で定義ファイルを引ける命名（`{name}.json`）にすれば一括実行に組み込める

### 運用メモ

- 修正定義の変更履歴を残したい場合は、`{BASE}/ocr/fixes/` にローカル専用の git リポジトリを別途作ればよい（公開リポジトリとは独立。本案件のスコープ外、ユーザーの任意）
- 本案件のドキュメント（リポジトリ内）には書籍本文の文字列を書かない。修正内容は式番号・ブロックインデックスで参照する
