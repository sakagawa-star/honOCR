# feat-010 要求仕様書: 手動修正の永続化 — 修正定義ファイルの機械適用

- 案件: `docs/issues/feat-010-apply-fixes/`
- 作成日: 2026-08-25
- 準拠基準: `docs/REQUIREMENTS_STANDARD.md`

## 1. プロジェクト概要

- **何を作るのか**: OCR 誤りの手動修正を「修正前文字列（old）→ 修正後文字列（new）」のペアとして章ごとの修正定義ファイル（JSON）に記録し、Markdown に機械適用する CLI `scripts/apply_fixes.py` を作る。`scripts/ocr_dir.py` の一括パイプラインの最終段に組み込み、初期データとして式番号誤結合5件の修正定義を作成して既存の最終成果物に適用する
- **なぜ作るのか**: final の md を直接手動修正すると、再OCR後の final 再構築で修正が失われる。定義ファイルとして分離すれば再適用1コマンドで復元でき、OCR 出力の変化で適用できなくなった場合もエラーで検出できる
- **誰が使うのか**: プロジェクトオーナー（ユーザー）。ocr_dir.py 経由では Claude Code なしで実行される
- **どこで使うのか**: 本プロジェクトのローカル環境（Linux、Python 3.12、uv 管理）。修正定義ファイルの実体はリポジトリ外 `{BASE}/ocr/fixes/` に置き、リポジトリにはスクリプトとテンプレートのみ置く（GitHub 公開時に書籍本文由来の文字列を含むファイルが公開されないようにする。ユーザー要件）

## 2. 用語定義

機能設計書・コード内でも同じ用語を使う。

| 用語 | 定義 |
|---|---|
| `{BASE}` | `/home/sakagawa/work/Pattern_Recognition_and_Machine_Learning`（CLAUDE.md と同一） |
| 修正定義ファイル | 章1つ分の修正を記録した JSON ファイル。`{BASE}/ocr/fixes/{name}.json`（name = chap01 等）。git 管理しない（リポジトリ外） |
| 修正（fix） | 定義ファイル内の1エントリ。`id`（識別子）・`reason`（理由）・`old`（修正前の完全一致文字列、非空）・`new`（修正後の文字列、非空）を持つ |
| 適用（applied） | md 内に `old` がちょうど1回出現し、`new` に置換されること |
| 適用済みスキップ（skipped） | md 内に `old` が出現しないが、適用済みとみなせる条件（FR-003）を満たし、置換せず正常継続すること |
| テンプレート | 修正定義ファイルの書式を示すサンプル。架空の文字列のみで構成し、リポジトリの `fixes/template.json` に置く |

## 3. 機能要求一覧

### FR-001: 修正適用 CLI

- **機能名**: `scripts/apply_fixes.py`
- **概要**: Markdown 1 ファイルと修正定義ファイル 1 個を入力に取り、全修正を適用した Markdown を出力する
- **入力**: 位置引数 `md`（UTF-8 Markdown ファイルパス）、位置引数 `fixes`（修正定義 JSON のパス）、`-o/--outdir`（出力ディレクトリ、必須）、`--overwrite`（出力先の同名ファイルが既存でも上書きする。既定は拒否）
- **出力**: `outdir/<md と同じベース名>` に適用後の Markdown を書き出す。標準出力に `"{md 名}: {N} applied, {M} skipped"` と `"total: {N} applied, {M} skipped"` の 2 行のサマリを出す。終了コードは成功 0、エラー 1
- **受け入れ基準**: FR-006 の初期修正定義を用いて、`final/chap01` の md に適用すると 1 件 applied となり、適用後の md で案件 README 調査表 #1 の 1 つ目の式（content_list インデックス 217 相当）に `\tag{1.25}` が、2 つ目の式（同 218 相当）に `\tag{1.26}` が付き、独立段落の `(1.26)` が存在しない。chap02 は 1 件、chap05 は 3 件 applied となり、調査表 #2〜#5 の各所で迷子番号の独立段落が消え、対応する式に原本どおりのタグが付く

### FR-002: 修正定義ファイルの書式と検証

- **機能名**: 定義ファイルの読み込み・検証
- **概要**: 修正定義ファイルは次の構造の JSON とする: トップレベルは `{"fixes": [...]}`。各要素は `id`（文字列、ファイル内で一意、非空）、`reason`（文字列）、`old`（文字列、非空）、`new`（文字列、**非空**）の 4 キーを必須で持つ。削除だけの修正は `new` 空では表現できず、削除対象の前後の残す文字列を含めた old→new として表現する（適用済み判定を new の存在で確実に行うため）
- **入力**: 修正定義 JSON
- **出力**: 検証エラー時は標準エラーに「どのエントリの何が不正か」を出して終了コード 1（部分適用しない）。検証項目は以下ですべてとする: JSON として解釈可能・トップレベルが `fixes` キーを持つ dict・`fixes` が list・各要素が dict で必須 4 キーを持つ・`id` の一意性と非空・`old` の非空・`new` の非空・`old` と `new` の非同一
- **受け入れ基準**: 必須キー欠落・`id` 重複・`old` 空・`new` 空・`old == new` の各不正データで終了コード 1 となり、出力ファイルが作られない

### FR-003: 適用規則

- **機能名**: 修正の適用判定
- **概要**: 各修正を定義ファイルの記載順に適用する。判定規則は以下ですべてとする（`count(s)` = md 内の文字列 s の出現回数）:
  1. `count(old) == 1` → old を new に 1 回置換し applied に数える
  2. `count(old) == 0` かつ `count(new) == 1` → 適用済みとみなし skipped に数える（置換しない）
  3. `count(old) == 0` かつ `count(new) == 0` → エラー（OCR 出力が変化して修正が適用不能）。標準エラーに `id` と old の先頭 40 文字を出して終了コード 1
  4. `count(old) == 0` かつ `count(new) >= 2` → エラー（適用済みかどうかを一意に判定できない）。標準エラーに `id` と new の出現回数を出して終了コード 1
  5. `count(old) >= 2` → エラー（一意に適用できない）。標準エラーに `id` と old の出現回数を出して終了コード 1
  - エラーが 1 件でもあれば出力ファイルを書かない（全修正が applied または skipped の場合のみ書く）
  - 各判定はそれ以前の修正の置換結果を反映した md に対して行う（記載順の逐次適用）
  6. **最終不変条件**: 規則 1〜5 をエラーなしで通過した後、出力前に、適用完了後の md に対して全修正の `count(old) == 0` かつ `count(new) == 1` を検査する。1 件でも violate すればエラー（標準エラーに `id` と violate 内容を出して終了コード 1、出力ファイルを書かない）。これにより「old が new の部分文字列である修正」や「後続の修正が先行の修正の new を書き換える修正」など、再実行時に全件 skipped とならない定義を初回適用時に検出する
- **受け入れ基準**: 規則 1〜5 と最終不変条件のそれぞれを検証する自動テストが成功する。FR-001 適用後の md に再実行すると 0 applied・全件 skipped となり、md はバイト単位で無変更である（冪等性）

### FR-004: ocr_dir.py への組み込み

- **機能名**: 一括パイプラインへの統合
- **概要**: `scripts/ocr_dir.py` にオプション `--fixes-dir <ディレクトリ>` を追加する。指定時、脚注挿入（feat-009）の直後に `<fixes-dir>/{name}.json` の存在を確認し、存在すれば正規化済み md にインプレース適用する
- **入力**: `--fixes-dir`（任意。既定 None = 修正適用を行わない）
- **出力**: 定義ファイルが存在しない場合はそのディレクトリの修正適用をスキップし（エラーにしない）、applied/skipped = 0/0 とする。適用した場合は `DirResult` に applied/skipped 件数を追加し、PASS 行に `fixes={N}+{M}skipped` を表示する。apply_fixes.py が非 0 終了またはサマリ解析不能の場合はそのディレクトリを FAIL とする
- **受け入れ基準**: `tests/test_ocr_dir.py` の既存テストが全件成功し、「fixes-dir 未指定でステップ自体が実行されない」「定義ファイルなしでスキップ」「適用成功で PASS 行に fixes= が出る」「適用失敗で FAIL」を検証する追加テストが成功する

### FR-005: テンプレートと使い方の文書

- **機能名**: リポジトリ側の公開物
- **概要**: リポジトリに `fixes/template.json`（書式を示すサンプル。**架空の文字列のみで構成し、書籍本文の文字列を一切含めない**）と `fixes/README.md`（書式仕様・適用規則・実体ファイルの置き場所 `{BASE}/ocr/fixes/{name}.json`・実行コマンド・注意事項を記載）を追加する
- **入力**: なし（静的ファイル）
- **出力**: 上記 2 ファイル
- **受け入れ基準**: `template.json` が FR-002 の検証を通る正しい書式であり、かつ `grep` で書籍固有の語（式番号 `1.25` 等・本文語句）を含まないことを確認できる。README.md に FR-003 の適用規則 1〜5 が記載されている

### FR-006: 初期修正定義の作成（式番号誤結合5件）

- **機能名**: `{BASE}/ocr/fixes/` の初期データ
- **概要**: 案件 README の調査記録に列挙した 5 件（chap01 の (1.25)/(1.26)、chap02 の (2.218)/(2.219)、chap05 の (5.98)〜(5.100)・(5.106)/(5.107)・(5.159)/(5.160)）を修正する定義ファイル `chap01.json`（1 fix)・`chap02.json`（1 fix)・`chap05.json`（3 fixes）を作成する
- **入力**: 現行の final md（old の抽出元）と原本スキャン TIF（あるべき状態の確認）
- **出力**: 各修正は「対応する式に正しい `\tag{}` を付与し、迷子番号の独立段落を除去する」内容とする。複数行が 1 つの array ブロックに統合された 3 件（chap02・chap05 の 2 件）は、array を独立した `$$ … $$` ブロックに分割し、それぞれに正しいタグを付ける。分割時は array の**構文要素のみ**（`\begin{array}{…}`・`\end{array}`・alignment marker `&`・行区切り `\\`）を除去してよく、数式トークン自体は変更しない（実測: chap02 の対象は `{r l}` 環境で `&` を含み、chap05 の 2 件は `{l}` 環境で `&` なし）。old は現行 final md からの正確な抜粋、new はそれに対する最小限の変更とする
- **受け入れ基準**: FR-001 の受け入れ基準と同一。加えて、各修正の new に含まれる数式トークン列が、old に含まれる数式トークン列と（タグの付与・付け替えと上記構文要素の除去を除き）同一である

### FR-007: 既存データへの適用

- **機能名**: final / run-01-normalized への一括適用
- **概要**: FR-006 の定義を既存データに適用する
- **入力**: `{BASE}/ocr/final/chapNN/chapNN_gray300.md` および `{BASE}/ocr/mineru-full/chapNN/run-01-normalized/chapNN_gray300.md`（NN = 01, 02, 05。定義ファイルのない章は適用しない）
- **出力**: 両系統の md をインプレース更新する。content_list.json・images/ は無改変とする
- **受け入れ基準**: applied 件数が chap01 = 1、chap02 = 1、chap05 = 3 で、final と run-01-normalized で同数。適用後、各章の final md と run-01-normalized md がバイト同一（`cmp`）。chap01/02/05 の content_list.json が適用前とバイト同一。適用後の md 全 8 章で「独立段落の迷子番号」（`(1.26)` `(2.219)` `(5.100)` `(5.107)` `(5.160)` のみからなる行）が 0 件

### FR-008: 自動テスト

- **機能名**: `tests/test_apply_fixes.py`
- **概要**: FR-001〜FR-003 の規則を合成データ（架空の文字列）で検証する自動テスト
- **入力**: `uv run pytest -v`
- **出力**: 全テスト成功。結果を `tests/results/feat-010_test_result.txt` に保存する
- **受け入れ基準**: 適用規則 1〜5・逐次適用（前の置換結果への適用）・冪等性・定義ファイル検証エラー各種（`new` 空を含む）・エラー時に出力を書かないこと・`--overwrite` 拒否・サマリ形式を検証するテストが存在し、既存テストを含む全件が成功する。**テストデータに書籍本文の文字列を使わない**

## 4. 非機能要求

- **パフォーマンス**: 1 章分（md 約 200KB・修正 100 件以下）の処理が 10 秒以内に完了する
- **対応環境**: Linux、Python 3.12（uv 管理）。GPU 不要
- **信頼性**: 出力は `normalize_punct.write_text_atomic` で原子的に書き込む。エラー時は出力ファイルを一切書かない（部分適用状態を残さない）
- **セキュリティ（公開分離）**: リポジトリにコミットするファイル（スクリプト・テンプレート・README・テスト）に書籍本文由来の文字列を含めない。修正定義ファイルの実体はリポジトリ外 `{BASE}/ocr/fixes/` にのみ置く

## 5. 制約条件

- 使用ライブラリは Python 標準ライブラリ（argparse、json、sys、pathlib）と既存モジュール `scripts/normalize_punct.py`（`write_text_atomic`）に限定する。新規外部依存を追加しない
- content_list.json は変更しない
- 入出力パス・定義ファイルパスはハードコードせず CLI 引数で受け取る（CLAUDE.md コーディング規約）
- ネットワークアクセスなし
