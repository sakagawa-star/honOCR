## 1. 変更理由

### 1.1 直接の理由（ユーザー確定・2026-09-01）

CLAUDE.md の「ドメイン知識」が肥大化しつつある。**ドメイン知識を CLAUDE.md の外に出し、CLAUDE.md からは参照する**。

### 1.2 背景にある構造問題

CLAUDE.md には性質の異なる2種類の内容が同居している。

| 種類 | 内容 | 更新する主体 |
|---|---|---|
| **統治** | 開発フロー・レビュー手順・運用ルール・コーディング規約 | update 案件のみ |
| **知識** | データの所在と仕様・ディレクトリ構成・ドメイン知識・技術スタック要約 | feat/bug 案件の完了処理 |

同居しているため、案件で得た知見を追記するという日常的な操作が、毎回「統治文書の編集」になっていた。
2026-09-01 の feat-018 インシデント調査（`docs/issues/feat-018-nanteiiu-misread/incident.md`）で、
この構造が「CLAUDE.md への正当な編集が頻繁にあるため、不適切な編集が紛れても目立たない」という
問題を生んでいることが顕在化した。分離すれば、知識ファイルへの追記は統治への干渉ではなくなり、
CLAUDE.md 本体の変更だけを厳格に扱える（「CLAUDE.md を変更する」行為そのものが稀な例外イベントになる）。

## 2. 現状の実測（2026-09-01）

### 2.1 どの案件種別が CLAUDE.md のどのセクションを更新してきたか

CLAUDE.md を変更した全17コミットについて、変更行の属するセクションを機械集計した。

### 2.3 技術スタック節（5行）と `docs/TECH_STACK.md` の対応（情報喪失の確認）

技術スタック節はポインタ化する（決定事項）。削除される5行の内容がすべて `docs/TECH_STACK.md` に存在することを確認した。

| CLAUDE.md 技術スタック節の行 | `docs/TECH_STACK.md` での所在 |
|---|---|
| 言語: Python 3.12.3 | 「実行環境」の言語 |
| パッケージ管理: uv | 「実行環境」のパッケージ管理 |
| 主要ライブラリ: MinerU 3.4.4、img2pdf / pillow | 「ライブラリ一覧」の表（mineru[core] 3.4.4・img2pdf 0.6.3・pillow 12.3.0） |
| 詳細: `docs/TECH_STACK.md` を参照 | （ポインタ自体。残す） |
| 注意: GPU は RTX 5060 Ti 16GB（Blackwell, sm_120）。CUDA 12.8 以降必須、古い CUDA 前提のツールは動かない | 「実行環境」の GPU 行（「CUDA 12.8 以降のビルドが必須」と断定）、および「環境構築手順」末尾の「環境依存の注意」（古い CUDA 前提のツールは「動作しない**可能性が高い**」） |

**事実の喪失はない**が、**表現の確度に差が1点ある**: 古い CUDA 前提のツールについて、CLAUDE.md 技術スタック節は「動かない」と断定し、`docs/TECH_STACK.md` は「動作しない可能性が高い」と幅を持たせている。根拠を確認すると、CLAUDE.md「背景」（L23）も「動作リスクがある」であり、実際に動かして確認した記録はない（feat-001 で検証したのは MinerU が動くことであって、ndlocr_cli 等を動かして失敗したのではない）。したがって**断定は根拠のない強めの言い換え**であり、ポインタ化に伴って `docs/TECH_STACK.md` の「可能性が高い」に統一する。これは**意図的な表現変更**として記録する（`docs/TECH_STACK.md` は変更しない）。なお制約の本体である「CUDA 12.8 以降のビルドが必須」は `docs/TECH_STACK.md` でも断定のままであり、運用上の制約は弱まらない。

## 4. ユーザー確定事項（4.1〜4.3 は 2026-09-01、4.4〜4.7 は 2026-09-02）

| # | 事項 | 決定 |
|---|---|---|
| 4.1 | 方針 | ドメイン知識を CLAUDE.md の外に出し、CLAUDE.md からは参照する |
| 4.2 | 方式 | **案A: 1ファイル**。データ・ドメイン知識・ディレクトリ構成の3セクションをまとめて外出し。技術スタックは `docs/TECH_STACK.md` へのポインタ化のみ |
| 4.3 | 分割閾値 | **500行**を超えたら分割を検討する（Claude Code の提案を採用。1000行案と比較して、必読ファイルの読み込みコスト・早発火の安さ・行長の分散を理由に 500 を推奨した）。注意書きの文面: 「本ファイルが 500 行を超えたら分割を検討する。分割しない判断をしてもよいが、その判断と理由を記録する」 |
| 4.4 | ファイル名 | **`docs/PROJECT_KNOWLEDGE.md`** |
| 4.5 | 反映担当 | **Claude Code 本体** |
| 4.6 | 案件の単位 | 1つの update 案件で対応する（変更要素が相互依存で、分割すると中間状態が不整合になるため） |
| 4.7 | 付随変更 | feat/bug フロー完了ステップの更新先の付け替え、必読指示、非対称ルール（外部ファイル＝各案件の完了処理で更新可／CLAUDE.md 本体＝update 案件のみ）の明文化 |

案A を選んだ理由（Claude Code の報告・ユーザー採用）: 3セクションはすべて「事実の記述」で更新契機も同じ（案件完了処理）、
`{BASE}`/`{BASE2}` の定義（データ節）とその参照元（ドメイン知識・ディレクトリ構成）が1ファイル内で閉じる、
必読指示が1つで済む、現状合計85行で分割する規模ではない。
