## 12. 設計判断の記録（ADR）

### ADR-1: 1ファイルにまとめる（案A）

- **決定**: データ・ディレクトリ構成・ドメイン知識を `docs/PROJECT_KNOWLEDGE.md` 1ファイルに置く
- **理由**: 3つとも「事実の記述」で更新契機も同じ（案件完了処理）。`{BASE}`/`{BASE2}` の定義とその参照元が1ファイル内で閉じる。必読指示が1つで済む。現状85行で分割する規模ではない
- **代替案**: 性質別に複数ファイル → 読む側・更新する側の手数が増えるだけで現時点の利益がない。肥大化時の分割余地は ADR-2 の閾値で担保する。不採用（ユーザー決定）

### ADR-2: 分割検討の閾値を 500 行とする

- **決定**: 500 行を超えたら分割を**検討**する（分割の強制ではない）。判断と理由をファイル末尾に記録する
- **理由**: (1) 必読ファイルのため、重さは毎セッション・毎サブエージェントが払うコストになる。現行の1行＝1知見の長大行スタイル（平均100文字/行・最長511文字）では 500 行で約5万文字に達し、「毎回全部読む」運用の実用限界に近い (2) トリガーは「検討」なので早発火のコストは1回の判断だけで済み、遅発火のコストは発火までの全セッションに及ぶ。閾値は低めが合理的 (3) 行数は `wc -l` で機械確認できる明確な基準である
- **代替案**: 1000 行 → 上限としては成立するが、検討開始点としては遅い（到達時点で約10万文字）。不採用（ユーザー決定）。文字数との併記 → 基準を1つに保つため採らない

### ADR-3: CLAUDE.md に知識の要約を残さない

- **決定**: CLAUDE.md の新節は参照・必読指示・役割分担のみとし、データやドメイン知識の要約を置かない
- **理由**: 要約を置くと二重管理になり、案件完了処理のたびに両方の同期が必要になる（本案件が解消しようとしている「知見追記＝統治文書の編集」が形を変えて残る）。常時参照性の低下は必読指示で補う
- **代替案**: 主要な注意点（`.tif` 非対応・`grep -c` 禁止等）だけ CLAUDE.md に残す → 「何が主要か」の判断が案件ごとに揺れ、境界が曖昧になる。不採用

### ADR-4: 技術スタック節はポインタ化する

- **決定**: 5行の要約を削除し、`docs/TECH_STACK.md` への参照1行にする
- **理由**: 5行の情報はすべて `docs/TECH_STACK.md` に存在する（案件 README.md §2.3）。要約を残すと ADR-3 と同じ二重管理になる（feat-001/002 で実際に要約行の更新が発生していた）。ポインタ文に「GPU/CUDA の制約を含む」と明記して、環境依存の注意の所在を失わないようにする
- **表現差の扱い**: 「古い CUDA 前提のツールは動かない」（断定）は `docs/TECH_STACK.md` の「動作しない可能性が高い」に統一する。断定の根拠（実機で失敗させた記録）がなく、CLAUDE.md「背景」も「動作リスクがある」と幅を持たせているため、幅のある表現のほうが事実に忠実である。`docs/TECH_STACK.md` を断定に書き換える案は、根拠のない強化になるため不採用。この差は「喪失」ではなく「意図的な表現変更」として README §2.3・§4.1・CHANGELOG に記録する
- **代替案**: `docs/PROJECT_KNOWLEDGE.md` に移す → `docs/TECH_STACK.md` と重複する。不採用
