### 1.2 シミュレーション（2026-09-07。ユーザーが Claude Code を相手に実施）

ユーザーが「feat-024 を自分が細かくやるとした場合」の手順を、質問を重ねる形で Claude Code に再構成させた。得られた事実:

**(a) 入出力の次元**（実測）

| 入力 | 成分数 |
|---|---|
| 成果物 md（10 章） | 517,974 文字 |
| 原本 TIF（383 ページ。`L` 341・`RGB` 34・`1` 8） | 10,351,879,984（RGB は 3 成分） |
| content_list（`page_idx` 6,071 ＋ `text` 451,663 文字） | 457,734 |
| **合計** | **10,352,855,692** |

最終出力は層ごとの (p̂_i, n'_i) の **6 成分**（区間の下限・上限と推定件数は式で決まる従属成分。Claude Code は当初 18 → 9 と 2 回誤った）。

**(b) 段の構成と、各段が最終出力の式のどの項を決めるか**

| 順 | 段 | 処理単位 | 単位あたり入力 → 出力 | 決める項 |
|---|---|---|---|---|
| 1 | 候補抽出 | 1 章の md | 11,842〜87,053 → 候補行 × 4 | **N_i**、率の分母の定義 |
| 2 | 標本抽出 | 1 層 | N_i × 4 → n_i × 3 | **n_i**、無作為性 |
| 3 | 逆引き | 1 標本 | ≤165,086 → 3 | 無し（E の誤り率を通してのみ） |
| 4 | ページ選択 | 1 標本 → 1 ページ | 21,148,640〜69,802,572 | 無し |
| 5 | 切り出し | 1 ページ ＋ bbox | → 約 6.2×10⁵ | 無し |
| 6 | 判定 | 1 切り出し | 約 6.2×10⁵ → 1 | **k_i, n'_i**（p̂ を生む唯一の段） |
| 7 | 推定 | 1 層 | n_i ラベル → 2 | 算術 |

一度に持つ最大の次元は 1 ページ（69,802,572）で、10,352,855,692 をどの段も持たない。結合（前段の全単位を待つ）は順 2 と順 7 の 2 か所だけ。

**(c) 実測との比較**: 値を生む 3 段（1・2・6）のうち終わっていたのは順 1 だけで、順 1 は「既知の欠落 16 件のうち母集団に入るのは 7 件（44%）」を示していた。順 3 は検査標本で 93.3%（想定通り）。順 6 は未着手・判定関数も未記述。M4 の Go 条件（判定不能率が層ごと 10% 以内）は、順 3 の失敗率 6.7〜8% だけで **42〜60% の確率で落ちる**設計だった（二項分布で算出）。

**(d) 見直しの梯子**（ユーザーが提示）: 想定値が出なかったら (1) その段を見直す → (2) 精度が悪いなら段を細かく分ける → (3) 分けられないならパイプラインの構成を見直す → (4) 見直しも無理なら最終ゴールを変更する（妥協・中止）。Claude Code は feat-024 で (1) を飛ばして (4) を提案し、別の場面では (1) で済むものを拡大していた。

### 1.3 目的

feat 案件のロードマップとマイルストーンを、**「入出力を次元で把握し、値が想定できる単位で段を作り、実行して想定と外れたら梯子の順で見直す」**形で切ることを規定し、次を担保する。

1. **最終出力に寄与しない作業が見える**: 各段が最終出力の式のどの項を決めるかを書かせる。項を持たない段に検証以上の作業を積ませない
2. **原因の分類を要さない判定**: 段ごとの想定値（根拠の種別つき）と実測の比較で外れを検出する。「同じ原因か」の分類（Claude Code が毎回「別の原因」と分類して行き詰まり検出を逃れた）に依存しない
3. **見直しの順序の固定**: 段の見直し → 分割 → 構成の見直し → 目標変更 の順を固定し、飛ばすには人の指示を要する

「馬鹿でも使える」の判定条件は、**記入欄と数える手順だけで構成され、Claude Code に「これは要るか」「同じ原因か」「十分か」の判断を要求しないこと**とする（ユーザー 2026-09-07「複雑なルールは基本お前は逸脱する」「条件を増やせばいいものではない」「言葉の定義や基準が曖昧過ぎる」）。

### 1.4 採らなかった案と不採用の理由

いずれも 2026-09-07 の対話で Claude Code が提案し、ユーザーが退けたもの。

| 案 | 不採用の理由 |
|---|---|
| 文書の行数上限（1 マイルストーン合計 500 行等） | 行数は副次的な情報。最終出力に寄与するかを見ていない。由来の lift2d update-005 でも人レビューで「行数基準 → 機能構成の 4 境界」と却下済み（update-006 README §5.1 (c)） |
| 「最終出力の確定数が 2 回動かなければ止める」 | 行き詰まり検出は既に規定にある。問題は検知ではなく「最終目標に対して無意味な作業を続けること」。また単位を人が決める形にすると、ロードマップ方式自体が不要になる |
| M1 を「最小の入力で最終出力を粗く出す」に固定 | 粗く出せる案件はロードマップ方式が不要。方式が要る（粗く出せない）案件に何も言っていない |
| 受け入れ基準に典拠（ユーザー確定／ロードマップ完了条件 (n)／調査／未検証）を必須化 | 承認範囲外の要件追加を 1 文書で止めるだけで、切り方・行き詰まりの認識に効かない（目標の主要部分に触れない） |
| 判断の境界の適用範囲の限定（判定対象が最終出力の要素の場合のみ） | 根拠にした「lift2d feat-036 でも判断の境界が全廃された」がテンプレート記録の誤読（後述 §4）。n=1 では一般化できない |
| 4 境界・併合 3 条件の削除 | 由来（lift2d update-005、人レビュー 3 回の差し戻しで確定）を読まずに提案したため。由来を確認後、本案件では「置換か並存か」を §5 でユーザー判断に委ねる |

### 1.5 人（ユーザー）レビューで方針が変わった記録

本案件の起案に至る対話で、ユーザーの指摘により Claude Code の方針が変わった点:

- 「肥大化は規定が一律様式を要求するため」→ 規定のせいにする他責思考として退けられ、Claude Code 自身の癖（近くて具体的な穴を意味を問わずに埋める）として記述し直した
- 「ロードマップ方式を撤回する」→ 目標は撤回ではなく「馬鹿でも使える形にする」と再設定された
- 「lift2d feat-036 はロードマップ方式の初運用で判断の境界を全廃した」→ ユーザー口述で訂正: feat-036 は**元の形式で途中まで進め、その段階で 6→3 に削り、その後ロードマップ形式を投入して終えた**。削った理由は「Opus が勝手に要件を増やし続けて必要ないものを作り続けた」。lift2d ではまだ現行ルールでのロードマップ運用は行われていない

## 3. 変更の候補（全量。確定は `design.md`）

### 3.1 追加する記入欄（ロードマップ）

| 欄 | 内容 | 判断を要求しないための形 |
|---|---|---|
| 最終出力の成分 | 独立な成分と従属な成分（式）を分けて列挙 | 式で書く。従属成分は独立成分からの式を添える |
| 入力の次元 | 各入力の成分数と数え方の規則（数値 1 成分、文字 1 文字 1 成分、画素 1 成分 × チャネル） | 実測値（コマンドで数えた値）を書く |
| 段（マイルストーン）の表 | 段ごとに: 処理単位／単位数／単位あたり入力の次元 → 出力の次元（**式**）／手段（既存ツール名・手作業・無し）／**最終出力の式のどの項を決めるか（無ければ「無し」）** | 次元は式、項は最終出力の成分名で書く |
| 想定値 | 段ごとに、出力の値または割合の想定と、**根拠の種別（実測／式から導出／推測）**、外れとみなす幅 | 数値と種別。実行直前に確定してよい（既存の直前予測と同じ） |

### 3.2 追加する手順（見直しの梯子）

想定値と実測が外れたとき、次の順で見直す。**飛ばすには人（ユーザー）の指示を要する**。

1. その段を見直す
2. 精度が悪い → 段を細かく分ける
3. 分けられない → パイプラインの構成を見直す
4. 見直しも無理 → 最終ゴールを変更する（妥協案・中止）

### 3.3 追加する禁止

- 「決める項」が「無し」の段に、その段の出力を次段に正しく渡すこと以上の作業（検証の検証等）を積まない
- 段の次元が式で書かれていない段には着手しない

### 3.4 既存規定との関係（§5 の判断で確定）

4 境界は段の境界の特殊形として読める（生成物の境界＝段、新規コンポーネント／環境の境界＝手段が「無し」の段、判断の境界＝想定値と実測の比較）。criteria lock は「想定値と外れの幅を実行前に固定する」ことに相当する。
