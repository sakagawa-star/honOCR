## 1. 経緯・目的

### 1.1 契機

update-014 の反映後、右ペインの Claude Code（Opus 5）が feat-025 `roadmap.md` §8 を全件点検し、「3 種のどれでもない入力」が 98・414 のほかに 3 箇所あると報告した（2026-09-09 14:29。ユーザーが本セッションに転記）。

| 箇所 | Opus が問題とした入力 | Opus の対処 |
|---|---|---|
| S2-1 | 「候補 1 件」（処理単位） | 「ステージ表で固定した値だからロードマップで固定した定数」と判断し `U_smoke` = 1 と命名 |
| S4 の `u`・`k` | 「`n` は上の式の値」 | `n` の定義を代入して展開（`u = ceil(n₀/(1+n₀/N)) × (1−q)`）し、「以降は `u = n × (1−q)` と書くが入力は 3 種のみ」と註記 |
| S5 | 「`n_eff`・`p̂` は上の式の値」 | 同様に展開 |

Opus は「同一ステージ内の先行する式の値（`n`・`n_eff`・`p̂`）が 3 種に無い」ことを共通の原因とし、ルール側に「中間量を展開した式を併記し、展開後の入力が 3 種に還元できることを示す」を足す案を出したうえで、判断をユーザーに委ねた。

### 1.2 Claude Code（Fable）の分析とユーザーとの確定

- **`n`・`n_eff`・`p̂` は入力ではなく、式の一部に名前を付けたもの**。`u = n × (1 − q)` の `n` にはロードマップ内に `n = ceil(n₀/(1 + n₀/N))` があり、その入力は `N`（S2）と定数である。`u` の式の入力（ステージの外から入る量）は最初から 3 種に収まっている。Opus は「式に現れる記号すべてに由来のラベルが要る」と読み、update-014 の「入力ごとに名指しする」がその読みを誘った
- Claude Code が最初に提案した文（「式の中でそれ以上式を持たない末端の記号」「式を持つ記号は辿る」）は、**ユーザーが「読んで意味が分からない。どうとでも解釈できそう」と却下**。規定に無い概念（末端・式を持つ・辿る）を 3 つ持ち込み、`N` も §6 の抽出規則という式を持つため辿りが止まらず、結局「入力かどうか」を読み手の判断に委ねていた
- **入力と出力だけで言い直した定義**: 「想定値の式の入力とは、そのステージの外から入る量をいい、3 種はその全部である。同じステージの式で先に計算する量は入力ではなく式の途中の値であり、由来を書かない」。feat-025 の想定値の入力を全件当てて例外が無いことを確認した（§2）
- **境界の 1 件**: S5 が使う `n` は S4 で `N` から計算した値で、測ったものではない。Opus は「前のステージの実測〔S4 が算出して確定〕」と書いて「実測」を計算値まで広げていた。規定の語を「前のステージの出力（`experiment_log.md` に記録した値）」に改めれば広げずに済む
- **例外が出たときの動作**: ユーザー「例外規定がないと Opus は後付けの理由をひねり出す」。例外のラベルではなく動作を固定する。3 種は「ステージの外から入る量」を尽くしたものなので、当たらない入力はステージの切り方の問題である。動作は**順に判定し最初に当てはまった 1 つを行う分岐**（ユーザー「条件分岐の文なら最初にそう書け」）: (1) 測れるものなら測るステージを前に置く (2) 自分のステージの前回の実行結果なら繰り返しを別のステージに分ける（次元の変更） (3) どちらでもなければ止まって報告する。その行は不適合のままで、規定を直すまでロードマップは収束しない。後付けの理由が効かないのは、検査側（update-014）が 3 種以外のラベルを値の正否に関係なく不適合とするため

### 1.3 目的

1. 「入力」を入力・出力の語で定義し、同じステージで先に計算する量（途中の値）に由来を書かせない。展開の併記も求めない
2. 3 種の 1 つ目の語を「前のステージの出力（`experiment_log.md` に記録した値。実測値と計算して確定した値の両方）」に改める
3. 3 種に当たらない入力が出たときの動作を、順序つきの分岐で規定に書く。検査側は「規定に無い」と明記された行を不適合（高）として報告し、収束させない

### 1.4 採らなかった案と不採用の理由

| 案 | 不採用の理由 |
|---|---|
| 由来に 4 種目「同一ステージ内の中間量」を足す（Opus も否定） | 中間量を由来として認めると、その中間量の入力を追わずに済み、update-014 で塞いだ「ラベルだけで通る」穴が別の形で開く |
| 中間量を展開した式の併記を要求する（Opus 案） | 入力の定義があれば展開は不要。多段になると式が読めなくなる。展開して書くこと自体は不適合ではない（feat-025 第2版はそのままでよい） |
| 「末端の記号」「式を持つ記号を辿る」で入力を定義する（Claude Code の最初の案） | ユーザー却下。規定に無い概念を 3 つ持ち込み、`N` の抽出規則まで辿ってしまい、判断を読み手に委ねる |
| 例外のラベル（「その他」等）を置く | Opus がそこに何でも入れる。ラベルでなく動作を固定する |
| 例外時の動作 (1)〜(3) を並列に書く | ユーザー「並列なのか順番なのか読みづらい。条件分岐なら最初にそう書け」。順に判定し最初に当てはまった 1 つを行うと明記 |
| ステージ表の処理単位・単位数を「定数」の例として加える | Opus の判断（ステージ表で固定した値だから定数）は現行の語で読めており、今回の 3 点の範囲外。必要になれば次の改訂で加える |
| feat-025 の `roadmap.md` を本案件で直す | 元案件側。展開版のまま人レビューを通して M1 に進めてよい（展開は不適合ではない） |
