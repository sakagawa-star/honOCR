# feat-006 要求仕様書: OCR 一括実行スクリプト（ocr_dir.py）

## 1.1 プロジェクト概要

- **何を作るのか**: TIF ディレクトリ1個以上を入力に取り、「入力PDF 生成 → MinerU 変換 → 句読点正規化 → 機械確認」を一括実行する CLI `scripts/ocr_dir.py`
- **なぜ作るのか**: 現在は各ステップを Claude Code が手動でつないでおり、OCR のたびに Claude Code の使用量を消費する。ユーザー自身のターミナルだけで OCR を完結できるようにする
- **誰が使うのか**: ユーザー本人
- **どこで使うのか**: 本リポジトリの uv 環境（Linux、CUDA GPU、プロキシ必須ネットワーク）。`uv run python scripts/ocr_dir.py ...` で起動する

## 1.2 用語定義

feat-005 requirements.md の用語（`{ROOT}`・全TIF・白紙ページ・MinerU 生出力・content list・正規化・機械確認・run ディレクトリ）を継承する。追加分:

| 用語 | 定義 |
|---|---|
| 入力ディレクトリ | 補正済み TIF が置かれたディレクトリ（例: `{BASE}/chap03/out`） |
| name | 出力の識別名。入力ディレクトリのベース名。ただしベース名が `out` の場合は親ディレクトリ名（例: `.../chap03/out` → `chap03`） |
| 対象TIF | 入力ディレクトリ直下でパターン `page-*_1L.tif`・`page-*_2R.tif` のいずれかに一致するファイルを辞書順に並べた列（既定。feat-005 の全TIF 定義と同一。上級オプションで変更可） |
| manifest | 入力PDF 生成時に隣に記録する JSON（対象TIF の絶対パス・サイズ・mtime の一覧）。PDF が「どの入力から作られたか」を固定し、再利用時の同一性検証に使う |

## 1.3 機能要求一覧

### FR-001: 一括パイプライン実行

- **機能名**: ディレクトリ単位の OCR 一括実行
- **概要**: 入力ディレクトリごとに次を順に実行する: (1) 対象TIF の列挙と白紙位置の検出 → (2) 入力PDF 生成（`make_ocr_pdf.py` 相当の呼び出し） → (3) MinerU 変換（`no_proxy` 設定込み・実行ログ保存） → (4) 句読点正規化（`normalize_punct.py` 相当の呼び出し） → (5) 機械確認（FR-002）
- **入力**: 入力ディレクトリ1個以上（位置引数）、出力先ルート `-o {ROOT}`（必須）
- **出力**: feat-005 と同一レイアウト — `{ROOT}/pdf/{name}_gray300.pdf`、`{ROOT}/mineru-full/{name}/run-NN/`（MinerU 生出力＋ `run-NN.log`）、`{ROOT}/mineru-full/{name}/run-NN-normalized/`（正規化済み md・content list）
- **受け入れ基準**:
  1. `uv run python scripts/ocr_dir.py {BASE}/chapNN/out -o {ROOT}` の1コマンドで、上記 (1)〜(5) が人手の介在なく完走する
  2. ページの除外・並べ替えを行わない（対象TIF 全数を辞書順のまま処理する。feat-005 のスコープ外定義と同じ）
  3. run 番号は実行ごとに自動で加算され（run-01, run-02, …）、過去の run を上書きしない
  4. 入力PDF が既に存在する場合、**manifest が存在し、その内容（対象TIF の絶対パス・サイズ・mtime の列）が現在の対象TIF と完全一致し、かつ PDF ページ数が対象TIF 数と一致する場合のみ**再利用する。manifest がない・一致しない場合は再利用せず不合格とし、`--overwrite-pdf` での作り直しを案内する（`--overwrite-pdf` 指定時は常に作り直し、manifest も書き直す）
  5. PDF のページ数検証（= 対象TIF 数）は **MinerU 実行前**に行う（不一致の PDF で長時間の MinerU を走らせない）
  6. 複数ディレクトリ指定時は逐次処理し（MinerU の並列実行をしない）、あるディレクトリが失敗しても残りを継続する

### FR-002: 機械確認の組み込み

- **機能名**: 変換結果の機械確認
- **概要**: feat-005 design §4.2/§4.3 の機械確認をスクリプト内に恒久化する
- **入力**: FR-001 の各ステップの出力
- **出力**: 確認結果（標準出力のサマリ）と終了コード
- **受け入れ基準**（各ディレクトリについて、以下のすべてを自動確認する）:
  1. 入力PDF のページ数 = 対象TIF 数（pypdf で確認。FR-001 基準5のとおり MinerU 実行前に実施する）
  2. MinerU 終了コード 0、md が存在しサイズ > 0
  3. content list が非空で、全ブロックが整数 `page_idx` を持ち、範囲外（≥ ページ数）の値がなく、欠落ページが白紙位置（サイズ 10,240 バイト未満の対象TIF の 0 始まり位置）の部分集合である
  4. 正規化前後でコードポイント数が一致し、差分が「、→，」「。→．」のみで、正規化後の残存「、」「。」が 0 件（md・content list の両方）
  5. いずれかが不合格の場合、そのディレクトリの処理を不合格として理由を標準エラーに出力する

### FR-003: CLI・エラー処理

- **機能名**: CLI 仕様とエラー処理
- **概要**: argparse による引数解析と、失敗時の明確な報告
- **入力**: コマンドライン引数
- **出力**: 終了コード（全ディレクトリ合格 = 0、1件でも不合格 = 1、引数エラー = 2）と、ディレクトリごとの合否サマリ（標準出力の最終部）
- **受け入れ基準**:
  1. 入力ディレクトリが存在しない・対象TIF が 0 件の場合、そのディレクトリを不合格として明確なメッセージを出す
  2. MinerU 非0終了・タイムアウト（既定 60 分/ディレクトリ、`--timeout` で変更可）時は、ログファイルのパスを添えて不合格として報告する
  3. `--name` は入力ディレクトリが1個のときのみ指定可（複数指定との併用はエラー・終了コード 2）
  3b. 複数ディレクトリ指定時、導出される name が重複する場合は処理を開始せずエラー（終了コード 2。同一 name の出力が混ざるのを防ぐ）
  4. 実行終了時に「ディレクトリ名 / 合否 / 主要数値（ページ数・置換件数）」の一覧を標準出力に表示する

### FR-004: 自動テスト

- **機能名**: pytest による自動テスト
- **概要**: GPU・MinerU 実行を伴わずにテストできる範囲（名前導出・白紙検出・run 番号・page_idx 検査・正規化検査・CLI 引数検証）をテストする
- **入力**: `tests/test_ocr_dir.py`
- **出力**: `uv run pytest -v` 全件 PASS、結果を `tests/results/feat-006_test_result.txt` に保存
- **受け入れ基準**: 検査ロジック（FR-002 基準3・4）の合格・不合格の両系をテストで固定する

## 1.4 非機能要求

- **処理時間**: スクリプト自体のオーバーヘッド（MinerU 実行を除く）は1ディレクトリあたり 60 秒以内
- **対応環境**: 本リポジトリの uv 環境（Python 3.12）。MinerU 実行には CUDA GPU が必要。プロキシ必須ネットワークで動作すること（`no_proxy` への `localhost,127.0.0.1` 追加をスクリプト内で行う）
- **信頼性**: 入力ディレクトリの内容を変更しない。過去の run ディレクトリ・既存 PDF を暗黙に上書きしない

## 1.5 制約条件

- **使用必須**: Python 3.12 標準ライブラリ＋既存導入済みの pypdf（現在 dev group 所属のため、本案件で通常依存へ移動する — `pyproject.toml` の変更と `docs/TECH_STACK.md` の用途更新を伴う。新規パッケージのインストールは発生しない）。MinerU は `mineru` CLI をサブプロセスとして呼ぶ（`mineru==3.4.4`、既定バックエンド・オプション指定なし）
- **既存スクリプトの再利用**: PDF 生成と正規化は `scripts/make_ocr_pdf.py`・`scripts/normalize_punct.py` を**サブプロセスとして**呼び出す（import はしない — feat-004 ADR-3 のスクリプト間 import 禁止方針を維持しつつ、実装の重複も避ける）。両スクリプトは改変しない
- **使用禁止**: 新規ライブラリの追加
- **出力レイアウトの固定**: feat-005 と同一（§1.3 FR-001）。feat-005 の残り処理を本スクリプトで実行できること
- **final 構築は含めない**: `{ROOT}/final/` への集約は本スクリプトの対象外（feat-005 §4.4 の手順で行う）
