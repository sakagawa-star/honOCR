### 2.2 何が起きるか

機能追加案件のステップ4（requirements.md / design.md のレビュー）で C を1回使うと、同じ案件内の
criteria 文書のレビューでは C を打てない。すると:

- C を実施できない → 収束の定義（ゲートの会話で高・中ゼロ）を満たせず、「人（ユーザー）レビューの前提（必須）」
  （227行目: 全文ゲートを実施済みであること）も満たせない
- 「逸脱の禁止」（遷移表にない動きをしない、迷ったら止まってユーザーに確認）により、別サイクルを
  独断で始めることもできない

結果として、**criteria lock を伴う実験案件が運用上デッドロックする**。

### 2.4 テンプレート側で採った解決（本案件でも同じ解決を採る）

C の上限単位を「案件」から **「レビュー単位」** に変更する。レビュー単位とは、**初回レビュー（A）で
対象ファイルとして指定した文書一式**である。

| レビューの場面 | レビュー単位 |
|---|---|
| 案件のフローのステップ4（requirements.md / design.md 等） | 案件につき1単位 |
| 案件を細分化して並列に進める場合 | 細分化単位ごとに1単位 |
| 実験・検証の criteria 文書のレビュー（criteria lock） | criteria 文書ごとに1単位 |

**同一の文書一式は、指摘を反映して内容を修正した後も同一のレビュー単位である**（同じ一式を A に
指定し直すこと・分割し直すこと・ストリームを変えることによって新しいレビュー単位にはならない）。
新しいレビュー単位のレビューは遷移表の「（開始時）」の行から始める（同一案件のストリームで続けてよい。
結果の保存は案件の連番を進める）。

上記の太字の1文は**テンプレート側には無い**。全文ゲート（codex-02）が「レビュー単位の同一性が
規定されておらず、同じ一式を A に指定し直せば C を何度でも実施できる」と重要度「高」で指摘したため、
ユーザー決定（2026-09-04）により honOCR 版にのみ追加した（`design.md` §8.1）。

「1回ゲート型」の趣旨（**同じ文書一式に「新しい目」を2回使わない**）は変わらない。update-002 が確定した
意図——新しいレビュアーが毎回新しい指摘を見つけて収束しなくなることを防ぐ——は、対象となる文書一式が
異なれば適用対象も異なるため、単位の明確化によって損なわれない。
