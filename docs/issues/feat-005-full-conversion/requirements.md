# feat-005 要求仕様書: 全スキャンデータの本処理（ディレクトリ単位の高精度 OCR）

## 1.1 プロジェクト概要

- **何を作るのか**: PRML スキャンデータの全8ディレクトリ（chap00〜chap07、補正済み TIF 計396枚）について、各ディレクトリの**全ファイル**を対象に MinerU 変換＋句読点正規化を適用し、ディレクトリ単位の Markdown（LaTeX 数式入り）と content_list.json を最終成果物ディレクトリに確定させる
- **なぜ作るのか**: プロジェクトの主目的「書籍を LLM が読める形式に変換する」の主成果物を得るため。ゴールは**入力ファイルに対する高精度な OCR 結果そのもの**であり、ページの取捨選択や再構成は目的に含まれない
- **誰が使うのか**: ユーザー本人（LLM に Markdown を渡して勉強する）
- **どこで使うのか**: 本リポジトリの uv 環境（Linux、RTX 5060 Ti、プロキシ必須ネットワーク）。成果物はリポジトリ外のデータディレクトリに置く

### スコープ外（明示）

以下は行わない（2026-08-18 ユーザー指示。編集的な加工はゴールの書き換えに当たる）:

- 白紙ページ・重複スキャンページの除外
- 章境界の再定義、ディレクトリをまたぐページの組み替え、ページの並べ替え
- feat-003 の章対応（chap-00/chap-01 分割）の適用。chap01 は全84枚を1単位として扱う

## 1.3 機能要求一覧

### FR-001: 入力PDF の生成（8ディレクトリ）

- **機能名**: ディレクトリ単位の入力PDF 生成
- **概要**: 対象ディレクトリごとに全TIF を辞書順で `make_ocr_pdf.py` に渡し、入力PDF を生成する
- **入力**: 各対象ディレクトリの全TIF（除外なし）
- **出力**: `{ROOT}/pdf/chapNN_gray300.pdf`（NN = 00〜07）
- **受け入れ基準**:
  1. `make_ocr_pdf.py` が8ディレクトリとも終了コード 0 で完了する
  2. `pdfinfo` のページ数が chap00 = 20、chap01 = 84、chap02 = 70、chap03 = 44、chap04 = 48、chap05 = 70、chap06 = 36、chap07 = 24 と一致する
  3. 実行前に入力ファイル列の枚数が上記と一致することを確認する（不一致なら実行せず中断して報告する — TIF の追加・削除があった場合は調査に戻る）

### FR-002: MinerU 変換（8ディレクトリ）

- **機能名**: 入力PDF の MinerU 変換
- **概要**: FR-001 の8つの PDF を MinerU 3.4.4（既定バックエンド hybrid-engine）でディレクトリごとに変換する
- **入力**: `{ROOT}/pdf/chapNN_gray300.pdf`（NN = 00〜07）
- **出力**: `{ROOT}/mineru-full/chapNN/run-NN/` 配下の MinerU 生出力一式、および実行ログ `run-NN.log`
- **受け入れ基準**（8ディレクトリそれぞれについて）:
  1. `mineru` コマンドが終了コード 0 で完了する
  2. `chapNN_gray300.md` が存在し、サイズが 0 バイトでない
  3. content list が存在し非空で、全ブロックが整数の `page_idx` を持ち、`page_idx` の値がすべて {0, 1, …, ページ数−1} の範囲内であり、この範囲のうち `page_idx` に現れないページが**白紙ページの位置の部分集合**である（白紙以外のページが1つでも欠けている場合、または範囲外の値がある場合は、その番号を報告して中断する）
  4. 追加のモデルダウンロードが発生しない（8ディレクトリの全実行を通じて `~/.cache` サイズ差が 100MB 未満）

### FR-003: 句読点正規化と機械確認（8ディレクトリ）

- **機能名**: MinerU 出力の句読点正規化
- **概要**: FR-002 の各生出力のうち md と content list の2ファイルに `normalize_punct.py` を適用し、機械確認で「差分が許可置換のみ」であることを確認する
- **入力**: FR-002 の各 `chapNN_gray300.md`・`chapNN_gray300_content_list.json`
- **出力**: `{ROOT}/mineru-full/chapNN/run-NN-normalized/` 配下の正規化済み2ファイル
- **受け入れ基準**（8ディレクトリそれぞれについて）:
  1. `normalize_punct.py` が終了コード 0 で完了し、2ファイルとも出力される
  2. 機械確認に2ファイルとも合格する: 正規化前後でコードポイント数が一致し、差分位置の変化が「、→，」「。→．」のみで、正規化後の残存「、」「。」が 0 件
  3. 機械確認に不合格のディレクトリがある場合、final の構築（FR-004）に進まず中断して報告する

### FR-004: final ディレクトリの構築（8ディレクトリ）

- **機能名**: 最終成果物の集約
- **概要**: 全8ディレクトリの正規化済み md・content_list.json と images/ を `{ROOT}/final/` に集約する
- **入力**: FR-003 の正規化済み2ファイル、feat-007（`colorize_images.py`）でカラー再切出した `run-NN-normalized/images/`（グレーの MinerU 生出力 `images/` は final に含めない）
- **出力**: `{ROOT}/final/chapNN/`（NN = 00〜07）それぞれに `chapNN_gray300.md`・`chapNN_gray300_content_list.json`・`images/`（ファイル名は元のベース名を維持する）
- **受け入れ基準**:
  1. 全8ディレクトリ × 3項目（md・content_list.json・images/）がすべて存在する
  2. md・content_list.json 計16ファイルについて、コピー元とコピー先で内容がバイト同一（`cmp` で確認）
  3. 各 md が参照する画像ファイル名（`images/<name>` 形式の参照を md から抽出したもの）がすべて `final/chapNN/images/` 内に存在する
  4. 各ディレクトリで content_list の `img_path` ユニーク数と `final/chapNN/images/` 内のファイル数が一致する（カラー再切出の完了確認。図ブロック 0 件の章は 0 件で可）
  5. **final は全8ディレクトリが揃って初めて構築する**。実施前条件は「全8ディレクトリで FR-001〜FR-003 が合格し、かつ feat-007 のカラー再切出が完了（content_list の `img_path` ユニーク数 = `run-NN-normalized/images/` のファイル数）していること」。FR-001〜FR-003 で中断したディレクトリ、またはカラー再切出が未了のディレクトリが1つでもある場合は FR-004 を実施せず、合格済み分は `run-NN-normalized/` までの中間成果物として残し、中断分と合わせて報告する。中断の解消（ドキュメント改訂または bug 案件）後に FR-004 を実施する

## 1.4 非機能要求

- **処理時間**: MinerU 変換は1ディレクトリあたり 60 分以内に完了すること（feat-003 実測: 64ページで 6分26秒。最大の chap01 は 84ページで約8.5分の見積もり。60分超過時は中断して報告する）
- **対応環境**: 本リポジトリの uv 環境（Python 3.12、mineru 3.4.4、CUDA GPU 必須）。プロキシ必須ネットワークで動作すること
- **信頼性**: 既存データ（各ディレクトリの TIF、`chap01/out/ocr/` 配下の feat-003/004 成果物、閲覧用PDF）を変更・削除しないこと。final への集約はコピーで行い、コピー元を残すこと
- **ディスク**: 実行前に `{BASE}` のあるファイルシステムの空き容量が 20GB 以上あることを確認する（run-02 実績: 64ページの生出力で約1GB 未満。8ディレクトリ・計396ページ分でも余裕を持つ）

## 1.5 制約条件

- **使用必須**: `mineru==3.4.4`（既定バックエンド hybrid-engine、オプション指定なし。feat-003/004 の品質確認条件と揃える）、`scripts/make_ocr_pdf.py`（feat-002。改変しない）、`scripts/normalize_punct.py`（feat-004。改変しない）
- **使用禁止**: 新規ライブラリの追加（既存の uv 環境のみで完結させる）
- **ネットワーク制約**: MinerU 実行時は `no_proxy`/`NO_PROXY` に `localhost,127.0.0.1` を追加すること（大学プロキシがローカル API ヘルスチェックを 502 にするため。feat-003 で確立）
- **入力の忠実性**: 対象ディレクトリの全TIF を辞書順のまま処理する。ページの除外・追加・並べ替えは禁止（§1.1 スコープ外のとおり）
- **環境変更の承認**: MinerU 実行（長時間ジョブ）の開始は、本案件ドキュメントの人レビュー承認をもって承認とみなす（feat-003 と同じ扱い）

## 品質確認の扱い（本案件で数値判定を行わない理由）

- パイプラインの品質（数式・本文・読み順）は feat-003/004 で criteria lock 済みの基準により chap01 のデータ（64枚サブセット）で判定し、**Go が確定している**（ユーザー二次確認済み 2026-08-17）。本案件は確立済みパイプラインの適用であり、新たな品質判定（Go/No-Go）は行わない
- 本案件の検証は、受け入れ基準に列挙した**機械確認**（終了コード・ファイル存在・ページ数・page_idx 検査・コードポイント比較・バイト同一・画像参照整合）と、手動テストでの**ユーザー目視確認**（Markdown を原本と見比べる。合否ラインを設けた判定ではなく、問題発見時は BUGFIX_STANDARD に従い修正計画を立てる）に限定する
- したがって「実験・検証の進め方（予測→実行→照合）」プロトコルの対象となる数値判定実験はない。MinerU 実行等の実測値（所要時間・置換件数）は参考記録として案件フォルダに残すが、Go/No-Go 判定には使わない
