# feat-013 要求仕様書: 字形正規化テーブルの拡充と確率統計への適用

## 1. プロジェクト概要

### 何を作るのか

`scripts/normalize_punct.py` の字形正規化テーブル `CJK_REPLACEMENTS` に中国語字・旧字体13種を
追加し（8種 → 21種）、既に構築済みの『プログラミングのための確率統計』の成果物へ再適用する。
あわせて、字形の対応関係では直せない個別の誤認識と、置換によって壊れる固有名詞を
`apply_fixes.py` の修正定義ファイルで補正する。

### なぜ作るのか

2026-08-28 に確率統計の全10章（383ページ）を処理したところ、feat-011 で導入した
「JIS X 0208 外漢字の警告」（FR-003）が、置換表に未登録の中国語字を9種検出した。
さらに調査したところ、**JIS X 0208 内にあるため警告に現れない旧字体が4種**含まれていた。

これらは日本語の数学書の本文として誤りであり、LLM に読ませる成果物の品質を下げる。
置換表は feat-011 で PRML 1冊分の実測のみを根拠に作られており、2冊目のデータで
不足が明らかになった形である。

### 誰が使うのか

本プロジェクトのユーザー（`ocr_dir.py` を直接実行する）。置換表の拡充は
以後すべての書籍の処理に自動的に反映される。

### どこで使うのか

`docs/TECH_STACK.md` に定義された既存環境（Ubuntu 24 系 / Python 3.12.3 / uv）。
新規のライブラリ・モデル・ネットワークアクセスは追加しない。

## 2. 用語定義

feat-011 要求仕様書 §2 の用語をそのまま用いる。本書で新たに使う用語は次のとおり。

| 用語 | 定義 |
|---|---|
| 字形正規化 | `normalize_punct.py` が中国語字・旧字体を対応する日本語字へ置換する後処理（feat-011）。対象は Markdown と content_list.json の両方 |
| 個別誤認識 | 字形の 1 対 1 対応が成立しない OCR 誤り（例: 「揾」→「掟」）。置換表では扱わず `apply_fixes.py` の修正定義ファイルで補正する（feat-011 ADR-3） |
| 固有名詞の復元 | 字形正規化によって正しい表記が壊れる固有名詞を、修正定義ファイルで元に戻すこと（本案件で新たに導入する運用。§3 FR-003） |
| 再適用 | 既に構築済みの成果物（`run-NN-normalized/` と `final/`）に対し、MinerU を再実行せずに正規化・修正適用・final 再構築のみを行うこと |

## 3. 機能要求一覧

### FR-001: 字形正規化テーブルの拡充

- **機能名**: `CJK_REPLACEMENTS` への13種の追加
- **概要**: 確率統計の本処理で検出された中国語字・旧字体を置換表に追加する
- **入力**: `scripts/normalize_punct.py` の定数 `CJK_REPLACEMENTS`（現在8種）
- **出力**: 次の13種を追加した21種の置換表

  | 置換前 | 置換後 | 種別 | 確率統計での件数（md / json） |
  |---|---|---|---|
  | 黑 | 黒 | 簡体字 | 12 / 12 |
  | 說 | 説 | 繁体字 | 2 / 2 |
  | 题 | 題 | 簡体字 | 2 / 2 |
  | 戾 | 戻 | 繁体字 | 2 / 2 |
  | 边 | 辺 | 簡体字 | 3 / 3 |
  | 橫 | 横 | 繁体字 | 1 / 1 |
  | 虛 | 虚 | 繁体字 | 1 / 1 |
  | 錄 | 録 | 繁体字 | 0 / 2 |
  | 權 | 権 | 旧字体 | 3 / 3 |
  | 收 | 収 | 旧字体 | 2 / 2 |
  | 檢 | 検 | 旧字体 | 2 / 2 |
  | 縱 | 縦 | 旧字体 | 1 / 1 |
  | 廣 | 広 | 旧字体 | 1 / 1 |

- **受け入れ基準**:
  1. 上表13種を含む入力に対し、出力では13種が1件も残らない
  2. 既存8種（值・变・单・对・图・换・徵・樣）の置換が従来どおり行われる
  3. 置換前後で文字列長が変わらない（すべて1文字→1文字の置換である）
  4. 置換表のキーに重複がない（21種すべてが異なる文字である）
  5. 句読点スタイル（`comma` / `touten`）によらず適用される（feat-011 FR-002 と同じ）

### FR-002: 確率統計の既存成果物への再適用

- **機能名**: 構築済み成果物の再正規化と final 再構築
- **概要**: MinerU を再実行せず、`run-NN-normalized/` と `final/` を更新する
- **入力**: `{BASE2}/ocr/mineru-full/chapNN/run-NN-normalized/`（NN = 00〜09。chap07 のみ run-02）
  （`{BASE2}` = `/home/sakagawa/work/確率統計`）
- **出力**: 更新された `run-NN-normalized/` と、そこから再構築された `{BASE2}/ocr/final/chapNN/`
- **受け入れ基準**:
  1. 全10章について、更新後の md・content_list.json に FR-001 の13種と既存8種が
     1件も残らない（ただし FR-003 で固有名詞として復元する箇所を除く）
  2. 更新前後で md・content_list.json の文字列長が変わらない
     （字形置換は1文字→1文字であり、FR-003 の修正も同じ文字数であるため）
  3. 更新後も句読点「、」「。」が保持される（`--punct-style touten` を用いる）
  4. 全10章で `final/chapNN/` が再構築され、`build_final.py` の3種類の機械検証に合格する
  5. 再構築後、`final/chapNN/` の md・content_list.json が
     `run-NN-normalized/` のものとバイト単位で一致する
  6. `images/` の内容が変化しない（本案件は画像を扱わない）
  7. MinerU を再実行しない（`run-NN/` 配下の生出力を変更しない）
  8. **再適用の前に、旧字体5種（權・收・檢・縱・廣）の全出現箇所を
     md と content_list.json の両方について列挙し、固有名詞かどうかを分類する**。
     分類結果を案件ドキュメントに記録し、固有名詞であれば修正定義ファイルに
     復元を登録してから再適用に進む
     （2026-08-28 に実施済み。md 9件・json 9件のうち固有名詞は chap09 の「廣済堂」のみ）。
     **ただし復元が適用されるのは md のみである**（`apply_fixes.py` は md 専用。基準9）
  9. **固有名詞の復元は md にのみ適用される**。content_list.json 側は
     正規化された表記（例: 「広済堂」）のままとなる。これは
     `apply_fixes.py` が md のみを扱う既存設計（feat-010）によるものであり、
     本案件で変更しない。許容する理由は次のとおり:
     - LLM に読ませる主成果物は md である（プロジェクトの主目的）
     - content_list.json は MinerU のスキーマを保った中間データであり、
       主用途は `page_idx` による原本ページとの対応付けと図ブロックの座標参照である
       （feat-005 ADR-7）
     - 個別誤認識（「揾」等）についても同じ非対称性が既に存在する（FR-003 基準7）

### FR-003: 修正定義ファイルの作成と適用

- **機能名**: 個別誤認識の補正と固有名詞の復元
- **概要**: 置換表で扱えない4件と、置換によって壊れる固有名詞1件を修正定義ファイルに登録する
- **入力**: `{BASE2}/ocr/fixes/chapNN.json`（新規作成。**書籍本文の文字列を含むためリポジトリに置かない**）
- **出力**: 次の5件の修正（すべて原本 TIF で目視確認済み。2026-08-28）

  | 章 | 種別 | 誤 | 正 | 原本での確認内容 |
  |---|---|---|---|---|
  | chap02 | 個別誤認識 | `\underline {{\text {亻}}} \| Y` | `\underline {{\text {イ}}} \| Y` | p23 の式 `P(X = イ\|Y = ウ, Z = ア)`。選択肢はカタカナ |
  | chap04 | 個別誤認識 | `という揾に反して` | `という掟に反して` | p54 の脚注 *19「…という掟に反してしまうからです」 |
  | chap05 | 個別誤認識 | `—— 椕円` | `—— 楕円` | p43 の見出し「5.4.2 （ケース 2）対角行列の場合 —— 楕円」 |
  | chap06 | 個別誤認識 | `\dots \dots (\text {亻})` | `\dots \dots (\text {イ})` | p12 の式番号「……（イ）」 |
  | chap09 | 固有名詞の復元 | `印刷·製本 広済堂` | `印刷·製本 廣済堂` | 奥付。**廣済堂は旧字を正式名称に用いる実在の社名**であり、FR-001 の `廣→広` によって壊れるため元に戻す |

- **受け入れ基準**:
  1. 5件すべてが `apply_fixes.py` により適用され、`applied` として報告される
  2. 適用後の md に誤りの文字列が1件も残らない
  3. **各修正の `new` が、適用後の md にちょうど1件だけ存在する**
     （`apply_fixes.py` の最終不変条件）。`new` が他所に正当に存在する場合は、
     一意になるまで `old` / `new` の両方に前後の文脈を含めること
     （機能設計書 §5.6 に確定値の表がある）
  4. `apply_fixes.py` を**2回連続で**実行したとき、2回目は全件 `skipped`（適用済み）となり
     md が変化しない（`apply_fixes.py` 単体の冪等性）
  5. **再適用の3ステップ全体（正規化 → 修正適用 → final 再構築）を繰り返したときは、
     最終的な出力内容が毎回同一になる**（内容の冪等性）。ただし chap09 の固有名詞の復元は、
     手順1の正規化が `廣→広` を再適用するため、手順2で毎回 `applied` として報告される。
     これは設計どおりの挙動であり、`skipped` にはならない
     （報告される件数ではなく、出力内容が不変であることをもって冪等とみなす）
  6. chap09 の復元後、`廣済堂` が md 内にちょうど1件存在する
  7. 修正定義ファイルの実体をリポジトリにコミットしない（feat-010 の公開分離ポリシー）
  8. **content_list.json は修正の対象外**とする（`apply_fixes.py` は md のみを扱う。feat-010 の設計）。
     そのため content_list 側には個別誤認識（「揾」等）が残り、
     **固有名詞の復元も行われない**（chap09 の json は「広済堂」のままとなる）。
     これは MinerU スキーマを維持するための既存ポリシーによるものであり、本案件で変更しない
     （許容の理由は FR-002 基準9 に記す）

### FR-004: PRML への非影響の確認

- **機能名**: 既存書籍への影響がないことの確認
- **概要**: FR-001 の13種が PRML の成果物に影響しないことを実測で確認する
- **入力**: `{BASE}/ocr/final/chapNN/`（`{BASE}` = `/home/sakagawa/work/Pattern_Recognition_and_Machine_Learning`）
- **出力**: 検証結果の報告
- **受け入れ基準**:
  1. PRML の final（md 8ファイル・content_list.json 8ファイル）に FR-001 の13種が
     **1件も出現しない**（2026-08-28 の実測値は 0 件）
  2. したがって PRML の成果物は再適用の対象外とし、**変更しない**

### FR-006: 旧字体の置換箇所の警告出力

- **機能名**: 旧字体を置換した箇所の報告
- **概要**: 旧字体は固有名詞では正当な表記になりうるため、置換した箇所を
  **置換前の文脈つきで**標準エラーへ報告し、ユーザーが固有名詞かどうかを判断できるようにする
- **入力**: 追加のオプションは設けない（常時実行する）
- **出力**: 標準エラーへ、ファイルごとに次の形式で出力する
  - 1行目: `{ファイル名}: 旧字体 {字種数} 種 {総件数} 件（固有名詞の可能性。必要なら fixes で復元すること）`
  - 2行目以降: 字種ごとに `  '{置換前}'→'{置換後}' x{件数}: ...{置換前の前後25文字の文脈}...`
    （文脈は最初の1件のみ、改行は空白に置換する）
  - 旧字体が0件のファイルについては何も出力しない
- **受け入れ基準**:
  1. 「廣済堂」を含む入力に対し、`'廣'→'広' x1: …印刷·製本 廣済堂…` の形式で警告が出る
  2. 警告の文脈は**置換前**の文字列である（置換後では元の字が失われ、
     固有名詞かどうかを判断できないため）
  3. 警告が出ても終了コードは 0 のままである（警告であって失敗ではない）
  4. 旧字体5種（權・收・檢・縱・廣）のみが対象であり、簡体字・繁体字16種は警告しない
     （日本語で正当に使われることがないため）
  5. `ocr_dir.py` はこの警告を素通しし、FAIL にしない（feat-011 FR-004 基準7 と同じ扱い）

### FR-005: 自動テスト

- **機能名**: 変更点の自動テスト
- **概要**: 置換表の拡充について自動テストを追加し、既存テストを維持する
- **入力**: `uv run pytest -v`
- **出力**: `tests/results/feat-013_test_result.txt`（コマンド出力をそのまま保存）
- **受け入れ基準**:
  1. 既存テスト206件がすべて PASS する
  2. FR-001 および FR-006 の受け入れ基準に対応するテストが追加され、すべて PASS する
  3. 実データに依存するテストを含めない（テストはリポジトリ内で自己完結する）

## 4. 非機能要求

- **パフォーマンス**: 置換表が8種から21種に増えることによる `normalize_text` の処理時間の増加は、
  変更前の 2 倍を超えないこと（`str.translate` は文字数に対して線形であり、
  置換表のサイズにほぼ依存しない）
- **対応環境**: Ubuntu 24 系 / Python 3.12.3 / uv。GPU は使用しない
- **信頼性**:
  - 再適用は MinerU 生出力（`run-NN/`）を変更しない
  - `final/` の更新は `build_final.py` の検証（バイト同一・画像参照・`img_path` 集合の一致）に合格すること
  - PRML の成果物を変更しないこと
- **後方互換性**: `normalize_punct.py` / `ocr_dir.py` の CLI インターフェースを変更しない
  （置換表の内容のみが変わる）

## 5. 制約条件

- 使用必須: 既存のスクリプト（`normalize_punct.py` / `apply_fixes.py` / `build_final.py`）のみ。
  新規スクリプト・新規ライブラリは追加しない
- 修正定義ファイルの実体は `{BASE2}/ocr/fixes/` にのみ置き、リポジトリにコミットしない（feat-010）
- 置換表に追加してよいのは「日本語字への 1 対 1 対応が確立している文字」に限る。
  字形の対応関係が成立しない誤認識は `apply_fixes.py` で扱う（feat-011 ADR-3 を踏襲）
- MinerU の再実行を行わない（約35分かかるうえ、OCR 結果は変わらないため）

## 7. 参考: 本案件で判明した既存機能の制約（変更しない）

feat-011 の JIS 外漢字警告（FR-003）は**正規化の時点**で出力される。
`insert_footnotes.py`（feat-009）は正規化より後の工程で content_list から md へ
脚注を挿入するため、そこで持ち込まれる文字は md 側の警告に現れない。

実例: chap04 の「揾」は正規化時点の警告では content_list 側にのみ 1 件計上され、
md 側は 0 件だった。しかし脚注挿入後の最終的な md には 1 件存在する。

content_list は全ブロックを保持しているため**警告の検出漏れは生じない**（json 側で必ず検出される）。
運用上は「json 側の警告を正とみなす」ことで足りるため、本案件では警告の出力位置を変更しない。
この事実は `CLAUDE.md` のドメイン知識に追記する。
