**分割の基準**（実装すべき機能の構成に基づく。ステップ2 の調査で次の4種類の境界を列挙し、該当する境界で分ける。列挙と判定の結果を `roadmap.md` の「分割の根拠」に記録する。境界がなくマイルストーンが1個の場合も、4種類とも該当しないことを記録する）:

1. **生成物の境界**: あるステージの出力（ファイル・データ）が次のステージの入力になり、そのステージ単独で実行して出力を確認できるところ（パイプラインのステージ単位）
2. **判断の境界**: Go/No-Go 判定・パラメータの採否・ユーザー承認など、その結果で後段の設計内容が変わる判断があるところ（判断の前後で分ける）
3. **新規コンポーネントの境界**: 新しいスクリプト・モジュール・外部ツール連携（subprocess で呼ぶ CLI 等）を追加する場合、そのコンポーネントの単体疎通を1マイルストーンにする
4. **環境の境界**: 新しい実行環境・ライブラリ・ジョブ基盤の初回疎通は、本体の実装より前の独立したマイルストーンにする（リスクの高い前提の先行検証）

**分けない条件**: 上記の境界がない単一機能の追加（既存スクリプトへのオプション追加・入力形式の追加等）は1マイルストーンとする。中間生成物が内部データにすぎず、後段なしに確認する意味がないものは境界にしない。

**併合の規則**（複数の境界が同時に該当する場合）: 次の3条件を**すべて**満たすときに限り、複数種の境界に該当する一連の作業を1マイルストーンにまとめる。1つでも満たさなければ分ける。

1. 判断の境界を含まない（判断の結果で後段の設計内容が変わるため、判断の前後は常に分ける）
2. 各作業が単独では、指定済みの入力から検証可能な出力を生成できない（例: ジョブスクリプトは実行して初めて出力が出る。設定ファイルはそれを読むドライバなしに検証できない）
3. 共通の完了条件が、それらを同一の1回の実行で初めて満たされる（例: 新規ジョブスクリプトの作成・実行環境の初回疎通・処理本体の疎通は、1回のジョブ投入で出力ファイルが出て初めて完了条件を満たす。バッチのドライバとそのジョブスクリプト・設定ファイルは1回のバッチ投入で初めて完了条件を満たす）

**マイルストーン ID とフォルダ**: ID は `M1`, `M2`, … と順に振り、フォルダ名は `m{番号}-{slug}`（例: `m1-env-smoke/`）とする。**ID は振り直さない**。ロードマップの改訂でマイルストーンを挿入する場合は枝番（例: `M3-1`, `M3b`。フォルダは `m3-1-{slug}/`, `m3b-{slug}/`）、追加する場合は末尾の番号を進める。作成済みのフォルダは案件フォルダと同様に削除・改名しない（中止したマイルストーンは `README.md` に中止と理由を記録して残す）。

**分割漏れの信号**: 設計書が肥大する、Codex レビューが収束しない、実装中に不要な機能や設計の欠陥が判明する、といった症状が出たら、微修正で押し通さず（「行き詰まり検出」と同じ扱い）、上記4種類の境界を再評価する。境界の見落としが確認された場合は「ロードマップの改訂（再計画）」に従って分割し直す。不要と判明した機能は分割ではなく削除する。境界に影響しない設計の欠陥は、影響範囲に応じて当該 `design.md` の修正または `requirements.md` からの作り直しに戻る。

#### ロードマップとマイルストーン文書の粒度

**原則: 各情報の所在を1つの文書に限定し、他の文書は参照する（再掲しない）。** 粒度の逸脱は、ほとんどが「別の文書に属する情報を書いた」ことで起きる。文書ごとに書くこと・書かないことを次の表で固定し、判断で削らずに機械的に適用する。

| 文書 | 役割 | 書くこと | 書かないこと |
|---|---|---|---|
| `roadmap.md` | 案件全体の計画。人レビュー通過後は固定し、変更は「ロードマップの改訂（再計画）」に従う | 目標。前提（各項目に典拠を付ける: ユーザー確定 / 調査 / M-n で実証 / 未検証〔M-n で検証する〕）。現状（実証済みの事実の要約と参照）。分割の根拠（4種類の境界の列挙と併合の判定）。マイルストーン一覧（ID・名称・フォルダ名・状態）と順序。各マイルストーンの5項目: 目的・依存（前提となるマイルストーンと前提の項目）・入力と出力の概要・開始条件・完了条件（判断の境界を持つマイルストーンは6項目目として「判断結果ごとの次の行き先」を加える。失敗時の扱い・実験の位置づけ・範囲などの補助節を加えてよい）。改訂履歴（改訂理由）。任意: 保留リスト（今はやらないが候補として残すもの） | 実施結果（`README.md` とマイルストーンフォルダに置く）。実行手順・CLI オプション・ジョブ構成・スクリプト・判定に使う閾値や測定式・確認サンプル・フォールバック候補（マイルストーン文書に置く） |
| `{マイルストーンID}-{slug}/requirements.md` | そのマイルストーンの「何を・なぜ・合否」 | 機能要求（受け入れ基準に判定の具体値・チェック項目・確認対象を書く。数値判定を伴う場合はここが criteria lock の対象）。非機能要求。制約。範囲外の明示 | 手順と実装。他のマイルストーンの要求。`roadmap.md` の再掲 |
| `{マイルストーンID}-{slug}/design.md` | そのマイルストーンの「どうやるか」 | 入出力ファイルの名前と形式。CLI とジョブ構成。処理手順。テスト。スクリプトの仕様（入出力・引数・手順）とファイルへの参照 | スクリプト本体（マイルストーンフォルダ配下のファイルとして置く）。コードの全文。他のマイルストーンの設計。`roadmap.md` / `requirements.md` の再掲 |
| `{マイルストーンID}-{slug}/experiment_log.md` | 予測と実測の記録（数値判定を伴うマイルストーンのみ） | 直前予測。実測。照合と乖離の原因 | 判定基準（`requirements.md` を参照） |
| `README.md` | 案件の状態 | ステータス。マイルストーン一覧と状態。実施記録（日付・結果の1行要約・判定・承認・詳細への参照） | 計画の内容（`roadmap.md` を参照）。結果の詳細（マイルストーンフォルダを参照） |
| 案件直下の補助文書（任意。構想書・知見集・調査記録） | 記録と根拠 | 調査結果。実証された事実と未検証事項の蒸留。式や変数の定義。`roadmap.md` から参照する | 判定基準と手順（`requirements.md` / `design.md` に置く） |

- **細かさの下限**: `design.md` は「それだけを読んで、判断なしに実装または実行できる」まで書く（「ドキュメント作成ルール」の自己完結の要件と同じ）
- **細かさの上限**: コードの全文は書かない。ジョブスクリプト・実験コードの本体はマイルストーンフォルダ配下のファイルとして置き、`design.md` はその仕様と参照を書く（本体と設計書の二重管理を避ける）

#### ロードマップの改訂（再計画）

ロードマップが真価を発揮するのは複雑な実装のときで、その場合はマイルストーンの途中で中断して計画を見直すことが多い。次のいずれかが起きたら、**その場で回避策を取らずに中断**し、何が起きたか・どこまで完了したかをユーザーに報告する。

- 設計書どおりに実行できない
- ドキュメントと実装の記述が矛盾する
- 完了条件を満たせない、または判定できない
- ロードマップの前提が実際と違うと判明した（前提の典拠が覆った）
- 分割漏れの信号（「マイルストーン分割」参照）が出た

中断後は、影響範囲に応じて戻る場所を選び、再レビューを経て再開する。「行き詰まり検出」は案件全体に適用する。

| 影響範囲 | 戻る場所 |
|---|---|
| そのマイルストーンの手順だけの問題 | 当該 `design.md` の修正 → ステップ5 |
| そのマイルストーンの目的・完了条件の問題 | 当該 `requirements.md` から作り直し → ステップ5 |
| 前提・マイルストーンの分割・順序の問題 | `roadmap.md` の改訂 → ステップ3 |

`roadmap.md` の改訂は次のとおり行う。

- 同じファイルを上書きで改訂し、改訂履歴に改訂理由（覆った前提、変更した分割・順序、削除・吸収したマイルストーン）を書く。旧版は git に残るため複製しない
- マイルストーン ID は振り直さない（「マイルストーン分割」の ID 規則）。完了済みマイルストーンの記録（`README.md`・マイルストーンフォルダ）は変更しない
- 前提の典拠を更新する（実証された項目は「M-n で実証」に、覆った項目は新しい値と典拠に）
- 改訂後の `roadmap.md` をステップ3（Codex 収束 → 人レビュー）に通してから、次のマイルストーンに着手する
