# feat-015 要求仕様書: chap02 の Q&A コラム見出しの分断修復

## 1. プロジェクト概要

### 何を作るのか

『プログラミングのための確率統計』chap02 の既存の修正定義ファイル
`{BASE2}/ocr/fixes/chap02.json`（feat-013 で作成済み・リポジトリ外）に修正を1件追記し、
`apply_fixes.py`（feat-010）で既存成果物に適用したうえで、
`build_final.py`（feat-012）で `final/chap02/` を再構築する。

**リポジトリ内のコード（`scripts/`）とテストコード（`tests/test_*.py`）は一切変更しない。**
本案件で作成・更新する成果物は次の3つに限られる。

1. リポジトリ外の修正定義ファイル1件（`{BASE2}/ocr/fixes/chap02.json` への追記）
2. それを適用したリポジトリ外の既存成果物（`{NORM}/` と `{BASE2}/ocr/final/chap02/`）
3. リポジトリ内の案件ドキュメント（`docs/issues/feat-015-chap02-split-heading/`）、
   `docs/BACKLOG.md` / `docs/CHANGELOG.md` / `CLAUDE.md` の完了処理、および
   テスト結果の記録 `tests/results/feat-015_test_result.txt`（新規作成。
   CLAUDE.md「テスト」のルールで必須）

### なぜ作るのか

chap02 の Q&A コラム見出し `? 2.2` が、Markdown 上で
「見出し行 ＋ 空行 ＋ 本文段落」の3ブロックに分断されている（案件 README.md §2・§3 で原本確認済み）。
原本では1つの質問文であり、分断は MinerU の layout 解析に起因する。

分断の影響は次の2点である。

1. 見出しが文の途中（`…分数の分数になっ`）で切れており、見出しとして意味をなさない
2. 質問文の後半（`てしまいました。これは…`）が見出しではなく本文段落として出力されるため、
   文書構造（見出しの階層）が原本と一致しない

LLM に読ませる主成果物である Markdown の品質を下げるため、修正する。

あわせて、分断箇所と**同一行**にある「なんという」→「なんていう」の誤読1件を修正する
（案件 README.md §3・§4 で原本確認済み。分断を結合する `old` / `new` にこの文字列が
必ず含まれるため、誤読を残したまま結合することができない）。

feat-013 の完了時に、確率統計の手動テストで見つかった問題を3案件に分ける方針が
決まっており（2026-08-31 引き継ぎノート）、本案件はそのうちの1件である。

### 誰が使うのか

本プロジェクトのユーザー。成果物（`{BASE2}/ocr/final/chap02/chap02_gray300.md`）を
LLM に読ませて学習に用いる。

### どこで使うのか

`docs/TECH_STACK.md` に定義された既存環境（Ubuntu 24 系 / Python 3.12.3 / uv）。
新規のライブラリ・モデル・ネットワークアクセスは追加しない。

## 2. 用語定義

feat-010・feat-013・feat-016 の要求仕様書の用語を継承する。本書で用いる主な用語は次のとおり。

| 用語 | 定義 |
|---|---|
| 修正定義ファイル | OCR 誤りを「修正前文字列（`old`）→ 修正後文字列（`new`）」のペアで記録した JSON。`{BASE2}/ocr/fixes/{name}.json` に置く。書籍本文を含むためリポジトリに置かない（feat-010） |
| 見出しの分断 | 原本では1つの見出しである文が、MinerU の layout 解析により「見出しブロック」と「非見出しブロック」の2つに分割されて出力された状態。本件の `? 2.2` がこれにあたる |
| Q&A コラム見出し | 本書籍の枠囲みコラムの質問文。Markdown では `## ? {章番号}.{連番} {質問文}` として出力される |
| 語彙単位の誤り | 1文字の字形置換では表現できず、複数文字の並びとしてのみ判定できる誤り。本件の「なんという → なんていう」がこれにあたる（feat-016 の「上的 → 上の」と同種） |
| 再適用 | 既に構築済みの成果物（`run-NN-normalized/` と `final/`）に対し、MinerU を再実行せずに修正適用・final 再構築のみを行うこと（feat-013 §2） |
| `{BASE2}` | `/home/sakagawa/work/確率統計`（git 管理外・リポジトリ外） |
| `{NORM}` | `{BASE2}/ocr/mineru-full/chap02/run-01-normalized`（chap02 の正規化済みディレクトリ） |
| `{FINAL}` | `{BASE2}/ocr/final/chap02`（chap02 の最終成果物ディレクトリ） |

## 3. 機能要求一覧

### FR-001: chap02 の修正定義ファイルへの修正追記

- **機能名**: `{BASE2}/ocr/fixes/chap02.json` への修正1件の追記
- **概要**: 分断した見出しの結合と、同一行の「なんという → なんていう」の訂正を、
  `fixes/template.json` の書式に従って**1件の fix** として定義し、既存の
  `chap02-001` の後ろに追記する
- **入力**: 案件 README.md §2・§3 で確定した誤り箇所（1箇所）
- **出力**: `{BASE2}/ocr/fixes/chap02.json`（既存ファイルの更新。UTF-8・JSON）
- **受け入れ基準**:
  1. `fixes/README.md`・`fixes/template.json` の書式に従い、`id` / `reason` / `old` / `new` の
     4キーをすべて文字列で持つ fix が**1件追加**され、追記後の `fixes` 配列の要素数が
     **2件**（既存の `chap02-001` ＋ 新規1件）になる
  2. 既存の `chap02-001` の `id` / `reason` / `old` / `new` を1文字も変更しない
  3. `apply_fixes.py` の `validate_fixes` がエラーを1件も出さない
  4. 適用**前**の `{NORM}/chap02_gray300.md` において、新規 fix の `count(old) == 1` である
  5. 適用**後**の `{NORM}/chap02_gray300.md` において、新規 fix の `count(new) == 1` である
     （`apply_fixes.py` の最終不変条件。CLAUDE.md の運用ルール）
  6. `reason` に、原本 TIF で確認済みであることと、`old` / `new` を一意にするために
     文脈を含めた理由を日本語で記述する
  7. ファイルはリポジトリに置かず、コミットもしない（feat-010 の運用）

### FR-002: 分断した見出しの結合

- **機能名**: `? 2.2` の見出しの1行への結合
- **概要**: 見出し行・空行・後続段落の3ブロックを、1つの見出し行に結合する
- **入力**: `{NORM}/chap02_gray300.md`（適用前）
- **出力**: `{NORM}/chap02_gray300.md`（適用後）
- **受け入れ基準**:
  1. 適用後の md の 546 行目が、次の1行になる（前後に他の変更がない）

     ```
     ## ? 2.2 本文の例の条件つき確率を式 (2.7) で求めようとしたら、 $\frac{3/16}{9/16}$ なんていう分数の分数になってしまいました。これはどうやって計算したらいいのですか？
     ```

  2. 適用後の md に文字列 `分数の分数になっ\n\nてしまいました。`（改行2つを挟む形）が
     **0 件**である
  3. 適用後の md の総行数が、適用前より **2 行少ない**
     （見出し行・空行・後続段落の3行が1行になるため）
  4. 適用後の md に `## ? 2.3` 以降の見出しが適用前と同じ内容で残っている
     （後続の Q&A 見出しを巻き込んでいないことの確認）

### FR-003: 「なんという」の誤読の訂正（chap02 の1件のみ）

- **機能名**: 見出し行内の「なんという」→「なんていう」の訂正
- **概要**: FR-002 の結合と同一の fix で、同じ行にある誤読1件を訂正する
- **入力**: `{NORM}/chap02_gray300.md`（適用前）
- **出力**: `{NORM}/chap02_gray300.md`（適用後）
- **受け入れ基準**:
  1. 適用後の `{NORM}/chap02_gray300.md` に「なんという」が **0 件**である
     （適用前は1件。件数はすべて Python の `str.count()` による**出現回数**で数える。
     `apply_fixes.py` の不変条件と同じ数え方であり、行数ではない）
  2. 適用後の `{NORM}/chap02_gray300.md` に「なんていう」が **1 件**である（適用前は0件）
  3. chap02 以外の9章の md に含まれる「なんという」計9件を**変更しない**
     （本案件のスコープ外。§7）

### FR-004: 既存成果物への修正の適用と final の再構築

- **機能名**: chap02 の再適用
- **概要**: MinerU と `normalize_punct.py` を再実行せず、`apply_fixes.py` と
  `build_final.py` のみを実行して chap02 の成果物を更新する
- **入力**:
  - `{NORM}/chap02_gray300.md`（正規化済み・feat-013 適用後の状態）
  - `{BASE2}/ocr/fixes/chap02.json`（FR-001 の成果物）
- **出力**:
  - `{NORM}/chap02_gray300.md`（インプレース更新）
  - `{FINAL}/`（再構築）
- **受け入れ基準**:
  1. `apply_fixes.py` の終了コードが 0 で、`applied = 1`・`skipped = 1` である
     （新規 fix が適用され、feat-013 で適用済みの `chap02-001` は skipped になる）
  2. `build_final.py` の終了コードが 0 である（3種類の機械検証がすべて合格）
  3. 適用後の `{NORM}/chap02_gray300.md` の文字数が **69000 文字**である
     （適用前 69002 文字 − 改行2文字。「と」→「て」は 1 文字 → 1 文字であるため
     文字数に影響しない。2026-08-31 実測に基づく）
  4. 適用前後で、本修正箇所以外の差分が**ない**（`diff` の差分ハンクが1つのみ）
  5. `{FINAL}/` の md・content_list.json が `{NORM}/` とバイト同一である
  6. `{FINAL}/images/` のファイル数が **47** のまま変わらない
  7. `{NORM}/chap02_gray300_content_list.json` は**変更されない**
     （`apply_fixes.py` は md のみを対象とする既存ポリシー。feat-010／feat-013 §6.1）

### FR-005: 影響範囲の限定

- **機能名**: 本案件で変更しない対象の明示
- **概要**: 修正の影響を chap02 の md 1箇所に限定する
- **受け入れ基準**:
  1. `scripts/` 配下のコードを1行も変更しない
  2. `tests/test_*.py`（テストコード）を1行も変更しない。
     `tests/results/feat-015_test_result.txt` の新規作成は**この制限の対象外**であり、
     CLAUDE.md「テスト」のルールに従って必ず作成する
  3. 確率統計の chap02 以外の9章の成果物・修正定義ファイルを変更しない
  4. PRML（`{BASE}`）の成果物を変更しない
  5. 既存の自動テストを全件実行し、feat-016 完了時点と同じくすべて成功する

## 4. 非機能要求

| 項目 | 要求 |
|---|---|
| 性能 | 再適用は chap02 1章のみ・MinerU 再実行なしのため、全工程が 10 秒以内に完了する |
| 再現性 | `apply_fixes.py` は冪等である（2回目以降の実行では `old` 不在・`new` 1件のため `skipped` として扱われ、終了コード 0・内容不変） |
| 可搬性 | 修正定義ファイルは書籍本文を含むためリポジトリ外に置く。リポジトリ側には書式テンプレート（`fixes/template.json`）のみを保持する（feat-010 の既存方針） |
| 保守性 | 修正の根拠（原本確認の事実と一意性確保の理由）を `reason` に残し、再 OCR 時に文面が変われば `apply_fixes.py` がエラーで検出できる状態を保つ |

## 5. 制約条件

- **MinerU を再実行しない**。OCR 結果は同一入力に対して変わらず、10章で約35分の実行コストに
  見合わない。分断は MinerU の layout 解析に起因するため、再実行しても再発する
  （feat-013 ADR-3・feat-016 ADR-2 と同じ判断）
- **`normalize_punct.py` を再実行しない**。feat-013 で適用済みであり、本案件は字形正規化
  テーブルを変更しないため結果は変わらない
- **`final/` を直接編集しない**。final は `run-NN-normalized/` からのコピーであり、コピー元を
  更新しないと次回の final 再構築で変更が失われる（feat-013 の既存方針）
- **`content_list.json` を修正しない**。MinerU のスキーマを維持する既存ポリシー（feat-010）。
  結果として md と json の当該箇所の表記・ブロック構造が一致しなくなるが、これは
  feat-013 §6.1・feat-016 §8 で許容済みの既知事項である
- 修正定義ファイルの実体は**コミット禁止**（書籍本文を含むため）
- 本案件は**コード変更を含まない**。作業中にコード変更が必要と判明した場合は中断して報告する

## 6. 優先順位

| 要求 | 優先度（MoSCoW） | 理由 |
|---|---|---|
| FR-001 | Must | 修正の定義そのもの。これがないと何も実行できない |
| FR-002 | Must | 本案件の主目的（見出しの分断修復） |
| FR-003 | Must | FR-002 の `old` / `new` に同じ文字列が含まれるため、FR-002 と不可分である |
| FR-004 | Must | 成果物に反映されなければ目的を達しない |
| FR-005 | Must | 影響範囲の逸脱は他章・他書籍の成果物を壊す危険がある |

MVP は FR-001〜FR-005 の全件である（いずれか1つでも欠けると成果物が不整合な状態で残る）。

## 7. スコープ外

次の項目は本案件では扱わない。

- **「なんという → なんていう」の残り9件**（chap01 の1件・chap03 の3件・chap06 の4件・chap08 の1件）。
  案件 README.md §4 のとおり全件が原本確認済みの誤読だが、2026-08-31 のユーザー決定により
  **別案件（feat-017 として起票予定）で扱う**。本案件では chap02 の1件のみを、
  分断修復と不可分なものとして修正する
- 見出しの分断を自動検出する仕組みの追加（本件は手動テストで発見した1件のみを対象とする）
- MinerU の layout 解析パラメータの調整（本プロジェクトは MinerU を既定設定で用いる）
- `normalize_punct.py` の置換表への「なんという → なんていう」の追加
  （機能設計書 ADR-1 で不採用とする理由を記す）
- feat-014（Q&A コラム見出しの「？」アイコン分離）の修正
- `content_list.json` におけるブロック分断の解消（`apply_fixes.py` の対象外。機能設計書 §8）
- PRML 成果物への字形正規化の再適用（引き継ぎノートの別項目）
