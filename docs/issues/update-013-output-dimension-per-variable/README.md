## 1. 経緯・目的

### 1.1 契機

feat-025 の `roadmap.md`（新基準 1.11 で 6 回のレビューを経て収束）について、ユーザーが右ペインの Claude Code（Opus 5）に「最終出力の次元は何？」と問うた（2026-09-09 00:08〜00:19。セッション `1dbee7b0-a0a7-4f8d-87e9-161c21a8cb0b`）。

| 回答者 | 答え | 誤り |
|---|---|---|
| Opus（1 回目） | 3（独立な成分 `N`・`k`・`u` の数） | `N`・`k`・`u` は S2・S4 の出力で、S5 の入力。最終出力ではない |
| Opus（2 回目。ユーザー「入力が 3 次元としか読めないのだが？最終出力は何？」の後） | 欠落件数 `M` の 1 変数で次元 1 | 区間を数えていない（ユーザーの定義では区間は 2 次元の変数として別に数える） |
| Claude Code〔Fable〕（本セッション。人レビュー前の確認） | S5 の出力の次元は 3（独立成分）であるべき | Opus の 1 回目と同じ誤り。式の入力の個数を出力の次元と呼んだ |
| Codex（codex-06〜11） | S5 の出力の次元を 6 → 10（報告書の数値の個数）に直させ、C で通した | 報告書に印字する数の個数を次元と呼んだ |

**ユーザーの定義**（2026-09-09）: 「出力が 1 変数 M で M がスカラーだったら 1 次元。出力が 1 変数で M が 3×3 の行列だったら 9 次元。出力が 2 変数で x がスカラー、y が 2 次元ベクトルだったら 1 次元と 2 次元」。次元は出力の変数ごとに、その変数の成分の数。変数が複数なら変数ごとに書き、足し合わせない。

**ユーザーが次元と式を使う目的**（2026-09-09）: (1) パイプラインの前後で次元が合っていなければ破綻するので、境界で照合しやすい (2) ステージ内は「入力 → 式 → 出力」で次元が変わるが、式がその次元の変換と意味が合っているかの検査にも使う (3) 次元と式が想定できない場合は、事前に調査するマイルストーンを置く。「インターフェース」等への言い換えは採らない（数として突き合わせられないため）。

### 1.2 規定の文面のどこが誤りを生んだか

| 箇所 | 現行の文面 | 生んだ読み |
|---|---|---|
| `CLAUDE.md`「パイプラインの切り方」ステップ2 の 1 | 「独立な成分と従属な成分（独立な成分からの式で決まるもの）に分ける。次元数（独立な成分の数）を明記する」 | 「他のすべてを式で生成できる最小の量の集合を探せ」と読め、探すと測定値（`N`・`k`・`u`）に行き着く。測定値が「最終出力の独立な成分」に化け、区間は「従属だから次元に数えない」ことになる |
| 同 3「決める項（最終出力の式のどの成分を決めるか）」 | ステージが決めるのは最終出力の式の**入力**（測定値）であるのに「成分」と書いている | ステージの出力（測定値）を最終出力の成分と同一視する |
| `docs/REVIEW_CRITERIA.md` 1.11 項目 1・2 | 「最終出力の成分の次元数に一致」「独立な成分のすべてが決める項に現れる」 | 同上。Codex が S5 の出力を「報告書の数値の個数」に合わせさせた（codex-06 中1） |
| 同 1.11 全体 | 式が「入力の次元 → 出力の次元」の変換として意味が合っているかの検査項目が無い | S5 の入力 3 成分から式で出るのは推定件数 1 と区間 2 であるのに、出力の次元 10 や 3 が通った |

update-008 のシミュレーション（README §1.2 (b)）では、列名は「最終出力の式のどの**項**を決めるか」で、中身は `N_i`・`n_i`・`k_i`・`n'_i`（測定値）だった。規定に書き写す際に「項」が「成分」になり、測定値と出力の区別が落ちた。

### 1.3 目的

1. 最終出力の次元を「変数ごとの成分の数」で定義し、独立／従属の区別と「次元数（独立な成分の数）」を廃止する
2. ステージの出力（測定値）が最終出力の式の入力であって最終出力の変数ではないことを、規定と検査項目の両方に書く
3. 「式が入力の次元から出力の次元への変換として意味が合っているか」を検査項目（1.11 項目 7）に加える
4. 「決める項」は残し、「このステージの出力が最終出力の式のどの入力になるか」と定義し直す

判定条件は update-008〜012 と同じ（記入欄と手順だけで構成し、判断を要求しない）。

### 1.4 採らなかった案と不採用の理由

| 案 | 不採用の理由 |
|---|---|
| 「次元」を「インターフェース」「スキーマ」等に言い換える | ユーザー 2026-09-09。次元は数なので境界で突き合わせられる。インターフェースは形・型の話で数として照合できない |
| 「右辺・左辺」で最終出力と測定値を区別する（Claude Code 案） | ユーザー「右辺に入力を置くことも出力を置くことも可能なので、そんな分かりにくい表現はしない」。入力と出力だけで書く |
| 独立／従属の区別を残し、定義だけ直す | 「式で決まるものは次元に数えない」という読みそのものが誤りの経路。区別を廃止する |
| 「決める項」を廃止する | ステージの出力が最終出力の式のどの入力になるかは、リネージとして要る（update-008 の目的「最終出力に寄与しない作業が見える」）。定義を入力・出力の語で書き直して残す |
| feat-025 の `roadmap.md` を本案件で直す | 案件文書の修正は元案件側（feat-025）で扱う規定。本案件の完了後に右ペインの Opus がユーザーの指示で書き直す |
