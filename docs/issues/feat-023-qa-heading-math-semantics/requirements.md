# feat-023 要求仕様書: Q&A コラム見出しの意味に影響する数式記号の欠落2件の修正

## 1. プロジェクト概要

### 何を作るのか

『プログラミングのための確率統計』の Q&A コラム見出し **2件**（chap06 `? 6.3` / chap08 `? 8.3`）を、
**原本の数式表記と完全に一致させる**。手段は既存の修正定義ファイル
（`{BASE2}/ocr/fixes/chap06.json`・`chap08.json`。いずれも作成済み・リポジトリ外）への
**計4件の追記**と、`apply_fixes.py`（feat-010）→ `build_final.py`（feat-012）の再適用である。

**リポジトリ内のコード（`scripts/`）とテストコード（`tests/test_*.py`）は一切変更しない。**
本案件で作成・更新する成果物は次の3つに限られる。

1. リポジトリ外の修正定義ファイル2件への追記（`chap06.json` に2件、`chap08.json` に2件）
2. それを適用したリポジトリ外の既存成果物（2章の `{NORM_NN}/` と `{FINAL_NN}/`）
3. リポジトリ内の案件ドキュメント（`docs/issues/feat-023-qa-heading-math-semantics/`）、
   `docs/BACKLOG.md` / `docs/CHANGELOG.md` / `docs/PROJECT_KNOWLEDGE.md` の完了処理、および
   テスト結果の記録 `tests/results/feat-023_test_result.txt`（新規作成。
   CLAUDE.md「テスト」のルールで必須）

**`CLAUDE.md` は更新しない**（update-003 で確定した非対称ルール）。
`docs/PROJECT_KNOWLEDGE.md` の更新要否は機能設計書 §11 で定める。

### なぜ作るのか

feat-021（全74件の原本突合）で、**意味に影響する数式記号の欠落が2件**あることが確定した
（後続案件案 B）。

| 章 | 番号 | 失われたもの | 意味への影響 |
|---|---|---|---|
| chap06 | 6.3 | 推定量のハット（`θ̂` → 素の `θ`） | **θ（真のパラメータ）と θ̂（その推定量）の区別が消える。** 見出しは「あらゆる種目 θ に対して最良の推定量 θ̂ を探す」という質問であり、ハットが失われると質問が成立しない |
| chap08 | 8.3 | 太字（ベクトル記法。`\boldsymbol{q}_i`・`\boldsymbol{x}` → 素の `q_{i}`・`x`） | **ベクトルとスカラーの区別が消える。** `z_i = q_i · x` は「ベクトル `q_i` とベクトル `x` の内積がスカラー `z_i`」という式であり、太字の有無で式の意味が変わる |

いずれも文字としては正当なため既存の警告・機械検証では検出できず（案件 README.md §6）、
残せば本プロジェクトのゴール「入力への忠実な OCR」に反する。

### 誰が使うのか

本プロジェクトのユーザー。成果物（`{BASE2}/ocr/final/chapNN/chapNN_gray300.md`）を
LLM に読ませて学習に用いる。**数式の意味が変わっている箇所は学習内容の誤りに直結する。**

### どこで使うのか

`docs/TECH_STACK.md` に定義された既存環境（Ubuntu 24 系 / Python 3.12.3 / uv）。
新規のライブラリ・モデル・ネットワークアクセスは追加しない。

## 3. 機能要求一覧

### FR-001: 修正定義ファイルへの修正追記（2章・計4件）

- **機能名**: `{BASE2}/ocr/fixes/chap06.json`・`chap08.json` への修正各2件（計4件）の追記
- **概要**: 4件を `fixes/template.json` の書式に従って定義し、各ファイルの既存 fix の後ろに追記する
- **入力**: 案件 README.md §2・§4 で確定した4箇所
- **出力**: 上記2ファイル（既存ファイルの更新。UTF-8・JSON）
- **受け入れ基準**:
  1. `fixes/README.md`・`fixes/template.json` の書式に従い、`id` / `reason` / `old` / `new` の
     4キーをすべて文字列で持つ fix が**各ファイルに2件ずつ追加**され、追記後の `fixes` 配列の
     要素数が chap06 = **9**（既存7＋新規2）、chap08 = **5**（既存3＋新規2）になる
  2. 新規 fix の `id` は `chap06-008` / `chap06-009` / `chap08-004` / `chap08-005` とする
     （各ファイルの既存 ID の最大値 + 1 からの連番）
  3. 既存の fix（chap06-001〜007、chap08-001〜003 の計10件）の
     `id` / `reason` / `old` / `new` を1文字も変更しない
  4. `apply_fixes.py` の `validate_fixes` が2ファイルとも エラーを1件も出さない
  5. 適用**前**の各 `{NORM_NN}/chapNN_gray300.md` において、新規 fix の `count(old) == 1` である
  6. 適用**後**の各 `{NORM_NN}/chapNN_gray300.md` において、当該章の**全 fix** について
     `count(old) == 0` かつ `count(new) == 1` である（最終不変条件）
  7. 各 `reason` に、失われた記号の種類と意味への影響、原本確認の根拠、
     および `old` / `new` を一意にするために文脈を含めた理由を日本語で記述する
  8. ファイルはリポジトリに置かず、コミットもしない（feat-010 の運用）

### FR-002: 対象2行を原本の数式表記と一致させる

- **機能名**: Q&A コラム見出し `? 6.3` / `? 8.3` の数式表記の復元
- **概要**: 2行を原本と完全に一致させる（2026-09-06 ユーザー決定。案件 README.md §3）
- **入力**: 各 `{NORM_NN}/chapNN_gray300.md`（適用前）
- **出力**: 同（適用後）
- **受け入れ基準**:
  1. 適用後の `chap06_gray300.md` の **253 行**が次の文字列と**完全に一致**する:

     ```
     ## ? 6.3 あらゆる種目 $\theta$ ですべてのライバルを凌駕する全種目征覇なスーパーチャンピオンの推定量 $\hat{\theta}$ を探さないといけないわけですか。がんばって探してみますね。
     ```

  2. 適用後の `chap08_gray300.md` の **285 行**が次の文字列と**完全に一致**する:

     ```
     ## ? 8.3 第 $i$ 主成分が $z_{i}=\boldsymbol{q}_{i}\cdot\boldsymbol{x}$ で求められるのはなぜ？
     ```

  3. 適用後の対象2行に**素の `θ` が0件**（chap06 253行）であり、
     `\hat{\theta}` が **1件**・`$\theta$` が **1件**含まれる
  4. 適用後の対象2行に `\boldsymbol{q}_{i}` と `\boldsymbol{x}` が**各1件**含まれる（chap08 285行）
  5. 件数はすべて Python の `str.count()` による**出現回数**で数える。**`grep -c` を使わない**

### FR-003: 既存成果物への修正の適用と final の再構築

- **機能名**: 対象2章の再適用
- **概要**: MinerU と `normalize_punct.py` を再実行せず、`apply_fixes.py` と
  `build_final.py` のみを章ごとに実行する
- **入力**: 各 `{NORM_NN}/chapNN_gray300.md` と `{BASE2}/ocr/fixes/chapNN.json`
- **出力**: 各 `{NORM_NN}/chapNN_gray300.md`（インプレース更新）と各 `{FINAL_NN}/`（再構築）
- **受け入れ基準**:
  1. `apply_fixes.py` の終了コードが2章とも 0 で、`applied` / `skipped` が次のとおりである:

     | 章 | applied | skipped |
     |---|---|---|
     | chap06 | 2 | 7 |
     | chap08 | 2 | 3 |

  2. `build_final.py` の終了コードが2章とも 0 である（3種類の機械検証がすべて合格）
  3. 適用後の md の文字数・行数が次のとおりである:

     | 章 | 文字数（前 → 後） | 行数（前 → 後） |
     |---|---|---|
     | chap06 | 36399 → **36419**（+20） | 833 → **833** |
     | chap08 | 67202 → **67229**（+27） | 1566 → **1566** |

  4. 適用前後の `diff`（通常形式）の差分ハンク数が**2章とも 1** である
     （各章の2件の修正が同一行にあるため1ハンクに収まる）
  5. 各 `{FINAL_NN}/` の md・content_list.json が対応する `{NORM_NN}/` とバイト同一である
  6. 各 `{FINAL_NN}/images/` のファイル数が変わらない（chap06 = 19 / chap08 = 43）

## 4. 非機能要求

| 項目 | 要求 |

## 5. 制約条件

- **MinerU を再実行しない**（feat-013 ADR-3・feat-022 ADR-6・feat-020 ADR-7 と同じ判断）
- **`normalize_punct.py` を再実行しない**
- **`final/` を直接編集しない**（コピー元 `{NORM_NN}` を更新する）
- **`content_list.json` を修正しない**（feat-010 の既存ポリシー。md と json の当該箇所の状態が
  食い違うが、feat-013 §6.1・feat-022 §8・feat-020 §8 で許容済み）
- **置換表（`normalize_punct.py`）に本件を追加しない**（機能設計書 ADR-1）
- **対象2行以外の `D4`（数式マークアップの欠落）を修正しない**（2026-09-06 ユーザー決定の範囲は
  「対象の見出し2行」であり、他の16件は案 F に残す）
- **`old` / `new` に見出し記号（`## ? 6.3` 等）を含めない**（機能設計書 ADR-3）。
  見出し体裁は feat-020 で確定済みであり、番号や `?` を `old` に含めると結合度が上がるため
- **`CLAUDE.md` を変更しない**（update-003 の非対称ルール）
- 修正定義ファイルの実体は**コミット禁止**
- 本案件は**コード変更を含まない**。作業中にコード変更が必要と判明した場合は中断して報告する
